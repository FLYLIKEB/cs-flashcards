# 기업 지원서 작성

## 정본과 범위

- 먼저 `applications/application_material_bank.md`를 전부 읽습니다.
- 기존 지원서를 수정할 때는 대상 파일도 전부 읽고 문항, 제한, 어조를 보존합니다.
- 공고나 입력 화면이 제공되면 문항 원문, 글자·바이트 제한, 블라인드 규칙을 우선합니다.
- 소재은행에 없는 경력, 수치, 기간, 역할, 성과를 만들지 않습니다. 불확실하거나 충돌하는 값은 `제출 전 확인사항`을 따릅니다.

## 작성 원칙

1. 문항이 평가하는 역량을 한 문장으로 정하고 소재은행의 `문항별 추천 조합`에서 가장 강한 경험 하나를 고릅니다.
2. 경험마다 수행 장소를 명시합니다: `재직 중 사내 프로젝트`, `학교교육`, `직업교육`, `팀 프로젝트`, `개인 프로젝트`, `자율 스터디`.
3. 상황·본인 행동·검증 가능한 결과·지원 직무 연결 순으로 씁니다. 여러 경험을 요구하지 않으면 대표 경험 하나를 깊게 씁니다.
4. 회사나 기관 설명보다 본인의 판단과 행동에 더 많은 분량을 씁니다. 기술명과 수치는 문제 해결의 근거로만 사용합니다.
5. 지원기업의 사업, 고객, 직무에 맞게 마지막 연결 문장을 새로 씁니다. 다른 기관명을 재사용하지 않습니다.
6. 약점·실패 문항에서는 한계를 숨기지 말고 이후 바뀐 행동과 검증 가능한 후속 경험을 연결합니다.

## 블라인드와 증빙

- 공고가 금지하면 회사명, 학교명, 출신지역, 가족관계, 성별, 나이, 성명, 신체조건, 총학점, 종교를 쓰지 않습니다.
- 회사명 대신 규모와 업무를 사용합니다. 예: `이용자 100만 명 이상인 커머스 플랫폼의 사내 상품 전시 프로젝트`.
- 학교명 대신 `학교교육`, 조직명 대신 `사내 서비스개발 조직`을 사용합니다.
- 소재은행에서 확인 필요로 표시한 값은 증빙 전까지 단정하지 않습니다. 특히 밋업 사회 횟수, OOM 경험의 귀속, 공식 전공명, 협업 조직 수를 확인합니다.

## 산출물과 검증

- 새 기업은 `applications/<company>_application_answers.md`, 입력용 근거는 필요할 때만 `applications/<company>_application_form_inputs.md`에 작성합니다.
- 각 답변 위에 문항 원문 또는 짧은 문항 제목과 실제 글자 수를 기록합니다. 바이트 제한이면 공고의 계산법을 따릅니다.
- 최종 확인:
  - 표시한 글자 수와 실제 본문 길이가 일치하는가?
  - 모든 답변이 제한 안에 있는가?
  - 경험의 수행 장소와 본인 역할이 드러나는가?
  - 수치와 기간이 소재은행 및 증빙 상태와 일치하는가?
  - 다른 회사명·기관명·문항 답변이 남지 않았는가?
  - 같은 경험을 여러 문항에서 불필요하게 반복하지 않았는가?
- 변경 후 관련 파일만 명시적으로 스테이징하고 프로젝트 `AGENTS.md`의 검증·커밋·푸시 규칙을 따릅니다.

## 소재은행 갱신 경계

- 새 사실이나 증빙을 사용자가 제공하면 해당 지원서에 먼저 반영합니다.
- 사용자가 소재은행 갱신도 요청한 경우에만 `applications/application_material_bank.md`를 함께 수정합니다.
