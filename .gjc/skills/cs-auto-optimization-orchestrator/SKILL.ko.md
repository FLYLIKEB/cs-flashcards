# CS 자동 최적화 오케스트레이터

이 문서는 매 감사 결과를 GitHub 이슈로 바꾸고, 이미 열려 있는 최적화 이슈가 있으면 그 이슈부터 실행 백로그로 재사용하며, 이슈 단위 서브에이전트를 병렬로 돌려 저장소 전반의 최적화 루프를 굴릴 때 사용한다.

## 강한 게이트

- 이미 열려 있는 최적화 이슈를 무시하지 않는다. 아직 유효하고 활성 PR/worktree가 붙어 있지 않다면 사라질 때까지 기다리지 말고 현재 실행 웨이브에 바로 편입한다.
- 같은 구체적 발견사항에 대해 중복 이슈를 만들지 않는다. 기존 이슈를 재사용하고 최신 감사 근거를 본문이나 코멘트에 보강해서, 배포 가능한 단위당 이슈 하나만 유지한다.
- 준비 상태 게이트는 활성 PR, 진행 중 리뷰, 충돌하는 이슈 worktree/branch 때문에 막히는 것이지, 재사용 가능한 열린 이슈가 존재한다는 이유만으로 막히는 것이 아니다.
- 감사 패스를 한 번 돌릴 때마다 결과를 artifact로 남기고, 채택된 발견사항은 구현 위임 전에 반드시 GitHub 이슈로 정규화한다.
- 메인 에이전트 응답은 짧게 유지한다. 자세한 근거는 채팅이 아니라 artifact, 이슈 본문, PR 본문, 리뷰 코멘트에 남긴다.
- 백엔드와 프론트엔드 모두 손볼 필요가 있으면 분리된 트랙으로 진행한다. 프론트엔드 검토에는 단순 버그뿐 아니라 UI/UX 개선 후보도 포함해야 한다.
- 각 구현 트랙은 반드시 이슈 단위여야 하며, 자기 전용 worktree/branch, 자기 전용 한글 PR 제목/본문, 자기 전용 서브에이전트 레인을 사용해야 한다.
- 리뷰 레인은 연속적으로 돈다. PR이 바뀌면 diff를 다시 보고, 차단 코멘트를 남기거나 승인한다.
- 승인이 나고 검증을 통과한 뒤에만 머지한다. 머지 후에는 완료된 worktree를 제거하고 연결된 이슈를 닫는다.
- 의미 있는 백엔드/프론트엔드 최적화 후보가 더 이상 없고, 현재 기준으로 저장소 완성도가 최소 95% 이상이라고 볼 수 있을 때만 루프를 멈춘다.

## 준비 상태 점검

1. GitHub의 열린 이슈를 확인한다.
   ```bash
   gh issue list --state open --limit 100 --json number,title,state,labels,assignees,url
   ```
2. GitHub의 열린 PR을 확인한다.
   ```bash
   gh pr list --state open --limit 100 --json number,title,headRefName,baseRefName,reviewDecision,mergeStateStatus,isDraft,url
   ```
3. 로컬 worktree를 확인한다.
   ```bash
   git worktree list --porcelain
   ```
4. 열린 이슈를 다음 셋으로 분류한다.
   - 재사용 가능한 백로그 이슈: 아직 유효하고, 활성 PR/worktree가 없으며, 지금 바로 실행 가능한 이슈
   - 진행 중 이슈: 이미 활성 PR, 리뷰 사이클, worktree와 연결되어 있어서 중복 실행하면 안 되는 이슈
   - 만료되었거나 범위 밖인 이슈: 현재 최적화 웨이브 대상이 아닌 이슈
5. 진행 중 PR/worktree 차단 요소가 있으면, 차단 요소와 재사용 가능한 백로그를 함께 요약한 짧은 상태 artifact를 작성한다. 반대로 차단 요소가 없고 재사용 가능한 백로그 이슈가 있으면 대기하지 말고 즉시 이슈 실행으로 넘어간다.

## 대기 루프

막힌 저장소 상태는 재사용 가능한 이슈 백로그 때문이 아니라, 활성 PR/worktree 충돌 때문에 생기는 폴링 상태다.

1. 스킬이 시작되면 즉시 준비 상태 점검을 실행한다.
2. 차단 요소가 남아 있으면 최신 차단 스냅샷을 `artifacts/auto-optimization-readiness.json`에 기록한다.
3. 재사용 가능한 백로그 이슈가 있고 이를 막는 PR/worktree 충돌이 없다면, 즉시 대기 상태를 벗어나 그 이슈들부터 실행한다.
4. 그렇지 않으면 백그라운드에서 살아 있으면서 준비 상태 점검을 반복 실행한다.
5. 충돌하는 PR/리뷰/worktree 차단 요소가 해소될 때까지 계속 반복한다.
6. 차단 요소가 사라지는 즉시 기존 백로그부터 다시 집행한다. 새로운 감사 패스는 재사용 가능한 이슈 백로그가 비었을 때만 다시 연다.

## 최적화 라운드

이 단계는 충돌하는 PR/worktree 차단 요소가 없을 때만 실행한다.

1. 재사용 가능한 이슈 백로그가 비어 있거나, 현재 백로그를 소진한 뒤 새 패스가 필요할 때 저장소를 감사해서 구체적인 개선 후보를 찾는다.
   - 백엔드: 정확성, 안전성, 배포/런타임 리스크, 데이터 무결성, 테스트 공백, 성능 병목, 유지보수성
   - 프론트엔드: UX 마찰, 접근성, 상태 버그, 시각적 불일치, 반응형 문제, 헷갈리는 플로우
2. 구체적이고, 검증 가능하며, 실제로 배포 가치가 있는 후보만 남긴다.
3. 현재 감사 패스에서 채택한 각 발견사항마다 GitHub 이슈를 생성하거나 기존 이슈를 재사용한다.
   - 먼저 기존 열린 이슈를 검색한다.
   - 범위가 같은 이슈가 이미 있으면 중복 생성하지 말고 최신 감사 근거로 그 이슈를 갱신한다.
   - 한 이슈가 정말로 교차 영역이며 검증 경계도 묶여 있는 경우가 아니라면 백엔드/프론트엔드 이슈를 분리한다.
   - 이슈 제목은 한글로 쓴다.
   - 본문에는 acceptance criteria, 검증 메모, 감사 근거를 넣는다.
4. 실행 큐는 다음 둘을 합쳐서 만든다.
   - 기존에 열려 있던 재사용 가능한 백로그 이슈
   - 이번 감사 패스에서 새로 생성했거나 갱신한 이슈
5. 큐에 들어간 이슈별로 격리된 worktree와 branch를 만든다.
6. 이슈별로 범위를 제한한 서브에이전트를 병렬 실행한다.
   - 백엔드 이슈 작업은 백엔드 범위에만 머문다.
   - 프론트엔드 이슈 작업은 감사 근거가 있으면 UI/UX 조정도 포함해야 한다.
7. 각 브랜치마다 실제 바뀐 동작을 정확히 검증하는 집중 테스트 또는 시나리오 점검을 수행한다.
8. 이슈와 연결된 한글 PR을 연다.
9. PR이 바뀔 때마다 리뷰 레인을 다시 수행한다.
   - diff가 아직 준비되지 않았으면 구체적인 리뷰 코멘트를 남긴다.
   - diff가 깨끗하면 승인한다.
10. 승인된 PR을 머지한다.
11. 머지 후에는 안전하면 완료된 worktree/branch를 삭제하고 연결된 이슈를 닫는다.
12. 준비 상태 점검을 다시 돌린다.
13. 재사용 가능한 백로그 이슈가 남아 있으면 즉시 다음 이슈 실행 웨이브를 시작한다.
14. 다시 차단 상태가 생기면 대기 루프로 복귀해서 백그라운드 폴링을 계속한다.
15. 백로그가 비어 있으면 즉시 다음 감사 패스를 연다.
16. 배포할 만한 후보가 더 이상 없으면 멈춘다.

## 리뷰 레인 계약

- 리뷰어는 실제 diff, 연결된 이슈의 acceptance criteria, 집중 검증 근거를 확인해야 한다.
- 리뷰어 출력은 다음 둘 중 하나여야 한다:
  - block: 정확한 결함/리스크와 필요한 수정 사항
  - approve: 명시적인 승인, 선택적 후속 조치는 별도로 기재
- 테스트가 통과했다는 이유만으로 도장 찍듯 승인하지 않는다.
- 새 커밋이 올라온 뒤 오래된 diff를 승인하지 않는다. 최신 head를 다시 검토한다.

## 95% 완료 휴리스틱

아래가 모두 참일 때만 루프가 끝났다고 본다.

- 최적화할 가치가 있는 백엔드 결함 또는 리팩터링 후보가 더 이상 없다.
- 최적화할 가치가 있는 프론트엔드/UI/UX 후보가 더 이상 없다.
- 재사용 가능한 열린 최적화 이슈가 없고, 열린 PR이 없고, 이전 라운드에서 남은 worktree도 없다.
- 마지막으로 채택한 변경에 대한 집중 테스트가 모두 녹색이다.
- 앞으로의 작업이 대부분 구체적 개선이 아니라 추측성 폴리싱에 가깝다.

## 권장 artifact

- `artifacts/auto-optimization-readiness.json`
- `artifacts/auto-optimization-audit-<round>.md`
- `artifacts/auto-optimization-issue-backlog.json`
- `artifacts/auto-optimization-merge-log.jsonl`

## Ultragoal 지속 규칙

이 문서를 Ultragoal 아래에서 실행할 때는:

- 충돌하는 PR/worktree 차단 요소가 남아 있다고 해서 런을 죽이거나 종료 처리하지 않는다.
- 대기 artifact를 최종 성공으로 취급하지 않는다.
- 재사용 가능한 이슈 백로그, 열린 PR, 차단 worktree 때문에 다음 이슈 실행 웨이브가 아직 완전히 끝나지 않았다면 Ultragoal을 완료 처리하지 않는다.
- 95% 완료 휴리스틱이 실제로 충족될 때까지 aggregate objective를 계속 active 상태로 두고 준비 상태 점검 → 이슈 실행 → 감사 사이클을 반복한다.
- 그때에만 최종 completion checkpoint를 만들고 inline goal을 complete로 정리한다.

## 자기 실현 규칙

이 문서를 리더가 직접 실행 기준으로 사용할 때는:

- 즉시 준비 상태 점검을 실행한다.
- 재사용 가능한 이슈 백로그가 있고 차단 요소가 없으면 어떤 새 이슈 생성보다 먼저 그 백로그를 실행한다.
- 활성 PR/worktree 충돌로 막혀 있으면 대기 근거를 영속 기록하고, 백그라운드 대기 루프에 남아서 차단 요소가 풀릴 때까지 계속 재확인한다.
- 백로그가 비어 있고 저장소가 비차단 상태라면 감사 → GitHub 이슈 등록 → 이슈 단위 서브에이전트 위임 순서로 시작한다.
