# CS 자동 최적화 오케스트레이터

이미 진행 중인 작업과 충돌하지 않으면서 저장소 전반의 최적화 루프를 돌릴 때 이 문서를 읽는다.

## 강한 게이트

- GitHub 이슈가 하나라도 열려 있거나, GitHub PR이 하나라도 열려 있거나, 활성 이슈 작업을 위해 만든 issue-train/worktree가 하나라도 남아 있으면 새 최적화 라운드를 절대 시작하지 않는다.
- 준비 상태 점검이 막혔다고 해서 작업이 끝난 것은 아니다. 그것은 백그라운드 대기 상태다.
- 게이트가 닫혀 있으면 먼저 차단 근거를 기록하고 백그라운드에서 계속 대기한다. 게이트가 열리기 전까지 다음 라운드를 위해 새 이슈, 브랜치, 워크트리, PR, 리뷰 소음을 만들지 않는다.
- 메인 에이전트 응답은 짧게 유지한다. 자세한 근거는 채팅이 아니라 artifact, 이슈 본문, PR 본문, 리뷰 코멘트에 남긴다.
- 백엔드와 프론트엔드 모두 손볼 필요가 있으면 분리된 트랙으로 진행한다. 프론트엔드 검토에는 단순 버그뿐 아니라 UI/UX 개선 후보도 포함해야 한다.
- 각 구현 트랙은 자기 전용 worktree/branch와 자기 전용 한글 PR 제목/본문을 사용해야 한다.
- 리뷰 레인은 연속적으로 돈다. PR이 바뀌면 diff를 다시 보고, 차단 코멘트를 남기거나 승인한다.
- 승인이 나고 검증을 통과한 뒤에만 머지한다. 머지 후에는 완료된 worktree를 제거하고 연결된 이슈를 닫는다.
- 의미 있는 백엔드/프론트엔드 최적화 후보가 더 이상 없고, 현재 기준으로 저장소 완성도가 최소 95% 이상이라고 볼 수 있을 때만 루프를 멈춘다.

## 준비 상태 점검

1. GitHub의 열린 이슈를 확인한다.
   ```bash
   gh issue list --state open --limit 100 --json number,title,state,labels,assignees,url
   ```
2. GitHub의 열린 PR을 확인한다.
   ```bash
   gh pr list --state open --limit 100 --json number,title,headRefName,baseRefName,reviewDecision,mergeStateStatus,isDraft,url
   ```
3. 로컬 worktree를 확인한다.
   ```bash
   git worktree list --porcelain
   ```
4. 위 셋 중 하나라도 진행 중 작업을 보여주면, 차단 요약이 담긴 짧은 상태 artifact를 작성하고 라운드 종료로 간주하지 말고 대기 루프로 들어간다.

## 대기 루프

막힌 저장소 상태는 종료 상태가 아니라 폴링 상태다.

1. 스킬이 시작되면 즉시 준비 상태 점검을 실행한다.
2. 차단 요소가 남아 있으면 최신 차단 스냅샷을 `artifacts/auto-optimization-readiness.json`에 기록한다.
3. 백그라운드에서 살아 있으면서 준비 상태 점검을 반복 실행한다.
4. 열린 차단 이슈 수가 0, 차단 PR 수가 0, issue/wave worktree 수가 0이 될 때까지 계속 반복한다.
5. 게이트가 열리는 즉시 새 수동 트리거를 기다리지 말고 자동으로 최적화 라운드를 시작한다.

## 최적화 라운드

이 단계는 준비 상태 점검 결과가 깨끗할 때만 실행한다.

1. 저장소를 점검해서 구체적인 개선 후보를 찾는다.
   - 백엔드: 정확성, 안전성, 배포/런타임 리스크, 데이터 무결성, 테스트 공백, 성능 병목, 유지보수성
   - 프론트엔드: UX 마찰, 접근성, 상태 버그, 시각적 불일치, 반응형 문제, 헷갈리는 플로우
2. 구체적이고, 검증 가능하며, 실제로 배포 가치가 있는 후보만 남긴다.
3. 채택한 후보에 대해 GitHub 이슈를 연다.
   - 한 이슈가 정말로 교차 영역이며 검증 경계도 묶여 있는 경우가 아니라면 백엔드/프론트엔드 이슈를 분리한다.
   - 이슈 제목은 한글로 쓴다.
   - 본문에는 acceptance criteria와 검증 메모를 넣는다.
4. 이슈별로 격리된 worktree와 branch를 만든다.
5. 이슈별로 범위를 제한한 구현 작업을 병렬 위임한다.
   - 백엔드 이슈 작업은 백엔드 범위에만 머문다.
   - 프론트엔드 이슈 작업은 감사 근거가 있으면 UI/UX 조정도 포함해야 한다.
6. 각 브랜치마다 실제 바뀐 동작을 정확히 검증하는 집중 테스트 또는 시나리오 점검을 수행한다.
7. 이슈와 연결된 한글 PR을 연다.
8. PR이 바뀔 때마다 리뷰 레인을 다시 수행한다.
   - diff가 아직 준비되지 않았으면 구체적인 리뷰 코멘트를 남긴다.
   - diff가 깨끗하면 승인한다.
9. 승인된 PR을 머지한다.
10. 머지 후에는 안전하면 완료된 worktree/branch를 삭제하고 연결된 이슈를 닫는다.
11. 준비 상태 점검을 다시 돌린다.
12. 다시 차단 상태가 생기면 대기 루프로 복귀해서 백그라운드 폴링을 계속한다.
13. 게이트가 계속 깨끗하면 즉시 다음 최적화 라운드를 시작한다.
14. 배포할 만한 후보가 더 이상 없으면 멈춘다.

## 리뷰 레인 계약

- 리뷰어는 실제 diff, 연결된 이슈의 acceptance criteria, 집중 검증 근거를 확인해야 한다.
- 리뷰어 출력은 다음 둘 중 하나여야 한다:
  - block: 정확한 결함/리스크와 필요한 수정 사항
  - approve: 명시적인 승인, 선택적 후속 조치는 별도로 기재
- 테스트가 통과했다는 이유만으로 도장 찍듯 승인하지 않는다.
- 새 커밋이 올라온 뒤 오래된 diff를 승인하지 않는다. 최신 head를 다시 검토한다.

## 95% 완료 휴리스틱

아래가 모두 참일 때만 루프가 끝났다고 본다.

- 최적화할 가치가 있는 백엔드 결함 또는 리팩터링 후보가 더 이상 없다.
- 최적화할 가치가 있는 프론트엔드/UI/UX 후보가 더 이상 없다.
- 이전 라운드에서 남은 열린 PR이나 잔여 worktree가 없다.
- 마지막으로 채택한 변경에 대한 집중 테스트가 모두 녹색이다.
- 앞으로의 작업이 대부분 구체적 개선이 아니라 추측성 폴리싱에 가깝다.

## 권장 artifact

- `artifacts/auto-optimization-readiness.json`
- `artifacts/auto-optimization-audit-<round>.md`
- `artifacts/auto-optimization-merge-log.jsonl`

## Ultragoal 지속 규칙

이 문서를 Ultragoal 아래에서 실행할 때는:

- 준비 상태 게이트가 막혔다고 해서 런을 죽이거나 종료 처리하지 않는다.
- 대기 artifact를 최종 성공으로 취급하지 않는다.
- 열린 이슈, 열린 PR, 잔여 차단 worktree 때문에 다음 최적화 라운드가 아직 시작되지 못한 상태라면 Ultragoal을 완료 처리하지 않는다.
- 95% 완료 휴리스틱이 실제로 충족될 때까지 aggregate objective를 계속 active 상태로 두고 대기 루프 → 최적화 라운드 사이클을 반복한다.
- 그때에만 최종 completion checkpoint를 만들고 inline goal을 complete로 정리한다.

## 자기 실현 규칙

이 문서를 리더가 직접 실행 기준으로 사용할 때는:

- 즉시 준비 상태 점검을 실행한다.
- 막혀 있으면 대기 근거를 영속 기록하고, 백그라운드 대기 루프에 남아서 게이트가 열릴 때까지 계속 재확인한다.
- 막혀 있지 않으면 어떤 구현 위임보다 먼저 이슈 생성부터 시작한다.
