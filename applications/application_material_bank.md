# 기업 자기소개서 통합 소재은행

> 기존 자기소개서·직무기술서·지원서 입력자료를 통합한 재사용 자료입니다. 기업별 문항에는 필요한 소재만 골라 쓰고, 회사명·학교명 등 블라인드 금지정보는 해당 공고 기준에 맞춰 제외합니다.
> 수치와 기간은 제출 전에 경력증명서, 이력서, 수료증, 저장소 기록 등으로 다시 확인합니다. 문서 간 표현이 충돌하는 항목은 아래 `제출 전 확인사항`에 따로 표시했습니다.

## 1. 핵심 프로필

- **직무 정체성:** 커머스 플랫폼의 상품 전시 도메인을 개발·운영한 백엔드 개발자
- **주요 기술:** Java, Spring Boot, JPA, QueryDSL, MySQL, Redis, Spring Batch, SQS·메시지 큐, JDBC, 비동기 처리, Jenkins, GitHub Actions
- **대표 강점:** 데이터 기반 문제해결, 대규모 시스템 분리·이관, 운영 안정성, 장애 추적성, 반복업무 자동화, 다부서 협업, 기술지식 공유
- **경험 규모:** 이용자 100만 명 이상 커머스 플랫폼, TPS 1,000, API 92개, 모듈 10개, 테이블 약 400개, 클래스 약 1,000개, 상품 데이터 100만 건
- **융합 배경:** 국문학·디자인·컴퓨터공학 3중전공을 통해 언어, 사용자 경험, 기술 구조를 함께 보는 관점 보유
- **교육:** 프로그래밍언어, 자료구조, 컴퓨터구조, 데이터베이스 학교교육 및 우아한테크코스 4기 Backend 이수
- **일하는 기준:** 추측보다 지표, 임시 대응보다 원인 해결, 배포보다 운영 안정화, 개인 기억보다 기록과 검증

## 2. 경력·사내 프로젝트 소재

### 2-1. 상품 전시 도메인 개발·운영

- **구분:** 재직 중 사내 업무
- **기간:** 2023.01~2024.11, 총 1년 11개월
- **환경:** 이용자 100만 명 이상 커머스 플랫폼의 서비스개발 조직
- **역할:** 백엔드 개발·운영
- **업무:** 상품 카탈로그, 기획전, 구좌, 할인, 필터, 탭 등 전시 도메인의 API와 운영 시스템 담당
- **행동:** 로그와 성능지표로 병목을 좁히고 DB 조회 순서, 캐시, 쿼리 탐지, 전역 로깅을 개선
- **활용 역량:** 서비스 운영, 문제 구조화, 장애 대응, 고객 영향 인식, 책임감
- **적합 문항:** 직무역량, 경력기술, 지원동기, 책임감, 입사 후 기여

### 2-2. 배너 API 성능 최적화

- **구분:** 재직 중 사내 성능개선 프로젝트
- **기간:** 2023.07~2023.08
- **상황:** 대규모 이벤트에 대응해야 하는 TPS 1,000 환경
- **과제:** 배너 API의 느린 응답속도와 이벤트 트래픽 대응
- **행동:** BatchSize 재설정, DB 조회 순서 조정, 캐싱 방식 개선
- **성과:** API 응답시간 909ms에서 18ms로 단축, 약 98% 개선
- **활용 역량:** 성능 최적화, 데이터 기반 문제해결, 고트래픽 대응, 고객경험 개선
- **적합 문항:** 가장 큰 성과, 기술적 문제해결, 도전, 전문성

### 2-3. 슬로우 쿼리 탐지 개선

- **구분:** 재직 중 사내 운영개선
- **상황:** 장애나 성능 저하의 원인을 찾는 데 시간이 오래 걸림
- **행동:** SQL 진입점 로깅과 탐지 체계를 개선하고 관련 지식을 사내에 공유
- **성과:** 평균 원인 파악시간 25분에서 9분으로 단축
- **활용 역량:** 관측가능성, 장애 대응, 운영 효율, 지식 공유
- **적합 문항:** 업무개선, 책임감, 운영역량, 조직 기여

### 2-4. 신규 가게홈 서버 분리·대규모 이관

- **구분:** 재직 중 사내 신규 서버 구축·전시 통합 프로젝트
- **기간:** 2023.12~2024.11, 약 1년
- **과제:** 레거시 구조에서 전시 도메인을 분리하면서 서비스와 데이터의 연속성 유지
- **범위:** API 92개, 모듈 10개, 테이블 약 400개, EC2 인스턴스, DB와 Redis
- **행동:** 의존관계 정리, Spring 다중 데이터소스 구성, API 마이그레이션, DB·Redis 이관, 단계별 배포 전 검증
- **성과:** 상품·기획전 기능을 운영 중단 없이 전환하고 변경 안정성과 추적성 향상
- **활용 역량:** 대규모 시스템 전환, 데이터 무결성, 변경관리, 업무 연속성, 책임과 신뢰
- **적합 문항:** 가장 어려운 프로젝트, 책임감, 협업, 리스크 관리, 금융 IT 연계

### 2-5. Deprecated 클래스 자동 탐지·일괄 수정

- **구분:** 가게홈 서버 분리 프로젝트 안의 사내 자동화 과제
- **상황:** 약 1,000개 클래스의 낡은 참조를 사람이 직접 찾고 고치면 누락과 일정 지연 위험이 큼
- **행동:** 사용 중단 대상 클래스 자동 탐지 도구를 개발하고 결과를 목록화한 뒤 Google Apps Script로 수정 대상을 일괄 반영
- **검증:** 변경 전후 참조와 빌드 결과 확인
- **성과:** 대량 변경의 속도와 일관성을 높이고 담당자가 예외 검토에 집중하도록 함
- **활용 역량:** 자동화, 변화·혁신, 휴먼에러 예방, 검증 설계
- **적합 문항:** 새로운 시도, 업무혁신, 디지털 전환, 반복업무 개선

### 2-6. MDC 기반 전역 로깅과 배포 전 검증

- **구분:** 재직 중 사내 운영 안정화
- **과제:** Batch, SQS·메시지 큐, JDBC, 비동기 처리처럼 분산된 흐름의 원인과 영향을 추적하기 어려움
- **행동:** MDC 기반 전역 로깅을 적용하고 배포 전 점검 기준과 기록 체계를 구축
- **성과:** 장애 원인, 변경 영향, 처리 흐름의 추적성 향상
- **추가 개선:** 여러 곳에 흩어진 스레드풀 설정을 Spring TaskExecutor로 통합
- **활용 역량:** 관측가능성, 내부통제, 감사 추적성, 장애 대응, 운영 표준화
- **적합 문항:** 책임감, 신뢰, 정보보호·내부통제, 운영체계 개선

### 2-7. 최소주문금액 안내 기능

- **구분:** 재직 중 사내 고객경험 개선 프로젝트
- **상황:** 고객이 주문 가능 여부와 부족 금액을 알기 어려워 상품 화면과 장바구니를 반복 이동
- **협업 범위:** 7개 이상의 유관부서 또는 7개 팀
- **갈등:** 기획은 일정과 고객경험, 개발은 안정성, 일부 부서는 단기 매출효과를 중시해 우선순위 합의가 어려움
- **행동:** 사용자 행동지표와 부서별 요구를 공통 자료로 정리하고, 주문 가능 여부와 부족 금액을 보여주는 핵심 기능부터 작게 출시하도록 제안
- **역할:** 요구사항 구조화, 이해관계자 조율, 백엔드 개발 주도, 상태·예외조건 점검
- **성과:** 장바구니 이탈 감소와 주문전환율 향상에 기여, 전사 UX 성공사례로 공유
- **활용 역량:** 사용자 중심, 다부서 협업, 갈등 조정, 데이터 기반 의사결정, 실행력
- **적합 문항:** 협업, 갈등 해결, 고객중심, 혁신, 주도성

### 2-8. 커머스 통합 지원 Slack 앱

- **구분:** 커머스 조직 관련 사내 프로젝트로 추정되나 정확한 경력 귀속과 기간 확인 필요
- **범위:** 20여 개 팀, 100여 개 워크플로우
- **문제:** 팀별 JIRA 티켓, DML·DDL 요청, 릴리스 백포팅, 지원 절차가 달라 반복 요청과 처리 기준 불일치 발생
- **행동:** 공통 요청과 팀별 예외를 구분하고 Slack 워크플로우·앱, JIRA 자동 생성, Google 스프레드시트 연동, GitLab 브랜치 머지, 릴리스 백포팅을 통합
- **추가 행동:** Jenkins로 JIRA와 Git 커밋의 티켓 연동을 점검하는 배포 전 검증 구축, 자동 멘션과 온콜 상태 표시 제안
- **성과:** 20여 개 팀과 100여 개 워크플로우의 통합 지원·반복요청 자동화 기반 마련
- **활용 역량:** 프로세스 표준화, 예외 설계, 현업 소통, 자동화, 내부 고객 지원
- **적합 문항:** 갈등 해결, 업무혁신, 조직 기여, 이해관계자 협업

### 2-9. 상품 예약·시간대별 노출 자동화

- **구분:** 가게홈 서버 구축 과정의 사내 기능개발
- **업무:** 기획전 상품 예약 기능 설계, 시간대별 상품 순서와 일정 자동화
- **활용 역량:** 반복운영 자동화, 일정 기반 업무 설계, 운영 효율
- **적합 문항:** 업무개선, 자동화, 운영 효율화

## 3. 교육·훈련 소재

### 3-1. 국문학·디자인·컴퓨터공학 3중전공

- **구분:** 학교교육
- **핵심 의미:** 같은 문제를 언어, 사용자 경험, 기술 구조의 세 관점에서 해석
- **국문학 연결:** 복잡한 내용을 정확한 문장과 논리로 구조화하고 상대의 배경에 맞게 설명
- **디자인 연결:** 사용자 흐름, 정보 위계, 화면에서 발생하는 불편을 관찰하고 시각화
- **컴퓨터공학 연결:** 요구사항을 데이터·시스템 구조와 구현 가능한 기술로 구체화
- **활용 역량:** 융합적 사고, 요구사항 분석, 사용자 중심 설계, 설명력, 현업과 개발의 언어 연결
- **적합 문항:** 차별화된 강점, 성장과정, 직무준비, 소통, 지원동기
- **주의:** 학교명은 블라인드 공고에서 제외하고, 3중전공 여부와 기간은 증빙자료와 일치시킬 것

### 3-2. 학교교육 과목

| 과목 | 핵심 학습내용 | 연결 역량 |

| 프로그래밍언어 | 기본 문법, 제어구조, 함수, 자료형, 객체지향 | 구현력, 논리적 문제해결 |

- **기간:** 2022.02~2022.11
- **분류:** NCS 20010202 응용SW엔지니어링
- **학습:** Java·Spring 기반 서버 개발, 객체지향 설계, 웹 애플리케이션 구현, 테스트, 리팩토링, HTTP 발표, 팀 프로젝트
- **기록:** 교육 학습내용 블로그 시리즈 24편과 미션 아카이브 구축
- **활용 역량:** 백엔드 기초, 자기주도 학습, 코드리뷰, 피드백, 협업
- **적합 문항:** 직무준비, 교육사항, 성장과정, 개발자로 전환한 계기
- **주의:** 교육시간·회차·수료일은 수료증이나 고용24 훈련이력으로 확인

## 4. 팀·개인 프로젝트 소재

### 4-1. 속닥속닥 익명 커뮤니티

- **구분:** 우아한테크코스 4기 팀 프로젝트
- **기간:** 2022.06~2022.11
- **역할:** 백엔드 개발자 5명 중 1명
- **기술:** Java 11, Spring Boot, JPA, Hibernate, QueryDSL, MySQL, Jenkins, Spring AOP, ThreadLocal
- **규모:** 실사용자 120명, 동시접속자 80명
- **성과:** BatchSize와 Fetch Join 개선으로 쿼리 수 5,000개에서 6개로 감소
- **활용 역량:** 팀 개발, ORM 성능 개선, 실사용자 서비스 운영, 코드리뷰
- **적합 문항:** 교육성과, 첫 팀 프로젝트, 협업, 기술적 문제해결

### 4-2. 차록(Chalog)

- **구분:** 개인 프로젝트
- **역할:** 백엔드 개발 및 시스템 설계
- **상태:** 계획한 전체 범위는 아직 진행 중인 것으로 기존 지원서에 기재
- **기능:** 100만 건 데이터에 할인·주문·재고 등 9개 조건을 적용하는 필터, 알림센터 연동 Spring Batch 푸시알림
- **문제:** 과도한 데이터 조회와 애플리케이션 후처리로 DB 부하, 메모리 급증, OOM 발생
- **행동:** DB 사용량과 메모리 변화 측정, 조건을 쿼리로 이동, 조회 범위·컬럼 축소, 페이징 적용, 변경 전후 동일 조건 검증
- **성과:** OOM과 DB 부하 해결, 상품 최대 노출 수 300개에서 1,000개로 확대
- **배움:** 큰 목표보다 핵심 기능과 완료 기준을 먼저 정하고 실행 가능한 단위로 범위를 관리
- **활용 역량:** 근본원인 분석, 대용량 데이터 처리, 실패·미완료 경험, 목표관리, 자기주도성
- **적합 문항:** 어려움 극복, 실패 경험, 책임감, 성능개선, 개인 프로젝트
- **주의:** 시작일과 실제 완료 상태를 확인하고, 사내 프로젝트로 오해되지 않게 `개인 프로젝트`라고 명시

## 8. 강점·약점·성장서사

### 강점

1. **문제 구조화:** 복잡한 장애와 요구를 데이터, 흐름, 우선순위로 분해
2. **설명력:** 국문학·디자인·컴퓨터공학 관점을 이용해 기술과 현업의 언어를 연결

4. **실행력:** 합의된 핵심 기능을 직접 구현하고 배포·검증까지 마침
5. **지식 공유:** 개인의 시행착오를 글, 발표, PR, 문서로 조직 자산화

### 약점과 보완

- **정책금융·여신심사·산업분석의 실무 이해 부족:** 기관 조사자료, 재무상태·현금흐름·산업전망을 함께 보는 연습, 입사 후 영업점·본부 업무 학습으로 보완
- **정확히 설명하려다 초기 공유가 늦어지는 경향:** 핵심 쟁점과 잠정 판단을 먼저 공유하고 상세 분석을 단계적으로 보완
- **큰 개인 프로젝트의 완료기준을 넓게 잡은 경험:** 핵심 기능, 품질기준, 완료조건을 먼저 정하고 기능별로 범위를 분할

### 성장서사

1. 국문학·디자인을 통해 언어와 사용자 관점을 익힘
2. 컴퓨터공학과 우테코를 통해 문제를 구현 가능한 시스템으로 바꾸는 역량을 확보
3. 커머스 플랫폼 실무에서 성능, 데이터, 운영 안정성 문제를 해결
4. 지식공유와 다부서 협업을 통해 개인 기술을 조직 성과로 확장
5. 앞으로 금융·공공 업무지식을 결합해 안정적이고 설명 가능한 디지털 서비스를 구축

## 11. 금융·공공 분야에 재사용할 관점

- **정확성:** 데이터 오류는 고객의 자격판단, 지급, 보증, 대출, 사후관리에 직접 영향을 줌
- **연속성:** 장애가 발생해도 핵심 업무가 멈추지 않도록 이관, 복구, 재처리, 모니터링을 설계
- **추적성:** 누가 무엇을 바꿨고 어떤 영향이 있었는지 로그와 기록으로 설명 가능해야 함
- **최소권한과 개인정보:** 대외기관 연계와 개인정보 처리에서는 권한, 전문 형식, 오류처리 기준을 명확히 함
- **설명 가능성:** AI·자동화의 결과를 그대로 믿지 않고 사람의 검토와 승인 절차를 남김
- **현업 이해:** 기술적 해결책보다 업무 목적, 규정, 데이터 정의와 책임 주체를 먼저 확인
- **선제 대응:** 장애나 부실이 현실화된 뒤 수습하기보다 지표와 스트레스 점검으로 이상징후를 조기에 탐지

## 12. 논술·상황판단 소재

### 조건부·단계적 지원 판단

- 기업 지원 여부는 기술경쟁력, 거래처, 공급망 파급효과, 현금흐름, 차입구조, 담보, 연체, 수주잔고, 매출채권, 재고, 미지급금으로 판단
- 지원 시 별도 관리계좌, 용도 제한, 분할 집행, 월별 경영현황, 자구계획, 추가 차입 사전협의 등 통제조건 설정
- 약정 위반이나 실적 악화 시 추가 집행 중단, 채권보전·정상화 절차 검토
- 지원의 편익뿐 아니라 회수손실, 자금 전용, 도덕적 해이, 공급망 의존 같은 부작용을 함께 제시

### 혁신 실행 원칙

- 기존 절차의 대기시간, 오류율, 재처리 건수를 기준선으로 남김
- 현업과 사용자의 불편을 확인하고 작은 범위로 설계
- 테스트 계정과 단계적 적용으로 위험 통제
- 개선 전후 처리시간, 정확도, 장애 건수를 비교
- 자동화하기 어려운 판단은 사람의 검토와 승인 유지

### 내·외부 협력 원칙

- 이해관계자별 목표, 제약, 의사결정권자 확인
- 데이터 정의, 제출 시점, 책임 주체, 오류 처리 기준 합의
- 의견 충돌 시 처리시간, 오류율, 고객 불편 같은 공동 지표로 우선순위 결정
- 외부 API·자료연계에서는 권한, 개인정보, 전문 형식, 재처리 절차를 사전 점검

## 13. 바로 재사용할 수 있는 핵심 문장

- 이용자 100만 명 이상인 커머스 플랫폼에서 상품 전시 시스템의 백엔드 개발과 운영을 담당했습니다.
- TPS 1,000 환경에서 DB 조회 순서와 캐시 구조를 개선해 API 응답시간을 909ms에서 18ms로 줄였습니다.
- 신규 가게홈 서버 구축 과정에서 92개 API, 10개 모듈, 약 400개 테이블의 의존관계를 정리하고 DB·Redis를 운영 중단 없이 이관했습니다.
- Batch·메시지 큐·JDBC·비동기 처리에 MDC 기반 전역 로깅을 적용해 장애 원인과 변경 영향을 추적할 수 있도록 했습니다.
- 약 1,000개 클래스의 낡은 참조를 자동 탐지하고 일괄 수정하는 도구를 만들어 누락 위험과 반복작업을 줄였습니다.
- 7개 이상의 유관부서가 참여한 고객경험 개선에서 요구사항을 공통 자료로 정리하고 핵심 기능부터 작게 출시해 합의를 이끌었습니다.
- 국문학·디자인·컴퓨터공학을 함께 전공하며 문제를 언어, 사용자 경험, 기술 구조의 관점에서 해석하는 역량을 길렀습니다.
- 개인 프로젝트의 OOM 문제를 서버 증설로 덮지 않고 지표와 쿼리 흐름을 분석해 구조적으로 해결했습니다.
- 기술 블로그 70편 이상과 사내 발표를 통해 개인의 시행착오를 동료가 재사용할 수 있는 지식으로 바꾸었습니다.
- 네 명이 참여한 CS 스터디를 네 달간 운영하며 43개의 PR과 12개의 주제글로 학습과 피드백을 지속했습니다.

## 14. 제출 전 확인사항

### 문서 간 충돌

1. **기술 세미나 사회 횟수:** 자료에 4회와 5회가 모두 존재합니다. 일정, 발표자료 또는 이력서로 확인한 뒤 전 문서를 하나로 통일합니다.
2. **100만 건 필터·OOM 경험의 소속:** 일부 직무기술서는 커머스 실무 문단에 포함하지만, 지원서 입력자료와 최신 산업은행 자기소개서는 개인 프로젝트 `차록`으로 구분합니다. 실제 이력서 기준으로 최종 확정합니다.
3. **전공 표현:** 기존 입력자료에는 `컴퓨터과학과 제2 복수전공`, 최신 사용자 확인에는 `국문학·디자인·컴퓨터공학 3중전공`이 있습니다. 학적증명서의 공식 전공명과 이수 상태로 통일합니다.
4. **최소주문금액 협업 범위:** 문서에 `7개 이상의 유관부서`와 `7개 팀`이 함께 쓰입니다. 실제 조직 단위에 맞춥니다.

### 추가 증빙 필요

- 차록의 시작일, 현재 완료 상태, 100만 건·9개 조건·최대 노출 수 수치
- Slack 앱의 정확한 활동기간과 경력 내 프로젝트 여부
- 카페포레스트의 기간, 팀 구성, 본인 역할, 600만 원 펀딩 자료
- 차 SNS의 플랫폼, 기간, 본인 역할, 누적 조회수 200만 회 산정 자료
- 최소주문금액 안내 기능의 이탈률·전환율 변화 수치와 전사 UX 사례 자료
- 기술 블로그 글 수, 밋업 사회 횟수, 참석자 규모
- 속닥속닥의 실사용자·동시접속자와 쿼리 감소 측정자료
- 학교 과목명, 학점, 이수상태 및 3중전공 공식 명칭
- 우아한테크코스 교육시간, 회차, 수료일

### 블라인드 점검

- 공고에서 금지하면 회사명, 학교명, 지역명, 성명, 나이, 성별, 가족관계, 종교, 신체조건, 총학점을 삭제
- 회사명 대신 `이용자 100만 명 이상 커머스 플랫폼`, 학교명 대신 `학교교육`, 조직명 대신 `사내 서비스개발 조직` 사용

- 기간과 수치는 증빙 가능한 범위에서만 기재
