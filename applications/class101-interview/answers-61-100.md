### 61

**핵심 키워드:** 대상 선정 · 청크 처리 · 발송 상태 · 멱등성

우아한형제들에서 100만 건 대상 할인 알림 배치를 구현했습니다. 이 규모에서는 Reader로 대상을 나눠 읽고, Processor로 조건을 검사한 뒤, Writer로 발송 요청을 저장하겠습니다. 외부 발송은 DB 트랜잭션 밖에서 처리하고 캠페인·대상별 발송 키를 사용하겠습니다. 처리 결과를 남겨 실패한 항목만 재시도하는 것이 핵심입니다.

### 62

**핵심 키워드:** 대상 고정 · 키셋 페이징 · 메모리 제한 · 누락 검증

전체 데이터를 한 번에 읽지 않고 실행 대상을 고정한 뒤 ID 순서로 나누어 조회하겠습니다. 마지막 ID 다음부터 필요한 컬럼만 읽으면 큰 OFFSET 비용과 메모리 사용을 줄일 수 있습니다. 청크마다 객체와 영속성 컨텍스트가 누적되지 않게 관리하겠습니다. 마지막에는 대상 수와 성공·실패·제외 건수를 대조해 누락을 검증하겠습니다.

### 63

**핵심 키워드:** 청크 크기 · 처리량 · 잠금 시간 · 커밋 비용

청크 크기는 처리량과 실패 비용을 함께 보고 정하겠습니다. 500건부터 시작해 메모리, 커밋 시간, 잠금 대기를 측정하고 크기를 조정하겠습니다. 발송 요청과 체크포인트는 같은 DB 트랜잭션 자원으로 묶되 외부 호출은 분리하겠습니다. 외부 발송은 롤백되지 않으므로 멱등성은 별도로 보장해야 합니다.

### 64

**핵심 키워드:** 체크포인트 · 고유 발송 키 · 결과 불명확 · 재시작

같은 실행 파라미터로 마지막 커밋된 체크포인트부터 재시작하겠습니다. 캠페인·대상 조합에 고유 제약을 두어 발송 요청이 다시 생성되지 않게 하겠습니다. 다만 외부 발송 후 결과 저장이 실패하면 중복 가능성이 있으므로 제공자의 멱등 키나 결과 조회로 복구하겠습니다. 결과를 확인할 수 없는 발송은 무조건 재전송하지 않고 별도 상태로 관리하겠습니다.

### 65

**핵심 키워드:** JobRepository · 고유 제약 · 조건부 갱신 · 처리권

작업 실행 중복과 개별 항목 중복을 따로 막겠습니다. JobRepository를 공유하고 캠페인과 기준 일자로 동일 작업의 중복 실행을 제어하겠습니다. 항목에는 고유 제약을 두고, 대기 상태를 처리 중으로 바꾸는 조건부 UPDATE에 성공한 작업자만 처리하겠습니다. 처리권이 만료돼 재할당되면 이전 작업자의 늦은 갱신도 버전 검사로 차단하겠습니다.

### 66

**핵심 키워드:** 오류 분류 · 지수 백오프 · 지터 · 재시도 한도

일시 장애와 영구 오류를 먼저 구분하겠습니다. 요청 제한에는 Retry-After를 우선 적용하고, 그 외 일시 오류는 지수 백오프와 지터로 재시도하겠습니다. 횟수와 총 대기 시간을 제한하고 잘못된 수신 정보는 바로 격리하겠습니다. 결과가 불명확한 전송은 같은 식별자로 조회하거나 멱등하게 재시도해야 합니다.

### 67

**핵심 키워드:** 영향 범위 · 항목 격리 · 부분 완료 · 지급 승인

개별 입력 오류라면 해당 항목을 보류하고 독립적인 정상 항목은 처리하겠습니다. 계산 규칙이나 환율처럼 전체 결과에 영향을 주는 오류라면 배치를 중단하겠습니다. 보류 항목을 성공으로 세지 않고 미처리 금액을 별도로 표시하겠습니다. 출금은 재무 담당자와 합의한 검증 기준을 통과한 범위에만 허용하겠습니다.

### 68

**핵심 키워드:** 아웃박스 · 원자적 저장 · 중복 소비 방지 · 전달 지연

업무 데이터와 이벤트를 같은 DB 트랜잭션에 저장하는 아웃박스를 사용하겠습니다. 별도 전달기가 미발행 이벤트를 전송하면 DB 반영 후 이벤트가 사라지는 공백을 줄일 수 있습니다. 전송 직후 장애가 나면 중복 발행될 수 있으므로 소비자는 이벤트 ID로 중복 효과를 막아야 합니다. 전달 지연과 재시도 상태도 운영 지표로 관리하겠습니다.

### 69

**핵심 키워드:** 공통 절차 · 팀별 예외 · 요청 자동화 · 승인 책임

Slack 통합 솔루션에서는 팀별 지원 요청을 공통 절차와 예외로 나누었습니다. JIRA 티켓 생성, 정보 전달, 스프레드시트 연동과 릴리스 백포팅처럼 반복되는 흐름을 연결했습니다. 팀별 필수 입력과 승인자는 설정으로 분리하는 것이 적합합니다. 입력 중복은 줄이되 업무별 검토와 승인 책임은 유지하는 것이 공통화의 기준입니다.

### 70

**핵심 키워드:** 기준 시점 · 정책 버전 · 금액 대사 · 완료 조건

정산 배치는 건수뿐 아니라 금액의 일치까지 완료 조건으로 보겠습니다. 대상 기간과 계약·수수료 정책 버전을 고정하고 원천 거래와 정산 항목을 연결하겠습니다. 통화별 합계와 누락·중복, 보류 금액을 대조하겠습니다. 프로세스가 정상 종료돼도 대사와 승인을 통과하기 전에는 지급 가능한 상태로 바꾸지 않겠습니다.

### 71

**핵심 키워드:** 방별 직렬화 · 경쟁 상태 · 검증과 변경 · 공유 자원

고산운에서 방별 작업 직렬화를 구현했습니다. 여러 요청이 같은 자원 상태를 읽고 각각 차감하면 자원이 중복 사용될 수 있기 때문입니다. 방 단위로 검증과 변경 순서를 묶으면 뒤의 작업은 앞선 결과를 기준으로 판단할 수 있습니다. 타이머와 저장처럼 다른 경로의 상태 변경도 같은 처리 경계를 따라야 합니다.

### 72

**핵심 키워드:** 단일 쓰기 주체 · 소유권 이전 · fencing token · 요청 ID

프로세스 내부 큐만으로는 다른 서버의 작업까지 막을 수 없습니다. 방마다 쓰기 주체를 하나로 정하고 요청을 해당 서버로 전달하겠습니다. 장애로 소유권이 바뀌면 fencing token을 저장 시 검증해 이전 서버의 쓰기를 차단하겠습니다. 같은 서버에도 재시도가 중복 도착할 수 있으므로 요청 ID 기반 중복 처리 방지가 필요합니다.

### 73

**핵심 키워드:** 상태 버전 · 일관된 복사본 · 캐시 무효화 · 역전 방지

고산운에서는 스냅샷 캐싱과 저장·복원을 구현했습니다. 상태와 캐시의 버전이 같을 때만 재사용하고, 다르면 일관된 복사본으로 다시 생성하는 방식이 적합합니다. 생성 도중 새 상태가 반영되면 이전 결과가 최신 캐시를 덮지 않게 버전을 검사하겠습니다. 클라이언트도 오래된 버전의 응답을 무시해야 상태가 되돌아가지 않습니다.

### 74

**핵심 키워드:** 원자적 저장 · 작업 로그 · 영속화 · 복구 범위

완료 응답한 작업을 어디까지 복구할지 먼저 정하겠습니다. 스냅샷은 원자적으로 교체하고, 이후 작업까지 보존하려면 작업 로그를 영속화한 뒤 응답하겠습니다. 복구 시에는 마지막 반영 위치 이후만 재생하고 중복 ID는 건너뛰겠습니다. 주기적 스냅샷만 저장한다면 그 이후의 메모리 작업은 잃을 수 있으므로 무손실 복구와 구분해야 합니다.

### 75

**핵심 키워드:** 세션 검증 · 전체 상태 동기화 · 서버 권위 · 재연결

선립:티버스에서 WebSocket 연결 복원과 방별 상태 관리를 구현했습니다. 재연결 복구는 세션을 검증한 뒤 참가자·좌석·진행 단계와 버전을 서버에서 다시 받는 방식으로 구성하겠습니다. 이전 클라이언트의 좌석 점유를 그대로 인정하지 않고 현재 서버 상태로 판단하겠습니다. 상태 규모가 커지면 증분 복구를 추가하되 전체 상태 수신을 복구 경로로 유지하겠습니다.

### 76

**핵심 키워드:** 자원 경합 · 원자적 점유 · 예약 만료 · 보상 처리

좌석과 재고 모두 같은 자원을 여러 요청이 동시에 점유하는 문제입니다. 검증과 갱신을 한 경계로 묶거나 조건부 UPDATE로 한 요청만 성공하게 해야 합니다. 다만 좌석은 연결 만료로 해제할 수 있어도 재고는 결제 결과가 불명확하면 바로 풀어서는 안 됩니다. 재고 예약은 늦은 승인과 환불까지 고려해 주문·결제 상태와 함께 관리해야 합니다.

### 77

**핵심 키워드:** 방별 상태 · Durable Objects · 비동기 인터리빙 · 저장 보장

Durable Objects는 방 ID별로 공유 상태와 요청 처리를 모으기 좋아 티버스 구조에 적합합니다. 다만 단일 스레드여도 외부 fetch를 기다리는 동안 다른 요청이 실행될 수 있습니다. 저장소 입력 게이트의 보호 범위와 별도 동기화가 필요한 구간을 구분해야 합니다. 객체별 부하와 재시작 시 복구, 비용과 플랫폼 의존성도 함께 고려하겠습니다.

### 78

**핵심 키워드:** 입력 검증 · 참가자 인증 · 빈도 제한 · 지연 허용

티버스에서 메시지 빈도와 좌표 검증을 구현했습니다. 서버 수신 단계에서 메시지 형식과 참가자·방 소속을 검사한 뒤 유한한 좌표인지, 공간 경계를 벗어나지 않는지 검증해야 합니다. 빈도 제한에는 정상적인 짧은 몰림과 네트워크 지연 여유를 두겠습니다. 이동 메시지는 합칠 수 있지만 좌석 변경 같은 명령은 거절 결과를 명확히 전달하겠습니다.

### 79

**핵심 키워드:** 하위 호환성 · 클라이언트 버전 · 점진적 변경 · 롤백

동일 릴리스 배포만으로 오래 열린 브라우저까지 교체되지는 않습니다. 필드 추가처럼 호환 가능한 변경부터 적용하고, 삭제나 의미 변경에는 호환 기간을 두겠습니다. 지원 범위를 벗어난 클라이언트에는 버전을 확인해 갱신을 안내하겠습니다. 구버전과 신버전이 동시에 요청하는 상황과 롤백까지 테스트해야 합니다.

### 80

**핵심 키워드:** 변경 순서 · 서버 검증 · 영속성 · 거래 대사

공유 상태의 변경 순서와 서버 기준 검증, 장애 후 복구 원칙은 결제에도 적용할 수 있습니다. 다만 금액은 메모리의 일관성만으로 부족하며 DB 원자성, 멱등성, 변경 이력과 대사가 필요합니다. 화면 차이는 다음 동기화로 복구할 수 있어도 중복 청구는 그렇게 해결되지 않습니다. 완료 응답 전에 무엇을 영속화할지 더 엄격하게 정하겠습니다.

### 81

**핵심 키워드:** MDC · 진입점 · traceId · 장애 추적

우아한형제들에서 MDC 기반 SQL 진입점 로깅으로 원인 파악 시간을 25분에서 9분으로 줄였습니다. SQL만으로는 알기 어려운 호출 업무와 처리 흐름을 연결한 것이 핵심입니다. 요청에는 traceId와 entryPoint, 배치에는 jobExecutionId를 연결하는 구성이 적합합니다. 느린 쿼리와 진입점을 함께 검색하되 민감한 파라미터는 제외해야 합니다.

### 82

**핵심 키워드:** 컨텍스트 전달 · TaskDecorator · finally 정리 · 스레드 재사용

MDC는 스레드에 묶이므로 비동기 작업 제출 시 필요한 값을 복사하겠습니다. TaskDecorator에서 실행 스레드에 설정하고 finally에서 이전 값을 복원하거나 제거하겠습니다. 정리하지 않으면 재사용된 스레드의 다음 요청에 이전 정보가 섞일 수 있습니다. 메시지 큐를 넘을 때는 추적 ID를 메타데이터로 전달하고 소비 지점에서 다시 구성하겠습니다.

### 83

**핵심 키워드:** 진단 시간 · 측정 구간 · 비교 조건 · 복구 시간 분리

SQL 진입점 로깅 개선으로 원인 파악 시간이 25분에서 9분으로 줄었습니다. 진단 시간은 담당자가 분석을 시작한 시점부터 문제 SQL과 호출 경로를 찾아 원인을 검증한 시점까지로 정의하겠습니다. 복구 완료 시간과 분리하고 유사한 장애 유형끼리 비교하는 것이 중요합니다. 평균뿐 아니라 중앙값과 사례별 분포를 함께 봐야 효과를 과장하지 않을 수 있습니다.

### 84

**핵심 키워드:** 테스트 격리 · 컨텍스트 캐시 · DB 정리 · 실행 순서

속닥속닥에서 테스트 격리와 실행 시간을 개선해 425개 테스트를 3분에서 45초로 단축했습니다. 같은 문제에서는 컨텍스트 재생성과 DB 초기화 시간을 먼저 나눠 측정하겠습니다. 설정을 통일해 컨텍스트를 재사용하되 데이터와 정적 상태는 테스트마다 격리해야 합니다. 단독·전체·순서 변경 실행에서 결과가 같아야 속도와 신뢰성을 함께 확보할 수 있습니다.

### 85

**핵심 키워드:** 동시 요청 · 멱등 키 · 재고 불변 조건 · 실제 DB

같은 멱등 키의 동시 요청과 응답 전 재시도에서 승인 효과가 한 번만 발생하는지 검증하겠습니다. 같은 키에 다른 금액을 넣는 요청은 거절돼야 합니다. 재고는 1개에 여러 주문을 동시에 보내 예약 합계가 재고를 넘지 않는지 보겠습니다. 예약 만료와 결제 성공의 경합까지 실제 DB에서 테스트해야 잠금과 제약조건을 검증할 수 있습니다.

### 86

**핵심 키워드:** PG 대역 · 응답 유실 · 중복 웹훅 · 복구 검증

PG 대역에서 승인 후 응답만 지연되는 경우와 승인 자체가 실패하는 경우를 나눠 재현하겠습니다. 웹훅은 중복·역순으로 보내고 처리 중 프로세스를 종료해 복구를 검증하겠습니다. DB도 커밋 전 실패와 커밋 결과를 알 수 없는 연결 종료를 구분하겠습니다. 오류 응답보다 중복 청구·초과 환불·누락 없이 거래 상태가 확정되는지가 핵심입니다.

### 87

**핵심 키워드:** 지연 분포 · 승인율 · 처리 적체 · 대사 불일치

기술 지표는 p95·p99 지연, 오류율, DB 잠금 대기와 PG 타임아웃을 보겠습니다. 업무 지표는 승인율, 오래 머무는 처리 중 거래, 환불 지연과 정산 미완료 금액입니다. 카드 거절과 시스템 오류를 구분하고 결제 수단·통화·단계별로 나눠 보겠습니다. 대사 불일치와 큐 적체도 함께 봐야 API가 정상이어도 생기는 업무 누락을 찾을 수 있습니다.

### 88

**핵심 키워드:** 독립 대사 · 거래 식별자 · 누락 탐지 · 멱등 재처리

정산 대상 원천 거래와 실제 정산 항목을 독립적으로 대조하겠습니다. 건수와 합계가 같아도 누락과 중복이 상쇄될 수 있으므로 거래 식별자 단위로 확인해야 합니다. 마감 시각을 넘긴 미처리 항목과 데이터 유입 중단도 감시하겠습니다. 누락은 원인을 기록하고 멱등한 경로로 재처리해야 복구 중 중복 정산을 막을 수 있습니다.

### 89

**핵심 키워드:** 최소 수집 · 마스킹 · 접근 통제 · 감사 기록

추적 ID, 내부 거래 ID, 상태 전이, 시각과 결과 코드를 중심으로 기록하겠습니다. 카드번호·토큰·비밀 키나 원문 요청 전체는 기본적으로 남기지 않겠습니다. 개인정보가 필요하면 마스킹과 접근 권한, 보존 기간을 함께 정하겠습니다. 금전 변경 감사 기록은 일반 진단 로그와 구분해 변경 전후 값과 사유를 변조하기 어렵게 보관하겠습니다.

### 90

**핵심 키워드:** 최소 권한 · 승인 분리 · 조정 이력 · 멱등 처리

조회, 환불 실행, 정산 조정 권한을 분리하고 서버에서 거래별 접근 권한을 검사하겠습니다. 영향이 큰 작업은 요청자와 승인자를 나누고 금액 한도와 추가 인증을 적용하겠습니다. 기존 원장을 덮지 않고 변경 전후 금액·사유·실행자를 조정 이력으로 남기겠습니다. 중복 클릭도 멱등하게 처리해 운영자의 반복 요청이 중복 지급으로 이어지지 않게 하겠습니다.

### 91

**핵심 키워드:** TypeScript · 풀스택 흐름 · 모듈과 DI · 유지보수

옥화당은 NestJS로 주문·결제 API를, Next.js로 고객·운영자 화면을 개발했습니다. 화면과 API를 함께 바꾸는 개인 프로젝트에서는 TypeScript로 언어를 통일하는 장점이 있습니다. NestJS의 모듈·DI 구조도 Spring 경험을 활용하기 좋습니다. 다만 타입 공유가 입력 검증을 대신하지는 않으며, 조직에서는 기존 운영 역량과 유지보수 비용을 우선하겠습니다.

### 92

**핵심 키워드:** 금액 정밀도 · 런타임 검증 · 트랜잭션 경계 · 상태 전이

두 환경 모두 금액 표현과 상태 전이 규칙을 명시해야 합니다. Java는 BigDecimal의 입력·스케일·반올림을, TypeScript는 number의 정밀도와 안전 범위를 주의하겠습니다. 금액은 최소 통화 단위 정수나 정확한 십진수 표현을 쓰고 DB·JSON 변환도 검증하겠습니다. 트랜잭션 방식은 달라도 주문·재고 갱신이 같은 경계에 참여하는지 확인하는 원칙은 같습니다.

### 93

**핵심 키워드:** 부분 취소 · 쿠폰 유효성 · 복원 시점 · 중복 방지

전체·부분 취소를 구분하고 만료된 쿠폰, 이미 재사용한 쿠폰의 복원 정책부터 합의하겠습니다. 발급 수량과 사용 횟수, 최소 주문금액도 복원 후 어떻게 적용할지 정해야 합니다. 취소 요청 접수가 아니라 취소 확정과 연결하고 같은 이벤트에 한 번만 복원하겠습니다. 환불 금액과 쿠폰 권리는 별도로 관리해 고객에게 처리 상태를 안내하겠습니다.

### 94

**핵심 키워드:** 거래 정확성 · 범위 축소 · 복구 절차 · 단계적 출시

금액 검증, 중복 청구 방지, 권한 통제와 복구 절차는 생략하지 않겠습니다. 대신 지원 결제 수단이나 할인 조합, 운영 편의 기능의 범위를 줄이겠습니다. 일부 자동화는 승인과 기록을 갖춘 수동 절차로 대체할 수 있지만 원장 직접 수정은 피하겠습니다. 핵심 장애 시나리오와 롤백 조건을 합의하고 작은 거래 범위부터 출시하겠습니다.

### 95

**핵심 키워드:** 문제 적합성 · 도구 생태계 · 단순한 구조 · 확장 근거

고산운은 웹 기술로, 영상 제작 도구는 Python·FFmpeg로 구현했습니다. 익숙한 Java·Spring으로 통일하기보다 브라우저 상호작용과 영상 처리에 맞는 도구를 활용하는 방식입니다. 구조도 처음부터 분산하기보다 프로세스 병렬화와 캐시로 요구를 충족하는지 보겠습니다. 공유 큐와 장애 격리가 실제로 필요해질 때 운영 복잡도를 감수하고 확장하겠습니다.

### 96

**핵심 키워드:** 불변 조건 · 실패 시나리오 · 재현 테스트 · 의사결정 기록

먼저 각 설계가 지키려는 조건부터 맞추겠습니다. 주문·재고가 함께 바뀌어야 하는 범위와 외부 결제 실패의 처리 상태를 합의한 뒤 대안을 비교하겠습니다. 같은 동시성·실패 시나리오를 적용하고 필요하면 작은 테스트로 잠금 시간과 복구 가능성을 검증하겠습니다. 취향보다 정확성과 운영 비용으로 결정하고 재검토 조건까지 기록하겠습니다.

### 97

**핵심 키워드:** 기술 공유 · 운영 문제 · 피드백 구체화 · 재현 검증

SQL 진입점 로깅처럼 운영 문제를 개선한 과정을 사내 기술 블로그와 서버개발그룹에서 공유했습니다. 결과 수치와 함께 기존 방식의 한계와 개선 원리를 전달하는 것이 중요합니다. 피드백은 실패 조건과 수정 범위로 구체화하고 재현 테스트로 검증하겠습니다. 비동기 추적에 대한 의견이라면 컨텍스트 전달과 정리 경계를 점검해 실제 개선으로 연결하겠습니다.

### 98

**핵심 키워드:** 문제 발견 · SQL 진입점 · 진단 시간 · 지식 공유

우아한형제들에서 장애 원인을 찾는 데 오래 걸리는 문제를 개선했습니다. SQL과 업무 흐름을 연결하기 위해 MDC 기반 진입점 로깅을 구현했고 원인 파악 시간을 25분에서 9분으로 줄였습니다. 기능 개발을 넘어 운영자가 문제를 찾는 과정까지 개선한 경험입니다. 해결 과정을 사내에 공유해 다른 개발자의 진단에도 활용할 수 있게 했습니다.

### 99

**핵심 키워드:** 초기 공유 · 잠정 판단 · 불확실성 구분 · 단계적 보완

정확히 설명하려고 세부사항을 충분히 확인한 뒤 공유하면서 초기 공유가 늦어지는 경향이 있었습니다. 분석을 기다리는 동안 동료의 판단도 늦어질 수 있다는 점을 인식했습니다. 지금은 확인된 사실과 가설, 필요한 결정을 먼저 나누고 상세 분석을 단계적으로 보완합니다. 불확실성을 명시하면 정확성과 빠른 공유를 함께 지킬 수 있다고 배웠습니다.

### 100

**핵심 키워드:** 병목 측정 · 자동 검증 · 예외 보류 · 지급 기준

정산 대기 시간이 수집·대사·승인 중 어디에서 생기는지 먼저 보겠습니다. 정상 거래는 자동 검증으로 빠르게 확정하고 불일치 거래만 보류하는 방식을 제안하겠습니다. 예정 금액과 출금 가능 금액을 구분해 일정과 보류 사유도 안내하겠습니다. 지급을 더 앞당기려면 환불 위험과 회수 조건을 재무·사업 담당자와 합의한 뒤 제한된 범위에 적용하겠습니다.
