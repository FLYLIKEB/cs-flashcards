### 61

우아한형제들에서 100만 건을 대상으로 하는 할인 알림 배치를 구현했습니다. 대용량 배치에서 중요하게 보는 부분은 대상 선정, 제한된 크기의 조회·가공, 발송 결과 기록을 분리해 실패 위치를 식별하는 것입니다. 같은 규모를 다시 설계한다면 실행 기준 시각과 대상 조건을 먼저 고정하고, 작은 단위로 처리하면서 성공·실패·재시도 상태를 남기겠습니다. 외부 알림 전송은 DB 커밋과 함께 원자적으로 성공하지 않으므로, 재시작 위치뿐 아니라 발송 중복을 막는 식별자도 함께 설계하겠습니다.

> 확인 메모: 100만 건의 기준이 상품·사용자·발송 건수 중 무엇인지와 당시 Reader·Writer, 알림센터 연계 방식, 직접 담당한 범위를 확인해야 합니다. 뒤의 구조 설명은 설계 제안입니다.

### 62

100만 건 전체를 한 번에 메모리에 올리는 방식은 피하겠습니다. 대상 식별자와 처리에 필요한 컬럼만 읽고, 정렬이 안정적인 키를 기준으로 일정량씩 조회하겠습니다. 처리 중 데이터가 추가·변경될 수 있다면 시작 시점의 상한 ID나 대상 목록을 고정해 조회 범위를 명확히 하겠습니다. 메모리는 조회 크기뿐 아니라 JPA 영속성 컨텍스트에 누적되는 객체도 확인하고, 청크 처리 후 참조가 해제되는지 보겠습니다. 마지막에는 예상 대상 수와 처리 결과를 대조해 누락을 검증하겠습니다.

> 확인 메모: 당시 사용한 커서·페이징 방식과 정렬 키, 메모리 측정치는 자료에 없어 단정하지 않았습니다.

### 63

청크 크기는 처리량을 높이면서도 메모리, 잠금 유지 시간, 실패 시 재처리 비용이 감당 가능한 수준으로 정하겠습니다. 작은 크기부터 같은 데이터로 측정하고, 커밋 비용 감소보다 긴 트랜잭션과 메모리 증가의 손해가 커지는 지점을 보겠습니다. DB 쓰기와 체크포인트가 같은 트랜잭션 자원에 묶이는지도 확인하겠습니다. 외부 알림 호출은 롤백되지 않기 때문에 청크 트랜잭션만으로 중복 발송을 막을 수 없으며, 별도 발송 상태와 멱등 처리가 필요합니다.

> 확인 메모: 당시 실제 청크 크기, 트랜잭션 매니저, 부하 측정 결과는 코드와 실행 기록으로 보완해야 합니다.

### 64

같은 실행 대상과 식별 파라미터를 유지한 채 마지막으로 커밋된 체크포인트부터 재시작하겠습니다. 다만 체크포인트 이전에 외부 발송이 성공하고 결과 저장만 실패할 수 있어, 체크포인트만 믿지는 않겠습니다. 캠페인과 수신 대상 조합에 고유한 발송 키를 두고, 외부 제공자가 멱등 키나 결과 조회를 지원하면 이를 활용하겠습니다. 지원하지 않으면 결과가 불명확한 발송을 별도 상태로 남겨 확인해야 합니다. 이런 조건에서 중복이 절대 없다고 약속하기보다 보장 범위와 복구 절차를 명확히 하겠습니다.

### 65

실행 단위 중복과 개별 항목 중복을 따로 막겠습니다. Spring Batch 메타데이터를 공유해 동일 JobInstance의 중복 실행을 제어하고, 업무 테이블에도 처리 대상과 실행 기준을 묶는 고유 제약을 두겠습니다. 서로 다른 실행이 같은 대상을 포함할 수 있으므로 작업 시작 시 조건부 UPDATE로 처리권을 획득하는 방식도 검토하겠습니다. 임대 방식의 잠금을 사용한다면 만료된 이전 작업자가 계속 쓰지 못하도록 버전 검증까지 필요합니다. 스케줄러 중복 방지만으로 업무 중복 처리가 해결되지는 않습니다.

> 확인 메모: 당시 실제 적용한 중복 실행 방지 장치는 확인되지 않았으므로 위 내용은 설계 답변입니다.

### 66

오류를 일시 장애와 영구 오류로 먼저 나누겠습니다. 요청 제한이나 일시적인 서버 오류는 제공자의 재시도 지침을 따르고, `Retry-After`가 있으면 존중하겠습니다. 그 외에는 지수 백오프에 지터를 더해 재시도가 동시에 몰리지 않게 하겠습니다. 재시도 횟수뿐 아니라 총 대기 시간과 알림의 유효 기간도 제한하고, 잘못된 수신 정보처럼 반복해도 해결되지 않는 오류는 격리하겠습니다. 전송 결과가 불명확할 때는 같은 식별자로 조회하거나 재시도해 중복 발송 위험을 줄이겠습니다.

### 67

실패 원인과 해당 항목이 전체 합계에 미치는 영향을 먼저 보겠습니다. 특정 항목의 잘못된 입력이라면 그 항목을 보류하고 원인과 금액을 기록하되, 의존관계가 없는 정상 항목은 처리할 수 있습니다. 반면 계산 규칙이나 환율 데이터가 잘못됐다면 전체 결과에 영향을 줄 수 있으므로 중단하겠습니다. 격리한 항목을 성공으로 세지는 않으며, 미처리 금액이 남은 정산은 부분 완료로 표시하겠습니다. 재무 담당자와 합의한 출금 승인 기준을 통과한 범위만 지급하겠습니다.

### 68

업무 데이터와 발행할 이벤트를 같은 DB 트랜잭션에 저장하는 트랜잭셔널 아웃박스 방식을 검토하겠습니다. 별도 전달기가 미발행 이벤트를 읽어 전송하고 성공 상태를 갱신하면, DB 반영 후 이벤트가 사라지는 공백을 줄일 수 있습니다. 전송 성공 직후 전달기가 죽으면 같은 이벤트가 다시 발행될 수 있으므로 소비자는 이벤트 ID를 기록해 중복 효과를 막아야 합니다. 주문별 순서가 중요하면 주문 ID와 버전도 함께 전달하고, 전달 지연·재시도·실패 격리 상태를 모니터링하겠습니다.

### 69

사내 Slack 통합 솔루션에서는 팀마다 달랐던 지원 요청을 공통 절차와 팀별 예외로 나누었습니다. JIRA 티켓 생성, 요청 정보 전달, 스프레드시트 연동, 릴리스 백포팅처럼 반복되는 작업을 연결해 요청자가 여러 도구를 오가며 정보를 다시 입력하는 부담을 줄였습니다. 반면 팀마다 다른 승인 담당자와 요청 조건까지 하나로 강제하는 것은 피해야 한다고 생각합니다. 공통화의 기준은 화면이 같은지가 아니라 요청 접수부터 처리 결과 확인까지 반복되는 업무 흐름이 같은지입니다.

> 확인 메모: 공통 기능과 팀별 설정의 실제 구분, 자동화·승인 경계를 당시 설계 자료로 확인해야 합니다. 20여 개 팀·100여 개 워크플로우는 최신 이력서 기준입니다.

### 71

개인 프로젝트 고산운에서 방별 작업 직렬화를 구현했습니다. 협동 시뮬레이션에서는 같은 방의 상태를 여러 요청이 읽은 뒤 각각 갱신하면, 앞선 변경이 덮이거나 이미 소모된 자원을 다시 사용하는 문제가 생길 수 있습니다. 방 단위로 상태 변경 순서를 정하면 한 작업의 결과를 다음 작업이 기준으로 삼을 수 있습니다. 설계상으로는 검증부터 변경까지 직렬화 경계 안에 두고, 저장·타이머처럼 다른 진입점도 같은 경계를 따르는지 확인해야 합니다.

> 확인 메모: 실제 재현했던 경쟁 상태와 코드 경계는 저장소 확인이 필요합니다. 자원 중복 사용은 가능한 문제의 예시이며 실제 발생한 장애로 단정하지 않습니다.

### 72

프로세스 내부 큐나 뮤텍스만 사용했다면 다른 서버의 작업까지 막지는 못합니다. 여러 서버로 확장한다면 한 방을 담당하는 쓰기 주체를 하나로 정하고 요청을 그 주체로 전달하겠습니다. 소유권 이전과 장애 복구 때는 이전 서버가 다시 쓰지 못하도록 세대 번호나 fencing token을 저장 시 검증해야 합니다. 또 클라이언트 재시도는 단일 소유자에게도 중복 도착할 수 있으므로 요청 ID로 처리 결과를 구분하겠습니다. 서버 수를 늘리는 것과 방 하나의 처리량을 늘리는 것은 별도의 문제입니다.

### 73

고산운에서는 스냅샷 캐싱과 저장·복원을 구현했습니다. 설계 원칙은 특정 버전의 상태로 만든 스냅샷이 중간 변경과 섞이지 않게 하는 것입니다. 이를 강화한다면 상태 변경 버전을 증가시키고, 직렬화된 처리 구간에서 일관된 복사본을 만든 뒤 그 버전을 캐시 키나 메타데이터에 기록하겠습니다. 스냅샷 생성 중 상태가 바뀌어도 이전 버전의 결과가 최신 캐시를 덮지 않도록 검사하겠습니다. 클라이언트에도 버전을 전달하면 오래된 스냅샷의 역전 적용을 막을 수 있습니다.

> 확인 메모: 실제 갱신 주기·무효화 조건·버전 필드의 적용 여부는 자료에 없어, 구현한 기능과 개선 설계를 구분했습니다.

### 74

저장 중 종료를 대비하려면 먼저 어디까지를 영속적으로 완료했다고 응답할지 정해야 합니다. 파일이라면 임시 파일에 완전히 기록한 뒤 교체하고, DB라면 트랜잭션으로 상태와 처리 식별자를 함께 저장하겠습니다. 마지막 스냅샷 이후 작업까지 복구해야 한다면 작업 로그나 이벤트를 내구성 있게 남기고, 복원 시 이미 반영된 요청은 건너뛰겠습니다. 메모리에서만 성공한 작업은 프로세스 종료로 잃을 수 있으므로, 저장 주기와 허용 가능한 손실 범위를 명시하고 실제 강제 종료 테스트로 검증하겠습니다.

> 확인 메모: 고산운의 실제 저장 매체·원자적 교체 방식·복구 보장 범위는 별도 확인이 필요합니다.

### 75

선립:티버스에서는 WebSocket 연결 복원과 방별 상태 관리를 구현했습니다. 재연결 시에는 끊기기 전 클라이언트 상태를 그대로 신뢰하지 않고 현재 서버 상태와 다시 맞추는 것이 핵심입니다. 설계한다면 참가자의 세션을 재검증하고 서버 스냅샷과 버전을 내려주겠습니다. 마지막 수신 버전 이후의 변경을 보관하고 있다면 증분 복구도 가능하지만, 이력이 없거나 간격이 크면 전체 상태를 다시 받겠습니다. 좌석 같은 공유 자원은 재접속했다고 자동 소유권을 인정하지 않고 서버의 현재 점유 상태를 기준으로 판단하겠습니다.

> 확인 메모: 실제 복원이 전체 스냅샷인지 증분 메시지인지, 참가자 식별 방식은 구현 확인이 필요합니다.

### 76

둘 다 같은 자원을 여러 요청이 동시에 점유하려는 문제라서, 조회 후 따로 갱신하면 경쟁 상태가 생깁니다. 한 처리 경계에서 점유 가능 여부를 확인하고 소유권을 바꾸거나, 조건부 갱신·고유 제약으로 한 요청만 성공하게 해야 합니다. 차이는 실패의 비용과 복구 기준입니다. 좌석은 연결 종료나 임대 만료로 해제할 수 있지만, 재고는 결제 결과가 불명확하면 즉시 풀어서는 안 됩니다. 재고 예약은 주문·결제 상태와 연결하고, 늦게 도착한 승인이나 환불까지 고려해 보상 절차를 설계해야 합니다.

### 77

선립:티버스는 방별로 사용자가 상호작용하는 서비스라, 방 ID를 기준으로 상태와 요청 처리를 모을 수 있는 Durable Objects와 잘 맞습니다. 이런 구조는 좌석과 진행 상태의 권위 있는 처리 지점을 만드는 데 도움이 됩니다. 다만 단일 스레드여도 외부 fetch를 기다리는 동안 다른 요청이 실행될 수 있어, 핸들러 전체가 자동 직렬화된다고 보지는 않겠습니다. 저장소의 입력 게이트가 보호하는 범위와 별도 동기화가 필요한 범위를 구분해야 합니다. 객체별 부하, 재시작 시 상태 복구, 비용과 플랫폼 의존성도 함께 평가하겠습니다.

> 확인 메모: 위 내용은 현재 서비스 구조에 대한 기술적 적합성 설명입니다. 당시 비교 후보와 실제 선택 이유는 본인의 의사결정 기록으로 확인해야 합니다.

### 78

선립:티버스에서 메시지 빈도와 좌표 검증을 구현했습니다. 원칙적으로 서버가 상태를 바꾸기 전에 메시지 형식, 인증된 참가자, 방 소속, 허용 범위를 검사해야 합니다. 이를 설계한다면 좌표의 숫자 여부와 유한성, 공간 경계, 시간 대비 이동량을 확인하고, 빈도 제한은 짧은 순간의 정상적인 몰림을 허용하되 지속적인 과부하는 차단하겠습니다. 모든 검증 실패를 같은 기준으로 처리하지 않고 관측 지표를 보면서 지연·재연결로 생긴 정상 요청과 악의적 요청을 구분하겠습니다.

> 확인 메모: 실제 제한 값, 검증 순서, 조정 이력은 확인되지 않았습니다. 속도 검증 등은 제안하는 추가 설계입니다.

### 79

웹과 API의 릴리스를 맞추는 것만으로 오래 열린 브라우저나 캐시된 파일까지 교체되지는 않습니다. 우선 필드 추가처럼 이전 클라이언트가 허용할 수 있는 변경을 적용하고, 필드 삭제나 의미 변경은 호환 기간을 두겠습니다. 요청이나 연결 과정에서 클라이언트 버전을 확인해 지원 범위를 벗어나면 명확한 갱신 안내를 제공하겠습니다. 데이터 구조를 바꿀 때는 구버전과 신버전이 함께 동작하는 단계가 필요하며, 배포 직후의 이전 클라이언트 요청과 롤백도 테스트하겠습니다.

### 80

공유 상태의 변경 순서를 정하고, 서버를 기준으로 검증하며, 재연결 후 상태를 복구하는 원칙은 결제·정산에도 적용할 수 있습니다. 다만 금액을 다루면 메모리의 일관성만으로는 부족합니다. DB의 원자성, 요청 멱등성, 변경 이력, 외부 거래와의 대사가 함께 필요합니다. 게임의 일시적인 화면 차이는 다음 스냅샷으로 맞출 수 있어도 중복 청구는 그렇게 해결되지 않습니다. 완료 응답 전에 무엇을 영속화해야 하는지, 장애 후 어떤 근거로 복구하는지를 더 엄격하게 정의하겠습니다.

### 81

우아한형제들에서 MDC 기반 SQL 진입점 로깅을 구현해 장애 원인 파악 시간을 25분에서 9분으로 줄였습니다. SQL 자체만 보면 어떤 업무 흐름에서 실행됐는지 바로 연결하기 어려운데, 진입점 정보를 함께 남기면 느린 쿼리를 요청이나 배치 흐름으로 거슬러 올라갈 수 있습니다. 설계 관점에서는 추적 ID, 진입한 업무 이름, 실행 시간을 연결하되 SQL 파라미터의 민감정보는 제외하겠습니다. 중요한 것은 로그의 양을 늘리는 것이 아니라 원인을 좁히는 데 필요한 연결 정보를 제공하는 것입니다.

> 확인 메모: 당시 실제 MDC 키와 SQL 진입점 수집 방식은 코드 또는 발표 자료로 확인해야 합니다.

### 82

MDC는 일반적으로 스레드에 묶여 있으므로 작업을 다른 스레드에 넘길 때 필요한 값을 복사해야 합니다. Spring의 TaskDecorator 같은 경계에서 제출 시점의 컨텍스트를 캡처하고 실행 스레드에 설정한 뒤, 작업이 끝나면 finally에서 이전 값을 복원하거나 제거하겠습니다. 스레드 풀은 스레드를 재사용하므로 정리하지 않으면 다음 요청의 로그에 이전 정보가 섞일 수 있습니다. 큐나 네트워크를 넘는 경우에는 추적 ID를 메시지 메타데이터로 전달하고 소비 지점에서 다시 컨텍스트를 구성하겠습니다.

> 확인 메모: 사내 TaskExecutor 통합 경험은 소재은행에 있지만, TaskDecorator를 실제 사용했는지는 확인되지 않았습니다.

### 83

기록된 성과는 SQL 진입점 로깅 개선으로 평균 원인 파악 시간이 25분에서 9분으로 줄었다는 것입니다. 이를 설명할 때 장애가 완전히 복구되는 시간과 원인을 식별하는 시간을 구분하겠습니다. 측정의 신뢰성을 확인하려면 시작·종료 시점의 정의, 비교한 사례 수, 장애 난이도와 담당자 차이를 함께 봐야 합니다. 같은 기준의 로그나 대응 기록을 제시하는 것이 가장 좋고, 일부 사례의 관측치라면 모든 장애에서 동일한 효과가 있었다고 확대해서 말하지 않겠습니다.

> 확인 메모: 표본 수, 관측 기간, 시작·종료 기준은 현재 자료에 없으므로 면접 전 근거 확인이 필요합니다.

### 84

우아한테크코스 팀 프로젝트 속닥속닥에서 테스트 격리와 실행 시간 개선을 수행했고, 425개 테스트 실행 시간이 3분에서 45초로 줄었습니다. 이런 개선은 반복되는 초기화 비용과 테스트 간 공유 상태를 나누어 보는 것이 중요합니다. 같은 문제를 점검한다면 Spring 컨텍스트 재생성, DB 초기화, 외부 I/O에 걸리는 시간을 먼저 측정하겠습니다. 컨텍스트를 재사용해도 데이터와 정적 상태는 테스트마다 초기화하고, 단독 실행·전체 실행·순서 변경에서 결과가 같은지 확인해 속도 때문에 격리를 희생하지 않겠습니다.

> 확인 메모: 실제 단축 원인이 컨텍스트 재사용인지 DB 정리 방식인지 등은 자료에 없습니다. 개선 성과와 일반적인 진단 방법을 구분했습니다.

### 85

같은 멱등 키로 동시에 결제 요청을 보내고, 응답을 받기 전 재시도하거나 같은 키에 다른 금액을 넣는 경우를 검증하겠습니다. 기대 조건은 승인 효과와 결제 레코드가 중복되지 않고, 다른 요청 내용이 같은 결과로 잘못 처리되지 않는 것입니다. 재고는 1개에 다수 요청을 동시에 시작해 예약 합계가 재고를 넘지 않는지 확인하겠습니다. 마지막으로 예약 만료와 결제 성공이 경쟁하는 경우도 테스트하겠습니다. 실제 DB의 잠금과 고유 제약을 검증해야 하므로 모킹한 단위 테스트만으로 끝내지 않겠습니다.

### 86

제어 가능한 PG 대역을 만들어 승인 직후 응답만 지연시키는 경우와 승인 자체가 실패하는 경우를 구분하겠습니다. 동일 웹훅을 반복하거나 역순으로 보내고, 처리 중 프로세스를 종료한 뒤 재시작해도 상태가 올바르게 복구되는지 확인하겠습니다. DB 장애는 커밋 전 실패와 커밋 결과를 알 수 없는 연결 끊김을 나눠 재현하겠습니다. 테스트의 핵심은 오류 응답을 받는지가 아니라 중복 청구, 초과 환불, 누락이 없고 불명확한 거래가 조회·대사로 해소되는지입니다.

### 87

기술 지표로는 응답 지연의 p95·p99, 오류율, 타임아웃, DB 잠금 대기, 큐 적체와 외부 PG 지연을 보겠습니다. 비즈니스 지표는 결제 시도 대비 승인율, 오래 머무는 처리 중 거래, 환불 지연, 정산 대상 대비 완료·보류 금액, 대사 불일치 건수입니다. 승인율은 카드 거절과 시스템 오류를 나누어야 불필요한 경보를 줄일 수 있습니다. 전체 평균만 보지 않고 결제 수단·통화·처리 단계별로 나누며, 금액과 건수는 민감정보 없이 집계하겠습니다.

### 88

요청이 성공했다는 지표와 업무가 완결됐다는 지표를 분리하겠습니다. 일정 시점에 정산 대상이 되어야 하는 원천 거래 목록을 독립적으로 산출하고, 실제 정산 항목과 식별자 단위로 대조하겠습니다. 건수와 금액 합계가 같아도 서로 다른 누락·중복이 상쇄될 수 있으므로 합계 비교만으로 끝내지 않겠습니다. 마감 시각을 넘긴 미처리 항목과 데이터 유입 중단도 감시하고, 발견된 누락은 원인을 남긴 뒤 멱등한 재처리 경로로 복구하겠습니다.

### 89

추적에 필요한 요청 ID, 내부 거래 ID, 상태 전이, 처리 시각, 실행 주체와 결과 코드를 중심으로 기록하겠습니다. 카드번호, 인증 토큰, 비밀 키, 전체 계좌정보나 원문 요청·응답은 기본적으로 남기지 않겠습니다. 조사에 필요한 개인정보가 있다면 마스킹·접근 통제·보존 기간을 함께 정하고, 로그 조회 자체도 감사 대상에 포함하겠습니다. 일반 진단 로그와 금전 변경 감사 기록은 목적이 다르므로, 후자는 변경 전후 값과 사유를 변조하기 어려운 방식으로 보관하겠습니다.

### 90

환불 조회, 환불 실행, 정산 조정을 별도 권한으로 나누고 서버에서 거래 단위 접근 권한을 검사하겠습니다. 정산 조정처럼 영향이 큰 작업은 요청자와 승인자를 분리하고, 금액 한도나 추가 인증을 정책에 맞게 적용하겠습니다. 변경 전후 금액, 대상 거래, 사유, 실행자·승인자, 시각을 기록하며 기존 원장을 덮기보다 조정 이력을 추가하겠습니다. 중복 클릭과 재전송도 멱등하게 처리하고, 운영자가 DB를 직접 수정하지 않고 검증된 관리 기능으로 복구할 수 있게 하겠습니다.

### 91

옥화당에서는 NestJS로 주문·결제 API를, Next.js로 고객 화면과 운영자 화면을 개발했습니다. 이 선택을 설명하는 기준은 개인 프로젝트에서 화면부터 서버까지 변경을 연결하기 쉬운지입니다. TypeScript를 함께 사용하면 언어 전환 부담이 줄고 NestJS의 모듈·DI 구조는 Spring 경험을 활용하기에도 좋습니다. 다만 타입을 공유해도 외부 입력이 검증되는 것은 아니므로 서버의 런타임 검증은 별도로 필요합니다. 조직에서는 개인의 익숙함보다 기존 운영 역량과 유지보수 비용을 우선하겠습니다.

> 확인 메모: 기술 선택의 실제 계기와 비교 후보는 사용자 확인이 필요한 답변 초안입니다.

### 92

두 환경 모두 금액 표현과 상태 전이 규칙을 명시적으로 다뤄야 합니다. Java에서는 BigDecimal을 문자열 등 정확한 입력으로 만들고 스케일·반올림 정책을 정하겠습니다. TypeScript의 number는 정수 안전 범위와 소수 오차를 고려해야 하므로 최소 통화 단위 정수 또는 검증된 십진수 표현을 선택하고 DB·JSON 변환도 확인하겠습니다. Spring의 프록시 기반 트랜잭션 경계와 NestJS·TypeORM의 트랜잭션 매니저 전달 방식은 다르지만, 결제·재고 갱신이 같은 트랜잭션에 참여하는지 검증해야 한다는 원칙은 같습니다.

### 93

전체 취소와 부분 취소를 먼저 구분하고, 쿠폰 유효기간이 지났거나 이미 다른 주문에 사용된 경우의 정책을 확인하겠습니다. 발급 수량 제한, 1인당 사용 횟수, 최소 주문금액, 다른 할인과의 중복 조건도 복원 후 유지할지 합의해야 합니다. 처리 시점은 취소 요청 접수가 아니라 실제 취소 확정과 연결하고, 같은 취소 이벤트를 여러 번 받아도 쿠폰은 한 번만 복원되게 하겠습니다. 환불 금액 계산과 쿠폰 권리 복원을 구분해, 고객에게 각각의 처리 상태를 안내하겠습니다.

### 94

금액 검증, 중복 청구 방지, 권한 검증, 거래 추적, 실패 복구는 일정 때문에 생략할 수 없는 조건으로 보겠습니다. 대신 처음 지원할 결제 수단이나 프로모션 조합, 운영 화면의 편의 기능은 범위를 줄일 수 있습니다. 자동화가 늦어지는 업무는 검증·승인·기록을 갖춘 수동 절차로 한시적으로 처리할 수 있지만, 원장을 직접 고치는 식의 우회는 피하겠습니다. 출시 전 핵심 장애 시나리오와 롤백 조건을 합의하고 작은 범위부터 적용해 실제 거래 결과를 확인하겠습니다.

### 95

고산운은 JavaScript·Canvas·Node.js로, 영상 제작 도구는 Python·FFmpeg로 구현했습니다. 같은 언어로 통일하기보다 브라우저 렌더링과 실시간 상호작용에는 웹 기술을, 영상 합성과 인코딩에는 해당 도구 생태계를 활용하는 방식입니다. 설계를 설명할 때도 우선 현재 규모에서 한 프로세스와 명확한 처리 경계로 해결할 수 있는지 보겠습니다. 분산 시스템이 필요한 근거가 없다면 운영 지점을 늘리는 구조를 서둘러 도입하지 않고, 실제 병목과 장애 요구가 드러날 때 확장하겠습니다.

> 확인 메모: 실제로 검토 후 제외한 기술이나 아키텍처는 기록에 없습니다. 마지막 부분은 기술 선택 원칙이며 특정 도입을 거절한 과거 사례가 아닙니다.

### 96

먼저 서로 지키려는 조건을 문장으로 맞추겠습니다. 예를 들어 주문과 재고가 항상 함께 바뀌어야 하는지, 외부 결제 실패를 어느 상태로 남길지부터 합의해야 트랜잭션 범위를 논의할 수 있습니다. 이후 각 안을 같은 동시성·실패 시나리오에 대입하고, 필요하면 작은 재현 테스트로 잠금 시간이나 복구 가능성을 비교하겠습니다. 취향보다 정확성, 운영 복잡도, 변경 비용을 기준으로 결정하고, 선택 이유와 나중에 재검토할 조건을 기록하겠습니다.

### 97

사내에서는 SQL 진입점 로깅처럼 실제 운영 문제를 개선한 과정을 기술 블로그와 서버개발그룹에서 공유했습니다. 저는 결과 수치만 전달하기보다 어떤 정보가 부족해 원인 파악이 어려웠고, 변경 후 어떤 경로로 문제를 추적할 수 있게 됐는지 설명하는 것이 중요하다고 생각합니다. 피드백을 코드에 반영할 때는 적용 범위나 예외 상황을 구체화해 재현 가능한 개선 항목으로 바꾸겠습니다. 공유의 가치는 발표 자체보다 동료가 같은 문제를 더 빨리 해결하도록 만드는 데 있습니다.

> 확인 메모: 실제 받은 피드백과 그로 인해 변경된 코드·운영 사례는 자료에 없어 만들지 않았습니다. 발표 자료에서 한 사례를 확인하면 답변을 더 구체화할 수 있습니다.

### 98

우아한형제들에서 장애 원인 파악에 시간이 오래 걸리는 문제를 개선한 경험이 있습니다. SQL만으로는 업무 진입점과 실행 흐름을 연결하기 어려웠기 때문에 MDC 기반 SQL 진입점 로깅을 구현했고, 평균 원인 파악 시간을 25분에서 9분으로 줄였습니다. 기능이 동작하는지에 그치지 않고 운영자가 문제를 찾는 과정까지 개선한 사례입니다. 이후 해결 과정을 사내에 공유해 개인의 문제 해결 경험이 다른 개발자의 진단에도 쓰일 수 있도록 했습니다.

> 확인 메모: 개선 과제를 처음 제안한 주체와 본인이 맡은 범위는 면접 전 확인해야 합니다. 성과의 측정 기준도 83번 확인 메모와 같습니다.

### 99

정확히 설명하려면 세부사항을 충분히 확인한 뒤 공유해야 한다고 생각해 초기 공유가 늦어지는 경향이 있었습니다. 하지만 분석이 완성될 때까지 기다리면 동료가 위험을 늦게 알거나 의사결정을 미룰 수 있다는 점을 인식했습니다. 그래서 현재는 확인된 사실, 아직 가설인 부분, 당장 필요한 판단을 먼저 나누고 상세 분석을 단계적으로 보완하는 방향으로 바꾸고 있습니다. 정확성과 빠른 공유는 반대되는 가치가 아니라, 불확실성을 명시하면 함께 지킬 수 있다고 배웠습니다.

> 확인 메모: 기존 지원서에 기록된 공유 방식의 개선 경험을 사용했습니다. 특정 장애·일정 지연 사건이나 정량 효과는 자료에 없어 추가하지 않았습니다.

### 100

먼저 빠른 정산이 필요한 이유와 검증에 시간이 걸리는 지점을 각각 확인하겠습니다. 실제 대기 시간이 데이터 수집, 대사, 승인 중 어디에서 생기는지 측정하면 정확성을 낮추지 않고 줄일 수 있는 시간이 보입니다. 정상 거래는 자동 검증으로 빠르게 확정하고, 불일치가 있는 거래만 보류하는 방식을 제안하겠습니다. 정산 예정 금액과 출금 가능 금액을 분리해 예상 일정과 보류 사유도 안내하겠습니다. 지급을 앞당기는 정책이 필요하다면 환불 위험과 회수 조건을 재무·사업 담당자와 합의한 뒤 제한된 범위에서 검증하겠습니다.
