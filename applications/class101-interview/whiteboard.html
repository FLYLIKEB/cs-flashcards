박지우 이력서와 클래스101 PP 팀 공고 Markdown을 기준으로 다시 골랐습니다. 결제·정산의 정확성을 연습하고, 대용량 처리·캐싱 경험과 연결해 설명하기 좋은 알고리즘 문제입니다. 확인된 기출이나 출제 확률 순위는 아닙니다.

먼저 ① 결제 이벤트 중복 → ② 결제 내역 대사 → ③ 쿠폰 배분을 연습하세요. 옥화당 경험을 PP 팀의 결제·정산 정확성과 가장 직접적으로 연결하는 준비 순서입니다.

한 문제를 20분에 설명하는 순서
  1. 0–2분 · 조건 확인. 입력 크기, 중복, 빈 입력, 결과가 없을 때를 질문합니다.
  2. 2–5분 · 작은 예제. 입력과 정답을 직접 쓰고 완전탐색부터 설명합니다.
  3. 5–9분 · 개선. 반복되는 일을 찾고 자료구조를 선택합니다. 무엇을 항상 유지할지 한 문장으로 씁니다.
  4. 9–15분 · 의사코드. 보드를 입력·상태·코드 세 칸으로 나누고 변수와 상태 변화를 연결합니다.
  5. 15–18분 · 검증. 정상 예제 하나와 경계 사례 두 개를 손으로 실행합니다.
  6. 18–20분 · 마무리. 시간·공간 복잡도와 조건이 바뀔 때의 대안을 설명합니다.

막히면 “우선 정확한 완전탐색을 적고, 중복 계산을 줄이겠습니다”라고 말하세요. 이 시간 배분은 연습용이며 실제 면접 진행 방식이 아닙니다.

01 · 해시맵

결제 이벤트 중복과 내용 충돌 구분하기

이 문제를 고른 이유

이력서: 옥화당의 결제 준비 멱등 처리·취소·환불. 공고: 결제·주문 데이터의 정확성과 일관성. 중복을 무엇으로 정의하는지부터 설명하는 연습입니다.

문제와 예제

이벤트를 도착 순서대로 읽고 NEW·DUPLICATE·CONFLICT로 분류하세요. 같은 eventId와 같은 내용은 중복, 같은 eventId인데 내용이 다르면 충돌입니다. e1/P1/승인/100원, 같은 e1, e1/200원, e2/P1/환불/100원 → NEW, DUPLICATE, CONFLICT, NEW. 같은 결제 P1의 승인과 환불은 별개 이벤트입니다.

먼저 물어볼 것

중복 키는 eventId인가요, paymentId인가요? 어떤 필드가 같아야 같은 내용인가요? 여기서는 전역적으로 유일한 eventId, 비교 대상은 paymentId·type·amount·currency, null 입력 없음으로 합의합니다. 충돌은 기록하되 최초 내용을 덮어쓰지 않습니다.

단순 접근 → 개선

매번 앞선 이벤트를 모두 찾으면 O(n²)입니다. eventId→최초 payload 맵을 만들면 평균 O(1) 조회로 신규·중복·충돌을 분리합니다. 금액만 비교하면 결제나 통화가 다른 충돌을 놓칩니다.

보드에 이렇게 추적하기

e1: 없음 → 최초 payload 저장, NEW
e1: 최초 payload와 같음 → DUPLICATE
e1: amount만 200으로 다름 → CONFLICT, map 유지
e2: paymentId=P1이어도 새 eventId → NEW
의사코드 보기
// Payload는 아래 필드의 값 동등성으로 비교하는 불변 record.
record Payload(String paymentId, String type,
               long amount, String currency) {}
Map<String, Payload> first = new HashMap<>();
for (Event e : events) {
    Payload payload = new Payload(e.paymentId, e.type,
                                  e.amount, e.currency);
    Payload previous = first.get(e.eventId);
    if (previous == null) {
        first.put(e.eventId, payload);
        emit(e.eventId, "NEW");
    } else if (previous.equals(payload)) {
        emit(e.eventId, "DUPLICATE");
    } else {
        emit(e.eventId, "CONFLICT");
    }
}

정확성 · 복잡도 · 경계 사례

맵은 각 eventId의 최초 내용을 보존합니다. 동일 결제의 다른 이벤트는 제거하지 않습니다. 고정 크기 payload와 키 비교를 가정하면 평균 시간 O(n), 공간 O(u), u는 서로 다른 eventId 수입니다. 빈 입력·완전 중복·통화만 다른 충돌·충돌 뒤 최초 내용 재전송을 검사하세요.

“같은 결제라는 이유로 버리지 않겠습니다. 이벤트 식별자로 찾은 뒤 내용까지 비교하고, 충돌은 정상 중복과 구분하겠습니다.”

꼬리질문: 이것으로 결제가 정확히 한 번 실행되나요? 아닙니다. 이 코드는 한 번의 입력을 분류하는 단일 스레드 알고리즘입니다. 재시작·동시 요청·외부 PG 호출에는 영속 멱등 키, 원자적 상태 전이와 별도 복구 설계가 필요합니다.

02 · 해시 조인

내부 결제와 PG 내역의 누락·금액 불일치 찾기

이 문제를 고른 이유

이력서: 주문·결제 구현과 100만 건 배치 경험. 공고: 결제에서 정산까지 정확한 자금 흐름. 실무 경험을 데이터 비교 알고리즘으로 연결하는 문제입니다.

문제와 예제

내부 목록과 PG 목록을 transactionId로 비교하세요. 내부 A/100/KRW, B/200/KRW, PG A/90/KRW, C/300/KRW이면 A=내용 불일치, B=PG에 없음, C=내부에 없음입니다. 금액과 통화가 모두 같아야 일치합니다.

먼저 물어볼 것

같은 거래 범위·시점의 스냅샷인가요? 승인과 환불을 구분한 거래 ID인가요? 각 목록에서 ID는 유일한가요? 여기서는 양쪽 목록의 ID 중복을 오류로 거부하고, 금액은 해당 통화의 최소 단위 정수로 받습니다. 결과 순서는 상관없습니다.

단순 접근 → 개선

내부의 각 행을 PG 전체에서 찾으면 O(nm)입니다. 양쪽에 유일 키 맵을 만들고, 내부를 순회하며 PG에서 짝을 제거합니다. 남은 PG 행이 반대 방향의 누락입니다. 검증을 먼저 끝내야 일부 비교 결과를 낸 뒤 중복을 발견하는 일을 피합니다.

보드에 이렇게 추적하기

검증: 내부 map={A,B}, PG map={A,C}
A: PG에서 A 제거 → 100 ≠ 90 → MISMATCH
B: PG에 없음 → MISSING_IN_PG
PG에 C만 남음 → MISSING_INTERNAL
의사코드 보기
Map<String, Tx> unique(List<Tx> rows) {
    Map<String, Tx> out = new HashMap<>();
    for (Tx t : rows) {
        if (out.containsKey(t.id))
            throw new IllegalArgumentException("duplicate id");
        out.put(t.id, t);
    }
    return out;
}
void reconcile(List<Tx> internal, List<Tx> pg) {
    Map<String, Tx> left = unique(internal);
    Map<String, Tx> right = unique(pg);
    for (Tx a : left.values()) {
        Tx b = right.remove(a.id);
        if (b == null) emit(a.id, "MISSING_IN_PG");
        else if (a.amount != b.amount ||
                 !a.currency.equals(b.currency))
            emit(a.id, "MISMATCH");
    }
    for (Tx b : right.values())
        emit(b.id, "MISSING_INTERNAL");
}

정확성 · 복잡도 · 경계 사례

처리된 내부 ID는 PG 맵에서 제거되므로 남은 PG 행은 내부에 대응 행이 없습니다. 평균 시간 O(n+m), 추가 공간 O(n+m), 출력 제외입니다. 양쪽 빈 목록·한쪽만 빈 목록·같은 금액 다른 통화·중복 ID를 확인하세요. 중복을 합산하거나 덮어쓰면 잘못된 정상 판정이 생깁니다.

“양쪽 누락을 따로 보겠습니다. 먼저 ID 유일성을 검증하고, 짝을 비교한 뒤 남은 PG 데이터도 결과에 포함하겠습니다.”

꼬리질문: 메모리에 못 담으면? transactionId로 정렬된 두 스트림을 투 포인터로 병합 비교합니다. 미정렬이면 외부 정렬 비용이 추가됩니다. 실무 대사는 시차·거래 상태·부분 환불과 마감 시점도 합의해야 합니다.

03 · 정수 계산 + 정렬

쿠폰 할인액을 상품에 오차 없이 배분하기

이 문제를 고른 이유

이력서: 옥화당의 주문·결제·취소·환불. 공고: 프로모션·쿠폰과 정확한 정산 금액. 알고리즘뿐 아니라 합계 보존과 반올림 규칙을 설명할 수 있는 문제입니다.

문제와 예제

상품 가격 비율로 정수 할인액 D를 배분하고 배분 합을 정확히 D로 맞추세요. A=100원, B=100원, C=100원, D=10원 → A=4원, B=3원, C=3원. 같은 나머지는 itemId 오름차순으로 우선합니다. 이 배분 규칙은 연습용이며 클래스101의 실제 정책을 뜻하지 않습니다.

먼저 물어볼 것

배분 대상 가격은 할인 전인가요? 같은 통화인가요? 0원 상품과 동률은 어떻게 처리하나요? 여기서는 서로 다른 itemId, 가격≥0, 총가격 S>0, 0≤D≤S입니다. 아래는 S≤10⁹ 최소 화폐 단위로 제한해 D×가격≤10¹⁸이 long 범위에 들게 합니다.

단순 접근 → 개선

비율을 double로 계산하고 각자 반올림하면 합이 D와 어긋날 수 있습니다. 각 상품의 D×가격 / S를 정수로 내림하고, 남은 단위를 나머지가 큰 상품부터 1씩 줍니다. 나머지는 같은 분모 S를 쓰므로 정수 나머지만 비교하면 됩니다.

보드에 이렇게 추적하기

S=300, D=10
상품  D×가격   몫   나머지
A       1000    3     100
B       1000    3     100
C       1000    3     100
기본 합=9, 잔여=1 → 동률에서 A에 1 추가 → [4,3,3]
의사코드 보기
// Item(id, price), Share(id, amount, remainder).
// 검증: 고유 id, price>=0, 0<S<=1_000_000_000,
//       0<=discount<=S. 합계 검증에도 addExact 사용.
long total = 0;
for (Item x : items) total = Math.addExact(total, x.price);
validate(items, total, discount);
List<Share> shares = new ArrayList<>();
long assigned = 0;
for (Item x : items) {
    long numerator = discount * x.price;
    long amount = numerator / total;
    shares.add(new Share(x.id, amount, numerator % total));
    assigned += amount;
}
shares.sort((a, b) -> {
    int c = Long.compare(b.remainder, a.remainder);
    return c != 0 ? c : a.id.compareTo(b.id);
});
long left = discount - assigned;
for (int i = 0; i < left; i++) shares.get(i).amount++;
// itemId와 배분액의 대응을 반환. 정렬 후 입력 순서와 혼동 금지.
return shares;

정확성 · 복잡도 · 경계 사례

내린 값의 합은 D 이하이고 남는 수는 상품 수 미만입니다. 잔여 수만큼 1을 더하므로 최종 합은 정확히 D입니다. 0≤D≤S이므로 상품별 할인도 가격을 넘지 않습니다. 시간 O(n log n), 공간 O(n). D=0·D=S·0원 상품·동률·단일 상품을 확인하세요. S=0과 범위 초과는 오류입니다.

“각 상품을 따로 반올림하지 않고 합계부터 보존하겠습니다. 정수 몫을 배분한 뒤 큰 나머지 순서로 남은 1원들을 배분합니다.”

꼬리질문: 금액 한도를 없애면? 합과 곱을 BigInteger로 바꿉니다. 환불 때는 남은 상품으로 재배분하지 않고 주문 시 확정한 배분 내역을 기준으로 할지 정책을 확인합니다.

04 · 정렬 + 구간 병합

구독 이용권의 연속 사용 가능 기간 합치기

이 문제를 고른 이유

이력서: 커머스 주문·결제와 상태 관리. 공고: 정기결제와 상품 정책. 날짜 경계와 자료구조를 함께 설명하는 구간 문제로 선정했습니다.

문제와 예제

한 사용자의 동일 이용권에 대한 유효 구간들을 합쳐 사용 가능 기간을 구하세요. [1,4), [3,6), [6,8), [10,12) → [1,8), [10,12). 시작 포함·끝 제외이며 빈틈없이 맞닿으면 합칩니다. 갱신·환불을 반영해 유효 구간이 이미 확정된 입력입니다.

먼저 물어볼 것

같은 이용권 종류와 권한끼리인가요? 끝점 포함 여부와 시간대는요? 여기서는 같은 권한, 공통 시간 기준, start<end, 입력 정렬 허용입니다. 맞닿는 구간을 합치는 것은 이 연습 문제의 규칙입니다.

단순 접근 → 개선

모든 쌍을 반복 비교하는 대신 시작점으로 정렬합니다. 현재 구간이 마지막 결과에 닿거나 겹치면 끝점을 max로 늘리고, 사이에 빈틈이 있으면 새 구간을 만듭니다. 구독 일수를 단순 합하면 겹친 기간을 중복 계산합니다.

보드에 이렇게 추적하기

[1,4) 저장
[3,6): 3≤4 → [1,6)
[6,8): 6=6 → 연속이므로 [1,8)
[10,12): 10>8 → 새 구간
사용 가능: [1,8), [10,12)
의사코드 보기
List<long[]> merge(long[][] intervals) {
    Arrays.sort(intervals,
        (a, b) -> Long.compare(a[0], b[0]));
    List<long[]> out = new ArrayList<>();
    for (long[] x : intervals) {
        if (out.isEmpty() ||
            out.get(out.size()-1)[1] < x[0]) {
            out.add(new long[]{x[0], x[1]});
        } else {
            long[] last = out.get(out.size()-1);
            last[1] = Math.max(last[1], x[1]);
        }
    }
    return out;
}

정확성 · 복잡도 · 경계 사례

결과는 처리한 구간의 합집합을 시작순으로 보존하고 서로 떨어져 있습니다. 반열린 구간이라도 [1,3)∪[3,5)=[1,5)이므로 연속 구간 병합이 가능합니다. 시간 O(n log n), 출력·정렬 보조 공간 O(n). 빈 입력·포함 관계·같은 시작·맞닿음·서로 다른 이용권을 확인하세요.

“중복 기간을 더하지 않고 합집합을 구하겠습니다. 같은 권한끼리 정렬한 뒤 마지막 결과의 끝점만 늘리겠습니다.”

꼬리질문: 환불로 [4,5)를 빼면? 합치기와 다른 구간 차집합 문제라서 분할이 필요합니다. 구독 갱신 자체의 결제 성공·실패 상태 전이는 이 알고리즘이 처리하지 않습니다.

05 · 해시맵 + 덱

사용자별 최근 W초의 요청 수 제한하기

이 문제를 고른 이유

이력서: 티버스 메시지 빈도 검증, Frameflow 요청 제한 재시도, 100만 건 알림 배치. 공고: 안정적인 백엔드 운영. 시간 경계와 상각 복잡도를 설명하는 문제입니다.

문제와 예제

사용자별로 최근 W초 동안 허용된 요청을 최대 L개로 제한하세요. W=10, L=2, 사용자 A의 요청 시각 [0,1,2,10] → [허용,허용,거부,허용]. 현재 시각 t의 집계 구간은 (t−W,t]이며 거절 요청은 저장하지 않습니다.

먼저 물어볼 것

거절 요청도 횟수에 넣나요? 사용자별인가요? 시각이 뒤로 갈 수 있나요? 여기서는 단일 스레드, W>0, L>0, 서버 시각 t≥0이며 전체 요청 시각이 비감소합니다. 동일 시각의 여러 요청도 각각 셉니다.

단순 접근 → 개선

매번 과거 모든 요청을 세면 요청 수가 늘수록 느려집니다. 사용자마다 시간순 덱을 두고 만료된 시각을 앞에서 제거합니다. 남은 개수가 L 미만일 때만 뒤에 현재 시각을 추가합니다.

보드에 이렇게 추적하기

A, t=0: [] → [0], 허용
A, t=1: [0] → [0,1], 허용
A, t=2: [0,1], 이미 2개 → 거부, 큐 그대로
A, t=10: t−W=0, 0 제거 → [1,10], 허용
B의 큐는 A와 별개
의사코드 보기
Map<String, Deque<Long>> accepted = new HashMap<>();
boolean allow(String user, long now) {
    Deque<Long> q = accepted.computeIfAbsent(
        user, key -> new ArrayDeque<>());
    while (!q.isEmpty() && q.peekFirst() <= now - window)
        q.removeFirst();
    if (q.size() >= limit) return false;
    q.addLast(now);
    return true;
}

정확성 · 복잡도 · 경계 사례

만료 제거 후 덱에는 (t−W,t]의 허용 요청만 시간순으로 남습니다. 각 허용 시각은 한 번 들어가고 한 번 제거되므로 요청당 평균 해시 비용 포함 상각 O(1), 한 번에 최대 O(L) 삭제입니다. 사용자당 최대 L개, U명의 맵을 유지하면 O(UL) 공간입니다. t−W와 정확히 같은 시각·연속 거절·다른 사용자·같은 시각을 검사하세요.

“시간 경계를 먼저 정하겠습니다. 현재 구간 밖의 허용 기록만 앞에서 지우고, 거절된 요청은 다음 판단에 누적하지 않습니다.”

꼬리질문: 사용자가 무한히 늘거나 서버가 여러 대라면? 비활성 사용자 항목은 만료 기록 정리 후 제거하는 청소가 필요합니다. 이 코드는 단일 프로세스용이며, 분산 제한에는 공통 저장소에서 조회·정리·추가의 원자성이 필요합니다.

06 · 최소 힙

정렬된 정산 배치 K개를 한 스트림으로 합치기

이 문제를 고른 이유

이력서: Spring Batch와 100만 건 할인 알림 처리. 공고: 정산·출금 데이터 처리. 전량 적재 없이 정렬된 입력의 성질을 활용하는 연습입니다.

문제와 예제

각 파일이 거래 시각 오름차순인 K개 정산 스트림을 전역 시각순으로 출력하세요. S0=[1,4], S1=[1,3], S2=[2] → (1,S0),(1,S1),(2,S2),(3,S1),(4,S0). 같은 시각이면 스트림 번호가 작을수록 먼저, 같은 스트림에서는 원래 순서를 유지합니다. 중복 제거는 하지 않습니다.

먼저 물어볼 것

입력이 같은 기준으로 정렬되어 있나요? 동률 순서는요? 전체 결과를 메모리에 담아야 하나요? 아래는 iterator가 한 행씩 읽고, 출력도 한 행씩 쓰는 조건입니다. 각 스트림은 비감소 순서이며 금액이 아닌 거래 시각으로 병합합니다.

단순 접근 → 개선

전부 모아 정렬하면 O(N log N) 시간·O(N) 적재 공간입니다. 각 스트림의 아직 출력하지 않은 첫 행 하나만 최소 힙에 둡니다. 가장 작은 행을 출력한 뒤 그 행이 속한 스트림에서 다음 행만 가져옵니다.

보드에 이렇게 추적하기

초기 힙: (1,S0),(1,S1),(2,S2)
(1,S0) 출력 → S0 다음 (4,S0) 추가
(1,S1) 출력 → S1 다음 (3,S1) 추가
(2,S2) 출력 → S2 종료
(3,S1), (4,S0) 출력
의사코드 보기
// Head(row, stream). iterator.next()는 지연 읽기.
PriorityQueue<Head> heap = new PriorityQueue<>((a, b) -> {
    int c = Long.compare(a.row.time, b.row.time);
    return c != 0 ? c : Integer.compare(a.stream, b.stream);
});
for (int i = 0; i < streams.size(); i++)
    if (streams.get(i).hasNext())
        heap.offer(new Head(streams.get(i).next(), i));
while (!heap.isEmpty()) {
    Head h = heap.poll();
    output.write(h.row);
    Iterator<Row> source = streams.get(h.stream);
    if (source.hasNext())
        heap.offer(new Head(source.next(), h.stream));
}

정확성 · 복잡도 · 경계 사례

각 스트림의 나머지는 그 스트림의 힙 원소보다 작지 않으므로 힙의 최솟값이 전체 미출력 원소의 최솟값입니다. K≥2이면 O(K+N log K) 시간, 추가 공간 O(K), 출력과 입력 버퍼 제외입니다. K=1은 O(N), 빈 스트림 확인은 O(K)입니다. K=0·모두 빈 입력·같은 시각·한 스트림만 긴 경우를 확인하세요.

“파일 전체가 아니라 각 파일의 다음 후보만 비교하겠습니다. 출력한 파일에서만 다음 값을 읽으면 메모리가 K에 비례합니다.”

꼬리질문: 정렬되지 않은 파일이면? 먼저 외부 정렬이 필요합니다. 중간 실패 재시작은 스트림별 위치와 출력 커밋 지점을 별도로 기록해야 하며 힙 병합만으로 중복 출금을 막지는 못합니다.

07 · 위상 정렬

정산·이관 작업의 의존 순서와 순환 찾기

이 문제를 고른 이유

이력서: 전시 API 92개 이관과 워크플로우 자동화. 공고: 결제·주문·정산 단계 연결. 의존 관계를 명시하고 실행 가능한 순서를 설명하는 문제입니다.

문제와 예제

연습용 정산 작업 0=거래 수집, 1=환불 반영, 2=수수료 계산, 3=정산 확정에 의존 관계가 있습니다. 실제 업무 순서가 아니라 입력으로 주어진 규칙을 따릅니다. 모든 작업을 수행할 순서 하나를 반환하세요. n=4, 0→1, 0→2, 1→3, 2→3 → [0,1,2,3]. [0,2,1,3]도 정답입니다.

먼저 물어볼 것

화살표는 선행 작업→후속 작업인가요? 순서가 여러 개면 아무거나 되나요? 순환이면 실패를 표시하나요? 아래는 유효한 작업 번호와 중복 없는 간선, 순환 시 실패를 가정합니다.

단순 접근 → 개선

매번 모든 작업의 선행 조건을 다시 확인하면 낭비가 큽니다. 남은 선행 작업 수인 진입차수를 기록합니다. 진입차수 0인 작업을 실행하고, 그 작업을 기다리던 후속 작업의 수만 하나씩 줄입니다.

보드에 이렇게 추적하기

초기 indegree = [0,1,1,2], queue = [0]
0 처리 → [0,0,0,2], queue = [1,2]
1 처리 → [0,0,0,1], queue = [2]
2 처리 → [0,0,0,0], queue = [3]
3 처리 → 완료 4개 = 전체 4개
의사코드 보기
// next[u]는 u가 끝나야 시작할 수 있는 작업 목록.
List<Integer> order(List<List<Integer>> next) {
    int n = next.size();
    int[] degree = new int[n];
    for (List<Integer> list : next)
        for (int v : list) degree[v]++;
    Deque<Integer> q = new ArrayDeque<>();
    for (int u = 0; u < n; u++)
        if (degree[u] == 0) q.addLast(u);
    List<Integer> result = new ArrayList<>();
    while (!q.isEmpty()) {
        int u = q.removeFirst();
        result.add(u);
        for (int v : next.get(u))
            if (--degree[v] == 0) q.addLast(v);
    }
    if (result.size() != n)
        throw new IllegalArgumentException("cycle");
    return result;
}

정확성 · 복잡도 · 경계 사례

진입차수는 아직 처리하지 않은 선행 작업 수입니다. 0인 작업만 꺼내므로 결과는 선행 조건을 지킵니다. 처리하지 못한 작업이 남으면 그 부분에 순환이 있습니다. 시간 O(V+E), 주어진 인접 리스트 외 추가 공간 O(V); 그래프 저장까지 포함하면 O(V+E). 간선 없음, 분리된 그래프, 자기 자신으로의 간선, 0→1→0을 확인하세요.

“아직 끝나지 않은 선행 작업 개수를 관리하겠습니다. 준비된 작업만 큐에 넣고, 끝난 뒤에도 남은 작업이 있으면 순환으로 판단합니다.”

꼬리질문: 가능한 순서 중 번호가 가장 작은 순서라면? 큐 대신 최소 힙을 사용합니다. 실제 이관·정산에서는 작업 성공·실패, 재시도, 롤백과 병렬 작업의 완료 시점을 별도 상태로 관리해야 합니다.

08 · 해시맵 + 이중 연결 리스트

배너·스냅샷 조회용 LRU 캐시 구현하기

이 문제를 고른 이유

이력서: B마트 배너 API 909ms→18ms 최적화와 고산운 스냅샷 캐싱. 공고: 상황에 맞는 기술 선택과 정확한 데이터 관리. 캐싱 경험에서 자료구조·정합성 질문으로 이어갈 수 있습니다. 기존 프로젝트가 LRU를 썼다는 뜻은 아닙니다.

문제와 예제

용량이 고정된 캐시의 get/put을 평균 O(1)에 구현하세요. 가득 차면 가장 오래 사용하지 않은 항목을 제거합니다. get과 기존 키의 put 모두 사용으로 간주합니다.

용량 2 · 목록은 최근 → 오래된 순서
put(1,A) → [1]
put(2,B) → [2,1]
get(1)   → A 반환, [1,2]
put(3,C) → 2 제거, [3,1]
get(2)   → 없음

먼저 물어볼 것

용량 0을 허용하나요? 없는 키의 반환값은 무엇인가요? null 값과 동시 접근을 지원해야 하나요? 아래는 용량≥0, null 값 불가, 없는 키는 null, 단일 스레드 조건입니다.

단순 접근 → 개선

배열은 중간 항목을 앞으로 옮기는 데 O(n)이 듭니다. 해시맵으로 노드를 찾고 이중 연결 리스트로 해당 노드를 O(1)에 분리·이동합니다. 더미 head 바로 뒤가 최신, tail 바로 앞이 가장 오래된 노드입니다.

보드에 이렇게 그리기

map: key → 해당 Node
head ⇄ [3,C] ⇄ [1,A] ⇄ tail
       최신       가장 오래됨
분리: prev.next = next / next.prev = prev
삽입: head와 기존 첫 노드 사이의 양쪽 연결 갱신
의사코드 보기
// Node는 key, value, prev, next를 가짐.
// 초기화: head.next=tail, tail.prev=head, map은 비어 있음.
// capacity는 0 이상. Node/head/tail은 필드.
void unlink(Node x) {
    x.prev.next = x.next;
    x.next.prev = x.prev;
}
void addFirst(Node x) {
    x.prev = head;
    x.next = head.next;
    head.next.prev = x;
    head.next = x;
}
Value get(Key key) {
    Node x = map.get(key);
    if (x == null) return null;
    unlink(x);
    addFirst(x);
    return x.value;
}
void put(Key key, Value value) {
    if (capacity == 0) return;
    Node x = map.get(key);
    if (x != null) {
        x.value = value;
        unlink(x);
        addFirst(x);
        return;
    }
    if (map.size() == capacity) {
        Node old = tail.prev;
        unlink(old);
        map.remove(old.key);
    }
    x = new Node(key, value);
    map.put(key, x);
    addFirst(x);
}

정확성 · 복잡도 · 경계 사례

map과 리스트에는 같은 항목이 정확히 한 번씩 있고, 리스트는 최근 사용 순서입니다. 접근한 노드를 맨 앞으로 보내면 이 순서를 유지하며 뒤에서 제거하면 LRU 정책을 지킵니다. 연산 평균 O(1), 공간 O(capacity). 용량 0·1, 기존 키 갱신, 없는 키 조회, 연속 축출을 검사하세요. 축출 시 map에서도 지워야 합니다.

“빠른 조회는 해시맵이, 사용 순서 변경은 이중 연결 리스트가 담당합니다. 두 구조가 항상 같은 항목을 담도록 삽입과 삭제를 함께 처리하겠습니다.”

꼬리질문: 실무에서는? 직접 구현이 요구되지 않으면 Java LinkedHashMap의 접근 순서 기능을 검토합니다. 동시성·TTL·무효화·메모리 크기 기준 축출은 별도 요구사항입니다. LRU는 교체 정책일 뿐 최신성을 보장하지 않으므로 결제 잔액이나 정산 확정 판단에 낡은 캐시를 그대로 사용하면 안 됩니다.
