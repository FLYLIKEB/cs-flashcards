### 1

Java·Spring 기반 커머스 백엔드 개발자 박지우입니다. 우아한형제들에서 B마트 전시 API를 개발하며 TPS 1,000 환경의 배너 API 응답시간을 909ms에서 18ms로 개선했고, 신규 가게홈 서버로 API 92개를 이관했습니다. 개인 프로젝트 옥화당에서는 주문·결제와 비관적 잠금 기반 재고 예약, 결제 준비 멱등 처리, 취소·환불을 구현했습니다.

제 강점은 성능 수치만 개선하는 데서 끝내지 않고 데이터가 어떻게 바뀌고 장애 시 어디를 확인할지 함께 생각한다는 점입니다. PP 팀에서도 결제부터 정산까지의 흐름을 이해하고, 정확성과 운영 안정성을 함께 높이는 개발자로 기여하고 싶습니다.

### 2

커머스에서 사용자의 행동이 실제 거래로 이어지는 과정과 그 거래가 정확하게 마무리되는 과정에 관심이 있습니다. B마트에서는 상품 전시 API의 성능과 운영 안정성을 다뤘고, 개인 프로젝트 옥화당에서는 주문·재고·결제·환불을 구현하며 거래 상태를 일관되게 유지하는 문제를 다뤘습니다.

클래스101 PP 팀은 결제에서 크리에이터의 정산과 출금까지 책임진다는 점이 매력적입니다. 제가 가진 커머스 개발 경험을 바탕으로 거래의 신뢰성을 높이고, 콘텐츠를 만드는 사람에게 결과가 정확하게 전달되는 시스템을 개발하고 싶습니다.


### 3

상품 전시에서는 사용자가 필요한 정보를 빠르게 찾도록 응답시간과 가용성을 높이는 것이 중요합니다. 데이터 종류에 따라 짧은 캐시 지연을 허용할 수도 있습니다. 반면 결제·정산에서는 같은 요청이 반복돼도 중복 청구나 중복 지급이 발생하지 않고, 금액과 상태 변경을 추적할 수 있어야 합니다.

따라서 결제·정산에서는 먼저 허용할 수 없는 상태와 금액 불일치를 정의하고 트랜잭션, 멱등성, 대사와 복구 절차를 설계하겠습니다. 두 도메인 모두 정확성과 성능이 필요하지만, 거래를 확정하는 판단을 오래된 캐시 값에 맡길 수 없다는 점에서 우선순위가 다르다고 생각합니다.

### 4

제 정규직 재직 기간은 2023년 1월부터 2024년 11월까지입니다. 공고에서 요구하는 역량은 그 기간에 맡은 문제의 범위와 해결 결과를 중심으로 설명드리고 싶습니다. TPS 1,000 환경의 성능 개선, API 92개 이관, SQL 진입점 로깅을 통한 장애 진단 개선을 경험했습니다.

이후 개인 프로젝트에서는 주문·결제·재고와 실시간 상태 관리까지 구현 범위를 넓혔습니다. 개인 프로젝트와 조직의 운영 경험이 같다고 생각하지는 않지만, 실무에서 검증한 문제 해결 방식과 직접 구현한 결과를 함께 설명하고 코드와 설계 질문으로 역량을 확인받겠습니다.

### 5

퇴사 이후에는 제가 관심을 가진 서비스를 기획부터 구현까지 이어 보며 개발의 시야를 넓히고 싶었습니다. 옥화당에서는 주문·결제와 운영 기능을, 고산운과 선립:티버스에서는 실시간 상태와 연결 복구를 다뤘습니다. 화면과 콘텐츠 제작까지 직접 맡으며 개발한 기능이 사용자에게 어떻게 전달되는지도 경험했습니다.

이제는 이런 경험을 동료의 리뷰와 조직의 운영 체계 안에서 더 깊게 발전시키고 싶습니다. 특히 결제·정산처럼 정책과 데이터 정확성이 중요한 도메인을 장기간 책임지고 개선하는 경험을 쌓고 싶습니다. 개인 프로젝트에서 넓힌 문제 인식과 커머스 실무에서 익힌 검증 방식을 함께 활용할 수 있는 곳이 PP 팀이라고 생각합니다.

### 6

이 직무와 연결해서 가장 깊게 설명할 수 있는 개인 프로젝트는 옥화당입니다. 상품·장바구니·주문·결제와 운영자 관리 화면을 개발했고, 재고 예약에는 트랜잭션과 비관적 잠금을, 결제 준비에는 멱등 처리를 적용했습니다. 취소·환불과 알림톡·SMS 연동도 담당 범위에 포함됩니다.

핵심은 주문 생성, 재고 확보, 외부 결제 확정이 서로 다른 시점에 일어난다는 점입니다. 주문이 생성됐어도 결제가 실패할 수 있고, 중복 요청이 들어와도 재고를 두 번 예약해서는 안 됩니다. 이런 상태 변화와 예외를 서비스 전체 흐름에서 생각하며, 사용자 화면과 운영자가 처리하는 기능까지 연결해 구현한 경험을 설명드릴 수 있습니다.

### 7

옥화당에서는 상품·장바구니부터 주문 생성, 재고 예약, 결제 준비, 취소·환불과 운영자 관리까지 거래를 처리하는 기능을 구현했습니다. 제 경험의 중심은 대규모 거래량을 운영한 성과보다는, 하나의 주문이 결제와 재고에 일관되게 반영되도록 기능을 연결한 데 있습니다.

운영 품질을 판단하는 기준으로는 정상 결제뿐 아니라 중복 결제 준비, 재고 부족, 승인 결과 지연, 취소·환불 이후의 상태까지 보겠습니다. 구현한 기능의 범위와 실제 거래 규모는 별개이며, 이 프로젝트는 주문·결제의 상태 모델과 동시성·멱등성 문제를 직접 다룬 경험으로 설명드리고 싶습니다.

### 8

우선 클래스101의 한 건의 결제가 어떤 기준으로 크리에이터의 정산 대상이 되는지 끝까지 따라가겠습니다. 결제 승인, 환불, 수수료·세금·공제, 정산 확정과 출금의 의미를 담당자와 맞추고, 각 상태의 원본 데이터와 책임 시스템을 확인하겠습니다.

그다음 실제 정산 사례를 계산해 보며 정상 거래와 부분 환불, 정산 후 환불 같은 예외를 익히겠습니다. 처음부터 큰 구조를 바꾸기보다 테스트와 로그를 보강하거나 누락 탐지처럼 범위가 명확한 개선부터 맡겠습니다. 주문·결제 구현 경험은 활용하되, 회계·세무 정책을 기술적인 추측으로 결정하지 않겠습니다.

### 9

zenleaf.log를 운영하며 콘텐츠 기획·제작과 사용자 반응을 직접 경험했고, 누적 조회수 600만 회와 팔로워 1만 명을 기록했습니다. 이 경험을 바탕으로 크리에이터에게는 좋은 콘텐츠를 만드는 일뿐 아니라 결과를 예측하고 이해할 수 있는 정보도 중요하다고 생각합니다.

정산 서비스에서도 금액만 보여주기보다 어떤 거래에서 어떤 공제가 발생했고 언제 출금할 수 있는지를 설명할 수 있어야 합니다. 다만 콘텐츠 운영 경험이 곧 정산 도메인 전문성은 아니므로, 실제 크리에이터 문의와 재무 담당자의 업무를 확인하며 이런 관점을 데이터와 화면 설계에 연결하겠습니다.

### 10

첫 달에는 결제·주문·정산의 상태 흐름과 정책, 데이터 모델, 배포·장애 대응 절차를 익히겠습니다. 대표 거래를 따라가며 코드와 운영 문서를 연결하고, 이해한 내용은 담당자에게 검증받겠습니다.

두 번째 달에는 테스트나 관측 지표 보강, 조회 병목 개선처럼 영향 범위가 명확한 업무를 맡아 팀의 개발·리뷰·배포 흐름을 경험하겠습니다. 세 번째 달에는 그 과정에서 확인한 문제 하나를 정책 확인부터 구현, 검증, 운영 관찰까지 책임지고 마무리하고 싶습니다. 성과 기준은 임의의 개선율보다 팀이 실제로 겪는 오류·수작업·지연을 얼마나 줄였는지로 합의하겠습니다.

### 11

사내 배너 API에서는 JPA 조회 방식과 DB 조회 순서, 캐싱 방식을 개선했고 응답시간을 909ms에서 18ms로 줄였습니다. 변경 내용을 바탕으로 병목을 해석하면, 연관 데이터의 반복 조회로 발생하는 DB 왕복과 같은 전시 정보를 요청마다 다시 읽는 비용이 함께 누적된 상황으로 설명할 수 있습니다.

진단은 요청 한 건의 SQL 호출 횟수와 소요시간을 모으고, 실행 계획과 캐시 적중 여부를 연결하는 순서로 접근하겠습니다. 전체 시간 중 DB 대기가 큰지부터 구분한 뒤 불필요한 조회를 줄이고 반복 조회를 캐시로 흡수합니다. 개선 후에는 응답시간뿐 아니라 DB 부하와 커넥션 대기도 함께 봐서 병목이 단순히 다른 곳으로 이동하지 않았는지 검증하겠습니다.

### 12

적용한 변경은 BatchSize 재설정, DB 조회 순서 조정, 캐싱 방식 개선입니다. BatchSize는 연관 데이터를 묶어 읽어 쿼리 왕복을 줄이는 역할을 하고, 조회 순서는 필요한 대상을 먼저 좁힌 뒤 상세 데이터를 읽도록 구성하는 방향입니다. 캐싱은 여러 요청이 반복 사용하는 전시 데이터의 조회 비용을 줄이는 역할을 합니다.

909ms에서 18ms로 줄어든 결과는 이 변경들을 함께 적용한 최종 성과입니다. 개별 기여도는 같은 부하에서 BatchSize 조정, 조회 흐름 변경, 캐시 적용을 순서대로 비교하는 방식으로 분리하겠습니다. 개선율을 임의로 나누기보다는 쿼리 수, DB 시간, 캐시 적중률 중 어떤 지표가 각 변경에 반응했는지로 설명하는 것이 타당합니다.

### 13

TPS 1,000 부하는 일정한 도착률로 초당 1,000건을 보내는 시나리오로 설명하겠습니다. 예시 프로토콜은 1분 동안 목표 부하까지 올리고, 워밍업을 거친 뒤 5분간 측정하며 같은 조건으로 세 차례 반복하는 구성입니다. 서버 수와 사양, 데이터와 요청 분포, DB·커넥션 설정을 고정해야 코드 변경의 효과를 비교할 수 있습니다.

캐시가 비어 있는 구간과 채워진 구간은 별도로 측정하고, 실제 성공 처리량과 오류율을 함께 기록하겠습니다. 요청 발생기가 부하를 충분히 만들었는지도 확인해야 합니다. 응답이 느려졌다고 요청 발생량까지 줄어드는 방식만 쓰면 병목이 작아 보일 수 있으므로, 목표 도착률과 완료 TPS를 구분해 해석하겠습니다.

### 14

909ms와 18ms를 평균 응답시간으로 가정하면 약 98% 단축된 결과입니다. 다만 평균은 일부 느린 요청을 가릴 수 있으므로 이것만으로 모든 사용자의 경험이 개선됐다고 판단하지 않겠습니다. 특히 실패 요청이 빠르게 종료돼 평균이 낮아지는 경우를 구분해야 합니다.

검증에서는 성공 요청의 평균과 p95·p99, 오류율, 타임아웃 수, 실제 성공 TPS를 함께 보겠습니다. p95·p99는 각각 요청의 95%·99%가 그 시간 이내에 완료됐다는 의미입니다. 같은 부하에서 평균과 꼬리 지연이 함께 개선되고 오류율도 허용 범위 안에 있어야 안정적인 성능 개선이라고 평가하겠습니다.

### 15

설계 예시로는 여러 서버가 공유할 수 있는 Redis 캐시를 두고, `banner:v1:{storeId}:{placement}:{audience}`처럼 응답을 구분하는 가게·전시 위치·노출 대상 조건을 키에 넣겠습니다. 개인화 정보는 공용 응답과 분리하고, 값에는 화면에서 필요한 배너 목록과 노출 기간을 담는 구성이 적합합니다.

TTL은 예를 들어 60초를 시작점으로 두되 다음 노출 시작·종료 시각을 넘지 않도록 제한하겠습니다. 운영자 변경이 커밋되면 관련 키를 무효화하고, 강한 최신성이 필요한 변경은 버전이 다른 키로 전환해 이전 조회가 새 값을 덮지 않도록 하겠습니다. 실제 TTL은 허용 지연과 적중률을 함께 보며 조정하는 기준입니다.

### 16

동시 만료에는 TTL에 작은 무작위 차이를 두고, 같은 키를 다시 계산하는 요청을 하나로 합쳐 원본 조회가 몰리지 않게 하겠습니다. 갱신 시간이 긴 데이터라면 미리 갱신하는 방식도 검토하겠습니다. 오래된 값을 잠시 제공하는 방법은 배너처럼 업무적으로 허용되는 데이터에만 적용하겠습니다.

캐시 장애 시에는 모든 요청을 무제한으로 DB에 넘기지 않겠습니다. 캐시 호출 타임아웃을 짧게 두고 원본 조회의 동시 실행 수와 요청량을 제한하며, 필요하면 일부 기능을 축소하겠습니다. 복구 시에도 한꺼번에 캐시를 채우지 않고 DB가 감당할 수 있는 속도로 점진적으로 회복하겠습니다.

### 17

추천 카탈로그 API는 TPS가 23% 증가하고 응답시간이 20% 단축됐습니다. 구현 세부를 추정해 설명하면, 후보 상품마다 필요한 정보를 개별 조회하는 비용과 필요 이상의 데이터를 가져와 후처리하는 비용을 줄인 사례로 구성할 수 있습니다. 후보를 먼저 좁히고 필요한 필드를 묶어 읽으면 요청당 DB 작업과 커넥션 점유를 줄일 수 있습니다.

이 가설은 동일한 요청 분포에서 쿼리 횟수·조회 시간·커넥션 대기와 응답시간을 비교해 검증하겠습니다. TPS 증가는 같은 오류율과 지연 기준을 유지하면서 더 많은 성공 요청을 처리했는지로 해석해야 합니다. 배너 API의 캐시 효과와는 구분해 이 조회 경로 자체가 줄인 비용을 설명하겠습니다.

### 18

우아한테크코스 팀 프로젝트 속닥속닥에서는 BatchSize와 fetch join을 활용해 쿼리 수를 5,000개에서 6개로 줄였습니다. 익명 커뮤니티의 목록 조회를 예로 들면, 게시글마다 작성자나 연관 정보를 개별로 불러오면 부모 조회 한 번 뒤에 추가 쿼리가 반복되는 N+1 구조가 됩니다.

필수 단건 관계는 fetch join으로 함께 읽고 컬렉션은 필요한 부모들을 묶어 배치 조회하는 방식으로 설명할 수 있습니다. 모든 관계를 한 번에 조인하면 행 수가 폭증할 수 있어 관계별로 조회 전략을 나누는 것이 핵심입니다. 쿼리 수뿐 아니라 같은 데이터의 응답 내용과 전체 처리시간을 함께 비교해야 실제 개선을 판단할 수 있습니다.

### 19

화면에 반드시 필요한 단건 연관관계라면 fetch join을 우선 검토하고, 여러 부모의 컬렉션을 읽어야 한다면 배치 조회를 검토하겠습니다. 조회 전용 화면에서 일부 필드만 필요하다면 DTO projection으로 전송량과 엔티티 로딩 비용을 줄일 수 있습니다. 선택 기준은 쿼리 개수뿐 아니라 결과 행 수와 메모리 사용량입니다.

컬렉션 fetch join에 페이지네이션을 함께 적용하면 Hibernate가 메모리에서 페이지를 자르는 상황이 생길 수 있어 피하겠습니다. 먼저 부모 ID를 안정적인 정렬로 페이지 조회한 다음 필요한 연관 데이터를 추가 조회하고, 원래 순서를 복원하는 방식을 검토하겠습니다. 실제 SQL에 제한이 적용되는지도 확인하겠습니다.

### 20

상품 전시 캐시는 조회 부하를 줄이는 데 효과적이지만, 결제나 정산을 확정할 때는 캐시를 최종 판단 근거로 사용하지 않겠습니다. 화면용 조회 캐시가 허용되더라도 승인·환불·출금 시에는 원본의 최신 상태와 금액을 트랜잭션 안에서 검증해야 합니다.

결제 진행 상태처럼 자주 바뀌는 값은 짧은 지연도 사용자 혼란을 만들 수 있으므로 캐시 필요성을 먼저 검토하겠습니다. 반대로 확정된 과거 정산 명세는 버전이 있는 조회 모델로 캐싱하기 쉽습니다. 정정이 발생하면 새 버전이나 무효화를 적용하고, 캐시가 원장이나 대사를 대체하지 않도록 경계를 두겠습니다.

### 21

옥화당에서는 주문·결제와 비관적 잠금 기반 재고 예약, 취소·환불을 구현했습니다. 상태 이름은 설명을 위해 결제 대기, 결제 완료, 취소·환불로 구분하겠습니다. 장바구니 단계는 재고를 확보하지 않고 주문 단계에서 서버가 가격과 재고를 다시 검증해 결제 대기 주문과 예약을 같은 트랜잭션으로 만드는 구성입니다.

외부 결제 승인이 확인되면 금액과 주문 정보를 검증해 결제 완료로 전환하고 예약을 확정합니다. 실패·만료 시에는 예약을 해제하되, 늦게 도착한 승인과 경쟁할 수 있으므로 현재 상태를 조건으로 변경합니다. 주문 상태와 결제 시도 상태를 분리해 결제 준비나 네트워크 타임아웃을 승인 완료·실패 확정과 혼동하지 않도록 하겠습니다.

### 22

재고 예약을 선택하는 설계 이유는 결제가 끝나기 전에도 해당 주문에 수량을 배정해 초과 판매를 막기 위해서입니다. 결제 완료 시점에만 재고를 확인하면 여러 사용자가 마지막 수량에 대해 결제한 뒤 일부를 취소해야 할 수 있습니다. 반대로 결제 대기 주문이 재고를 무기한 보유하면 다른 사용자가 구매하지 못합니다.

따라서 예를 들어 10분의 예약 유효 시간을 두고, 승인 성공 시 확정하고 실패·만료 시 해제하는 정책으로 설명하겠습니다. 실제 시간은 PG 결제 흐름과 구매 이탈에 맞춰 조정할 값입니다. 예약 확정과 해제는 한 번만 일어나야 하며, 만료와 승인 통지가 경합할 때는 실제 승인 여부를 확인해 재고 재확보나 승인 취소로 마무리하겠습니다.

### 23

옥화당에서는 비관적 잠금을 사용해 재고 예약을 구현했습니다. 선택 기준은 동일 상품의 재고 확인과 예약을 짧은 임계 구역으로 묶고, 재고 부족을 결제 준비 전에 판단할 수 있다는 점입니다. 여러 상품과 예약 기록을 함께 변경할 때 처리 순서를 명확하게 설명하기에도 적합합니다. 외부 PG 호출은 잠금을 풀고 나서 수행해야 합니다.

낙관적 잠금은 충돌이 드물면 유리하지만 인기 상품에 요청이 몰리면 재시도가 늘 수 있습니다. 단순 수량 변경이라면 `재고 >= 요청 수량` 조건의 UPDATE와 영향받은 행 수 확인도 좋은 대안입니다. 비관적 잠금이 항상 더 낫다는 뜻은 아니며, 경합 정도와 주문 트랜잭션의 복잡성을 함께 보고 선택하겠습니다.

### 24

비관적 잠금 기반의 처리에서는 재고 행을 먼저 잠근 요청이 최신 수량을 확인해 1개를 예약하고 커밋합니다. 다음 요청은 잠금을 얻은 뒤 판매 가능 수량이 0임을 확인하므로 재고 부족으로 종료합니다. 중요한 점은 잠금 전에 읽은 재고를 재사용하지 않고, 잠금 안에서 검증과 예약을 함께 수행하는 것입니다.

따라서 정상적으로 완료된 요청 중 예약 성공은 최대 한 건이어야 합니다. 나머지는 재고 부족이나 제한 시간 내 잠금 획득 실패로 응답할 수 있습니다. 동일 주문의 중복 요청은 고유 제약과 멱등 처리로 묶고, 동시성 테스트에서는 성공 건수뿐 아니라 예약 합계와 최종 판매 가능 재고까지 검증하겠습니다.

### 25

전체 주문이 함께 성공하거나 실패하는 정책으로 설명하겠습니다. 모든 주문 항목의 재고를 공통 순서로 잠그고 검사한 뒤 예약과 주문 생성을 하나의 로컬 트랜잭션으로 처리합니다. 하나라도 부족하면 예외로 전체를 롤백해 앞서 예약한 상품만 남는 상황을 막고, 부족한 항목을 사용자에게 안내합니다.

일부 상품만 구매하게 하려면 서버가 임의로 부분 성공시키기보다 새 상품 구성과 금액, 쿠폰·배송비를 계산해 사용자에게 다시 확인받는 흐름이 필요합니다. PG 호출은 재고 잠금 구간 밖에서 수행하겠습니다. 재고가 서로 다른 DB에 분산돼 있다면 로컬 롤백 대신 이미 확보한 예약을 해제하는 보상 절차가 필요합니다.

### 26

같은 상품들을 서로 다른 순서로 잠그면 순환 대기가 생길 수 있으므로 모든 코드 경로에서 상품 ID 같은 공통 기준으로 정렬한 뒤 잠그겠습니다. 필요한 행만 인덱스로 좁혀 조회하고 트랜잭션을 짧게 유지하며, 외부 API 호출은 잠금 구간 밖으로 빼겠습니다.

그래도 데드락은 발생할 수 있으므로 DB가 중단한 트랜잭션 전체를 새 트랜잭션에서 제한적으로 재시도하겠습니다. 재시도에는 짧은 지연과 무작위 차이를 두고, 주문·예약의 멱등성을 보장해야 합니다. 계속 실패하면 무한 반복하지 않고 오류를 반환하며 데드락 로그로 실제 잠금 순서와 인덱스를 점검하겠습니다.

### 27

예약 만료 처리와 결제 성공 처리가 같은 주문 상태를 동시에 바꾸지 않도록 잠금이나 조건부 상태 전이로 경쟁을 해결하겠습니다. 다만 우리 DB의 상태 변경과 외부 PG의 승인을 하나의 트랜잭션으로 묶을 수는 없으므로, DB에서 만료가 먼저 됐다는 이유만으로 실제 승인이 없었다고 판단해서는 안 됩니다.

승인이 늦게 확인되면 PG의 실제 거래와 승인 시각을 조회하고, 이미 예약이 해제됐는지와 재고를 다시 확보할 수 있는지 확인하겠습니다. 확보가 불가능하면 정책에 따라 승인 취소·환불하고, 그 처리도 멱등하게 수행하겠습니다. 미확정 건은 별도 상태와 재조정 작업으로 끝까지 추적하겠습니다.

### 28

MySQL InnoDB의 REPEATABLE READ를 사용하는 구성으로 가정하겠습니다. 일반적인 일관 읽기는 트랜잭션의 스냅샷을 보지만, `SELECT ... FOR UPDATE` 같은 잠금 조회는 최신 변경 상태를 대상으로 잠금을 얻는다는 차이가 있습니다. 그래서 일반 조회의 수량을 읽은 뒤 별도로 갱신하는 방식만으로는 재고 경쟁을 해결할 수 없습니다.

재고 행을 잠근 상태에서 판매 가능 수량을 검증하고 예약을 반영하거나, 조건부 UPDATE로 검증과 변경을 합치겠습니다. 범위 잠금은 인덱스와 조회 조건에 따라 넓어질 수 있어 대기·데드락도 살펴야 합니다. READ COMMITTED에서는 문장별로 보이는 값이 달라질 수 있지만, 어떤 격리 수준이든 업무 불변 조건을 직접 보장하는 것이 핵심입니다.

### 29

Spring의 기본 프록시 방식에서는 같은 객체 안의 직접 호출이 프록시를 거치지 않으므로 내부 메서드의 `@Transactional` 설정이 새로 적용되지 않을 수 있습니다. 외부에서 시작한 트랜잭션이 없어지는 것은 아닙니다. 예를 들어 같은 클래스의 내부 메서드에 REQUIRES_NEW를 붙여도 직접 호출하면 기대한 새 트랜잭션이 만들어지지 않습니다.

주문 서비스를 Spring으로 구성하는 예시라면 트랜잭션이 필요한 예약 처리를 별도 빈으로 분리해 프록시를 통하게 하겠습니다. 기본 롤백 대상은 RuntimeException과 Error이며 체크 예외는 `rollbackFor` 등으로 정책을 명시합니다. 예외를 잡고 정상 반환하는 경우와 비동기 스레드에 트랜잭션이 자동 전파되지 않는 경우도 함께 테스트하겠습니다.

### 30

서비스마다 DB가 분리되면 전체를 하나의 로컬 트랜잭션으로 되돌릴 수 없습니다. 주문 서비스가 진행 상태를 관리하면서 재고 예약, 결제, 주문 확정 단계를 수행하고, 실패 시 예약 해제나 결제 취소 같은 보상 작업을 실행하는 Saga 방식을 검토하겠습니다. 각 단계는 중복 실행돼도 같은 결과가 되도록 멱등해야 합니다.

DB 변경과 이벤트 발행 사이의 유실은 트랜잭셔널 아웃박스로 줄이고, 소비자는 이벤트 중복과 순서 역전에 대응해야 합니다. 타임아웃은 실패 확정이 아니라 결과 미확정일 수 있으므로 조회·재조정을 거치겠습니다. 보상까지 실패한 거래도 추적 가능한 상태로 남겨 자동 재시도와 운영자 복구가 가능하게 하겠습니다.
