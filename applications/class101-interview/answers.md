## 1. 지원 동기·경력·직무 적합성

### 1. 본인의 경력 중 클래스101 PP 팀과 가장 밀접하게 연결되는 경험을 중심으로 자기소개해 주세요.

Java·Spring 기반 커머스 백엔드 개발자 박지우입니다. 우아한형제들에서 B마트 전시 API를 개발하며 TPS 1,000 환경의 배너 API 응답시간을 909ms에서 18ms로 개선했고, 신규 가게홈 서버로 API 92개를 이관했습니다. 개인 프로젝트 옥화당에서는 주문·결제와 비관적 잠금 기반 재고 예약, 결제 준비 멱등 처리, 취소·환불을 구현했습니다.

제 강점은 성능 수치만 개선하는 데서 끝내지 않고 데이터가 어떻게 바뀌고 장애 시 어디를 확인할지 함께 생각한다는 점입니다. PP 팀에서도 결제부터 정산까지의 흐름을 이해하고, 정확성과 운영 안정성을 함께 높이는 개발자로 기여하고 싶습니다.

### 2. 커머스 백엔드 경험을 바탕으로 클래스101의 결제·주문·정산 업무에 지원한 이유는 무엇인가요?

커머스에서 사용자의 행동이 실제 거래로 이어지는 과정과 그 거래가 정확하게 마무리되는 과정에 관심이 있습니다. B마트에서는 상품 전시 API의 성능과 운영 안정성을 다뤘고, 개인 프로젝트 옥화당에서는 주문·재고·결제·환불을 구현하며 거래 상태를 일관되게 유지하는 문제를 다뤘습니다.

클래스101 PP 팀은 결제에서 크리에이터의 정산과 출금까지 책임진다는 점이 매력적입니다. 제가 가진 커머스 개발 경험을 바탕으로 거래의 신뢰성을 높이고, 콘텐츠를 만드는 사람에게 결과가 정확하게 전달되는 시스템을 개발하고 싶습니다.

> 확인 메모: 지원 동기는 경력과 공고를 연결한 제안 문안입니다. 실제 지원 계기와 관심사에 맞는지 확인한 뒤 사용하세요.

### 3. B마트 상품 전시 도메인과 결제·정산 도메인은 개발 시 우선순위가 어떻게 다르다고 생각하나요?

상품 전시에서는 사용자가 필요한 정보를 빠르게 찾도록 응답시간과 가용성을 높이는 것이 중요합니다. 데이터 종류에 따라 짧은 캐시 지연을 허용할 수도 있습니다. 반면 결제·정산에서는 같은 요청이 반복돼도 중복 청구나 중복 지급이 발생하지 않고, 금액과 상태 변경을 추적할 수 있어야 합니다.

따라서 결제·정산에서는 먼저 허용할 수 없는 상태와 금액 불일치를 정의하고 트랜잭션, 멱등성, 대사와 복구 절차를 설계하겠습니다. 두 도메인 모두 정확성과 성능이 필요하지만, 거래를 확정하는 판단을 오래된 캐시 값에 맡길 수 없다는 점에서 우선순위가 다르다고 생각합니다.

### 4. 공고의 ‘경력 3년 이상 또는 그에 준하는 역량’을 어떤 경험과 결과로 설명할 수 있나요?

제 정규직 재직 기간은 2023년 1월부터 2024년 11월까지입니다. 공고에서 요구하는 역량은 그 기간에 맡은 문제의 범위와 해결 결과를 중심으로 설명드리고 싶습니다. TPS 1,000 환경의 성능 개선, API 92개 이관, SQL 진입점 로깅을 통한 장애 진단 개선을 경험했습니다.

이후 개인 프로젝트에서는 주문·결제·재고와 실시간 상태 관리까지 구현 범위를 넓혔습니다. 개인 프로젝트와 조직의 운영 경험이 같다고 생각하지는 않지만, 실무에서 검증한 문제 해결 방식과 직접 구현한 결과를 함께 설명하고 코드와 설계 질문으로 역량을 확인받겠습니다.

### 5. 우아한형제들 퇴사 이후 개인 프로젝트를 진행한 배경과, 다시 조직에서 일하려는 이유는 무엇인가요?

퇴사 이후에는 개인 프로젝트를 통해 상품·주문·결제부터 사용자 화면과 콘텐츠 제작까지 서비스의 여러 부분을 직접 다뤘습니다. 옥화당에서는 커머스 기능을, 고산운과 선립:티버스에서는 실시간 상태와 연결 복구를 구현했습니다. 기능을 만드는 것뿐 아니라 이용자가 접하는 흐름까지 생각할 수 있는 경험이었습니다.

앞으로는 이런 경험을 바탕으로 동료와 설계를 검토하고 장기간 운영하며 한 도메인의 깊이를 쌓고 싶습니다. 특히 PP 팀에서 정책과 데이터 정확성이 함께 중요한 거래 시스템을 다루며, 개인의 판단을 팀의 검증과 운영 체계 안에서 발전시키고 싶습니다.

> 확인 메모: 실제 퇴사 사유는 제공되지 않았으므로 만들지 않았습니다. 첫 문단 앞에 본인의 실제 사유를 짧게 설명하고, 재취업 동기 역시 본인의 생각과 일치하는지 확인하세요.

### 6. 여러 개인 프로젝트 중 기술적으로 가장 깊게 관여한 프로젝트는 무엇이며, 직접 구현한 범위는 어디까지인가요?

이 직무와 연결해서 가장 구체적으로 설명할 수 있는 개인 프로젝트는 옥화당입니다. 상품·장바구니·주문·결제와 운영자 관리 화면을 개발했고, 재고 예약에는 트랜잭션과 비관적 잠금을, 결제 준비에는 멱등 처리를 적용했습니다. 취소·환불과 알림톡·SMS 연동도 구현 범위에 포함됩니다.

특히 주문이 만들어지는 시점, 재고를 확보하는 시점, 외부 결제가 확정되는 시점이 다르다는 문제를 중심으로 설명하고 싶습니다. 단순히 API 개수를 나열하기보다 각 단계의 성공·실패가 다음 상태에 어떤 영향을 주는지, 제가 구현한 코드의 경계를 보여드리겠습니다.

> 확인 메모: ‘가장 깊게 관여한 프로젝트’로 옥화당을 선택한 제안입니다. 협업 여부, 기존 코드와 직접 작성한 부분의 경계는 실제 저장소를 기준으로 확인하세요.

### 7. 개인 프로젝트에서 개발한 주문·결제 기능은 실제 사용자와 거래를 대상으로 어느 수준까지 운영했나요?

제가 구체적으로 말씀드릴 수 있는 범위는 옥화당의 상품·장바구니·주문·결제, 재고 예약, 결제 준비 멱등 처리와 취소·환불 기능을 구현했다는 점입니다. 다만 기능 구현 여부와 실제 운영 규모는 나눠서 설명하겠습니다. 결제 연동이 있다는 이유만으로 대규모 실거래 운영 경험이라고 표현하지 않겠습니다.

운영 경험을 설명할 때는 테스트 결제와 실거래를 구분하고, 실제 결제·취소·환불 처리 내역과 제가 대응한 운영 이슈를 근거로 제시하겠습니다. 거래 건수와 운영 기간은 확인된 수치만 사용하고, 구현한 예외 처리와 실제 발생했던 장애도 구분하겠습니다.

> 확인 메모: 실거래 건수, 운영 기간, 매출, 실제 장애 대응 내역은 이력서에 없습니다. 면접 전 운영 기록에서 확인해야 하며 임의의 숫자를 덧붙이지 마세요.

우선 클래스101의 한 건의 결제가 어떤 기준으로 크리에이터의 정산 대상이 되는지 끝까지 따라가겠습니다. 결제 승인, 환불, 수수료·세금·공제, 정산 확정과 출금의 의미를 담당자와 맞추고, 각 상태의 원본 데이터와 책임 시스템을 확인하겠습니다.

그다음 실제 정산 사례를 계산해 보며 정상 거래와 부분 환불, 정산 후 환불 같은 예외를 익히겠습니다. 처음부터 큰 구조를 바꾸기보다 테스트와 로그를 보강하거나 누락 탐지처럼 범위가 명확한 개선부터 맡겠습니다. 주문·결제 구현 경험은 활용하되, 회계·세무 정책을 기술적인 추측으로 결정하지 않겠습니다.

zenleaf.log를 운영하며 콘텐츠 기획·제작과 사용자 반응을 직접 경험했고, 누적 조회수 600만 회와 팔로워 1만 명을 기록했습니다. 이 경험을 바탕으로 크리에이터에게는 좋은 콘텐츠를 만드는 일뿐 아니라 결과를 예측하고 이해할 수 있는 정보도 중요하다고 생각합니다.

정산 서비스에서도 금액만 보여주기보다 어떤 거래에서 어떤 공제가 발생했고 언제 출금할 수 있는지를 설명할 수 있어야 합니다. 다만 콘텐츠 운영 경험이 곧 정산 도메인 전문성은 아니므로, 실제 크리에이터 문의와 재무 담당자의 업무를 확인하며 이런 관점을 데이터와 화면 설계에 연결하겠습니다.

### 10. PP 팀에 합류한 첫 3개월 동안 어떤 방식으로 도메인을 익히고 기여하겠나요?

첫 달에는 결제·주문·정산의 상태 흐름과 정책, 데이터 모델, 배포·장애 대응 절차를 익히겠습니다. 대표 거래를 따라가며 코드와 운영 문서를 연결하고, 이해한 내용은 담당자에게 검증받겠습니다.

두 번째 달에는 테스트나 관측 지표 보강, 조회 병목 개선처럼 영향 범위가 명확한 업무를 맡아 팀의 개발·리뷰·배포 흐름을 경험하겠습니다. 세 번째 달에는 그 과정에서 확인한 문제 하나를 정책 확인부터 구현, 검증, 운영 관찰까지 책임지고 마무리하고 싶습니다. 성과 기준은 임의의 개선율보다 팀이 실제로 겪는 오류·수작업·지연을 얼마나 줄였는지로 합의하겠습니다.

## 2. 성능 최적화·JPA·캐싱

### 11. B마트 배너 API의 응답시간이 909ms였던 핵심 원인은 무엇이었으며, 어떻게 찾아냈나요?

사내 배너 API에서는 JPA 조회 방식과 DB 조회 순서, 캐싱 방식을 개선했고 응답시간을 909ms에서 18ms로 줄였습니다. 개선한 축은 확인되지만, 전체 지연을 하나의 원인 때문이라고 단정하지는 않겠습니다. 쿼리 호출 횟수, 각 조회의 시간, 캐시 적중 여부와 애플리케이션 처리 시간을 나눠 봐야 병목을 정확히 설명할 수 있습니다.

같은 문제를 다시 진단한다면 요청 하나의 SQL 흐름과 실행 계획부터 확인하고, 반복 조회나 불필요한 조회 범위를 좁힌 뒤 캐시 적용 구간을 검토하겠습니다. 전체 응답시간과 DB 부하가 함께 줄었는지 비교해 병목이 다른 곳으로 옮겨가지 않았는지도 확인하겠습니다.

> 확인 메모: 당시 지연의 원인별 비중, 실행 계획과 진단 도구는 원본 자료로 보완하세요. 이 답변의 진단 절차는 재현 시 접근법이며 당시 수행 사실을 추가로 단정한 것이 아닙니다.

### 12. 배너 API 응답시간을 18ms로 개선하기 위해 적용한 변경 사항과 각각의 기여도를 설명해 주세요.

확인되는 변경은 BatchSize 재설정, DB 조회 순서 조정, 캐싱 방식 개선입니다. BatchSize 조정은 필요한 연관 데이터를 묶어 가져와 왕복 횟수를 줄이는 데, 조회 순서 조정은 뒤에서 필요하지 않을 데이터를 먼저 읽는 낭비를 줄이는 데 의미가 있습니다. 캐싱은 반복 계산과 조회를 줄이는 방향입니다.

다만 최종 응답시간 개선을 세 변경에 임의의 비율로 나누지는 않겠습니다. 각각의 기여도를 입증하려면 같은 데이터와 부하에서 변경을 하나씩 적용한 결과가 필요합니다. 당시 단계별 결과가 없다면 909ms에서 18ms로 줄어든 값은 여러 변경을 함께 적용한 최종 결과라고 설명하겠습니다.

> 확인 메모: 실제 변경 전후 BatchSize 값, 조회 순서, 캐시 대상과 개별 측정값은 확인이 필요합니다. 일반적인 최적화 효과를 당시 코드의 세부 동작으로 오인하지 않도록 구분하세요.

### 13. TPS 1,000이라는 부하 조건은 어떻게 만들었으며, 개선 전후의 데이터·인프라·캐시 조건은 같았나요?

이력서에 기록한 조건은 TPS 1,000 환경입니다. 정확한 비교를 위해서는 목표로 보낸 요청량과 실제 성공 처리량부터 구분해야 합니다. 같은 데이터, 요청 비율, 인프라와 실행 시간을 유지하고 워밍업 구간을 제외한 뒤 응답시간과 오류율을 함께 비교해야 합니다.

특히 캐시를 개선한 작업이므로 캐시가 비어 있는 구간과 충분히 채워진 구간을 나눠 보는 것이 필요합니다. 반복 실행 결과와 DB·CPU·커넥션 사용량도 함께 제시하겠습니다. 당시 부하 설정과 환경 기록을 확인한 범위까지만 동일 조건이라고 설명하고, 목표 TPS만으로 실제 처리량을 대신하지 않겠습니다.

> 확인 메모: 부하 도구, 동시 사용자 수, 요청 모델, 실행 시간과 캐시 워밍업 조건은 제공되지 않았습니다. 속닥속닥에서 사용한 nGrinder를 B마트에서도 사용했다고 추정하지 마세요.

### 14. 909ms와 18ms는 평균값인가요, 특정 백분위 지연시간인가요? 오류율과 p95·p99는 어떻게 달라졌나요?

909ms와 18ms는 이력서에 기록된 응답시간이지만, 평균인지 특정 백분위인지까지는 원본 측정 자료로 확인해 설명하겠습니다. 평균만 낮아졌어도 일부 요청이 오래 걸리거나 실패 요청이 빠르게 종료됐다면 사용자 경험이 좋아졌다고 단정할 수 없습니다.

따라서 성공 요청 기준의 평균과 p95·p99, 오류율, 타임아웃 수, 실제 처리량을 함께 보겠습니다. 같은 부하에서 꼬리 지연과 오류가 악화되지 않았는지 확인해야 개선이 유효합니다. 기록이 없는 p95·p99 수치를 새로 만들어 말하기보다, 확인된 지표와 추가 검증이 필요한 지표를 구분하겠습니다.

> 확인 메모: 909ms·18ms의 집계 방식과 당시 오류율·p95·p99는 미확인입니다. 면접 전 부하 테스트 보고서에서 확인하세요.

### 15. 배너 API에 사용한 캐시의 저장 위치, 키, 만료 시간과 무효화 정책은 어떻게 정했나요?

배너 API에서 캐싱 방식을 개선한 경험은 있지만, 당시 저장소와 키 구성, 만료 시간을 기억에 의존해 단정하지 않겠습니다. 설계 기준으로는 응답을 달라지게 만드는 가게·전시 위치·사용자 조건이 있다면 키에 반영하고, 개인화 데이터를 공용 캐시로 섞지 않는 것이 먼저입니다.

만료 시간은 허용 가능한 정보 지연과 변경 빈도로 정하겠습니다. 운영자가 배너를 바꾸거나 노출 시간이 종료됐을 때의 반영 정책도 필요합니다. 갱신 시 무효화와 TTL을 함께 검토하되, 지연된 조회가 오래된 값을 다시 채우는 경쟁까지 고려하고 캐시 적중률과 실제 최신성으로 검증하겠습니다.

> 확인 메모: 실제 사용한 Redis·로컬 캐시 여부, 키, TTL, 무효화 구현은 자료에 없습니다. 위 내용은 선택 기준이며 당시 설정값을 뜻하지 않습니다.

### 16. 캐시가 동시에 만료되거나 캐시 서버가 장애를 일으키면 원본 데이터베이스를 어떻게 보호하겠나요?

동시 만료에는 TTL에 작은 무작위 차이를 두고, 같은 키를 다시 계산하는 요청을 하나로 합쳐 원본 조회가 몰리지 않게 하겠습니다. 갱신 시간이 긴 데이터라면 미리 갱신하는 방식도 검토하겠습니다. 오래된 값을 잠시 제공하는 방법은 배너처럼 업무적으로 허용되는 데이터에만 적용하겠습니다.

캐시 장애 시에는 모든 요청을 무제한으로 DB에 넘기지 않겠습니다. 캐시 호출 타임아웃을 짧게 두고 원본 조회의 동시 실행 수와 요청량을 제한하며, 필요하면 일부 기능을 축소하겠습니다. 복구 시에도 한꺼번에 캐시를 채우지 않고 DB가 감당할 수 있는 속도로 점진적으로 회복하겠습니다.

### 17. 추천 카탈로그 API의 TPS 23% 증가와 응답시간 20% 단축은 어떤 병목을 해결한 결과인가요?

추천 카탈로그 API에서는 TPS 23% 증가와 응답시간 20% 단축이라는 개선 결과가 있습니다. 다만 배너 API에서 사용한 변경 사항을 이 작업에도 그대로 적용했다고 섞어서 설명하지 않겠습니다. 구체적인 병목은 당시 변경 코드와 쿼리, 부하 테스트 결과를 연결해 설명해야 합니다.

검증할 때는 같은 요청 구성을 유지한 채 조회 횟수와 시간, 애플리케이션 처리 시간, 커넥션 대기 중 무엇이 줄었는지 보겠습니다. TPS가 늘었다는 결과만으로 CPU 병목이 해결됐다고 판단하지 않고, 응답시간과 오류율이 허용 범위를 유지한 상태의 성공 처리량인지 확인하겠습니다.

> 확인 메모: 추천 카탈로그의 구체적인 변경 내용과 병목 근거가 현재 자료에는 없습니다. 배너 API 개선과 다른 사례이므로 관련 PR 또는 측정 기록을 확인하세요.

### 18. 속닥속닥에서 쿼리 수를 5,000개에서 6개로 줄인 조회 구조와 개선 방법을 설명해 주세요.

우아한테크코스 팀 프로젝트 속닥속닥에서는 BatchSize와 fetch join을 활용해 쿼리 수를 5,000개에서 6개로 줄였습니다. 연관 데이터를 순회하면서 필요한 시점마다 개별 조회하는 구조에서는 조회 대상 수에 비례해 쿼리가 늘어날 수 있습니다. 필요한 관계를 함께 가져오거나 묶어서 조회해 DB 왕복을 줄이는 방식으로 접근했습니다.

다만 쿼리 수만 줄이는 것이 목표는 아닙니다. 여러 컬렉션을 한꺼번에 조인해 결과 행이 폭증하거나 메모리 사용량이 늘면 오히려 손해일 수 있습니다. 어떤 관계를 조인하고 어떤 관계를 배치 조회할지 구분하고, 같은 데이터에서 결과의 정확성과 응답시간도 함께 확인하는 것이 중요합니다.

> 확인 메모: 5,000개·6개의 측정 대상 API, 데이터 건수, 관계 매핑과 배치 크기는 원본 자료로 보완하세요.

### 19. 컬렉션 조회에서 fetch join, 배치 조회, DTO projection을 어떤 기준으로 선택하나요? 페이지네이션이 있으면 판단이 달라지나요?

화면에 반드시 필요한 단건 연관관계라면 fetch join을 우선 검토하고, 여러 부모의 컬렉션을 읽어야 한다면 배치 조회를 검토하겠습니다. 조회 전용 화면에서 일부 필드만 필요하다면 DTO projection으로 전송량과 엔티티 로딩 비용을 줄일 수 있습니다. 선택 기준은 쿼리 개수뿐 아니라 결과 행 수와 메모리 사용량입니다.

컬렉션 fetch join에 페이지네이션을 함께 적용하면 Hibernate가 메모리에서 페이지를 자르는 상황이 생길 수 있어 피하겠습니다. 먼저 부모 ID를 안정적인 정렬로 페이지 조회한 다음 필요한 연관 데이터를 추가 조회하고, 원래 순서를 복원하는 방식을 검토하겠습니다. 실제 SQL에 제한이 적용되는지도 확인하겠습니다.

### 20. 상품 전시 API에서 효과적이었던 캐싱을 결제 상태나 정산 금액 조회에 적용한다면 어떤 제약을 두겠나요?

상품 전시 캐시는 조회 부하를 줄이는 데 효과적이지만, 결제나 정산을 확정할 때는 캐시를 최종 판단 근거로 사용하지 않겠습니다. 화면용 조회 캐시가 허용되더라도 승인·환불·출금 시에는 원본의 최신 상태와 금액을 트랜잭션 안에서 검증해야 합니다.

결제 진행 상태처럼 자주 바뀌는 값은 짧은 지연도 사용자 혼란을 만들 수 있으므로 캐시 필요성을 먼저 검토하겠습니다. 반대로 확정된 과거 정산 명세는 버전이 있는 조회 모델로 캐싱하기 쉽습니다. 정정이 발생하면 새 버전이나 무효화를 적용하고, 캐시가 원장이나 대사를 대체하지 않도록 경계를 두겠습니다.

## 3. 주문·재고·트랜잭션·동시성

### 21. 옥화당에서 장바구니부터 주문 생성, 재고 예약, 결제 완료까지의 상태 전이를 설명해 주세요.

옥화당에서는 주문·결제와 트랜잭션·비관적 잠금 기반 재고 예약, 취소·환불을 구현했습니다. 이 흐름을 설계한다면 장바구니 자체는 재고 확보를 보장하지 않고, 주문 시 서버에서 가격과 재고를 다시 검증해 결제 대기 주문과 예약을 함께 만들겠습니다.

이후 외부 결제 결과를 확인해 주문을 결제 완료로 전환하고 예약을 확정하겠습니다. 결제 실패나 만료 시에는 예약을 해제하되, 늦게 도착한 승인과 경합할 수 있으므로 상태 조건을 확인해야 합니다. 주문 상태와 결제 시도 상태는 구분하고, 결제 준비가 곧 승인 완료를 의미하지 않도록 하겠습니다.

> 확인 메모: 구현 기능은 이력서로 확인되지만 실제 상태 이름, 예약 생성 시점과 만료 정책은 코드 확인이 필요합니다. 두 번째 문장 이후는 설명을 위한 권장 상태 흐름입니다.

### 22. 재고를 결제 완료 시점에 차감하지 않고 예약하는 구조를 선택한 이유는 무엇인가요?

재고 예약의 의미는 외부 결제가 끝나기 전에도 해당 주문에 수량을 일시적으로 배정하는 것입니다. 결제 완료 시점에만 재고를 확인하면 여러 사용자가 같은 마지막 수량에 대해 결제를 진행한 뒤 일부 승인을 취소해야 할 수 있습니다. 반대로 결제 대기 주문을 무기한 보유하면 다른 고객의 구매 기회를 막습니다.

그래서 예약을 사용한다면 유효 시간을 정하고 승인 성공 시 확정, 실패·만료 시 해제하는 흐름을 함께 설계하겠습니다. 판매 가능 수량과 예약 수량의 의미도 명확히 해야 합니다. 예약만 추가하는 것이 아니라 중복 해제와 늦은 승인까지 처리할 수 있어야 안전한 방식이라고 생각합니다.

> 확인 메모: 옥화당의 재고 예약 사용은 확인됩니다. 실제 도입 배경과 예약 시간은 미확인이므로 위 설계 이유가 본인의 선택 이유와 일치하는지 확인하세요.

### 23. 재고 예약에 비관적 잠금을 선택한 이유는 무엇이며, 낙관적 잠금이나 조건부 UPDATE와 비교했나요?

옥화당에서는 비관적 잠금을 사용해 재고 예약을 구현했습니다. 비관적 잠금은 동일 재고를 검사하고 변경하는 짧은 구간을 직렬화해, 먼저 읽은 수량을 여러 요청이 동시에 사용하는 문제를 막는 데 적합합니다. 대신 잠금 대기와 데드락 비용이 있으므로 외부 결제 호출 동안 잠금을 유지해서는 안 됩니다.

대안으로 충돌이 드물면 버전 기반 낙관적 잠금과 제한된 재시도를, 단순 수량 차감이면 재고가 충분할 때만 변경하는 조건부 UPDATE를 검토하겠습니다. 조건부 UPDATE는 영향받은 행 수로 성공 여부를 판단할 수 있습니다. 여러 상품과 예약 기록을 함께 다뤄야 하는지에 따라 전체 트랜잭션 구조까지 비교하겠습니다.

> 확인 메모: 당시 낙관적 잠금·조건부 UPDATE를 실제로 비교하거나 벤치마크한 기록은 없습니다. 비교 내용은 설계 지식이며 과거 수행 사실로 말하지 마세요.

### 24. 재고가 1개 남은 상품에 주문 요청 100개가 동시에 들어오면, 구현한 시스템은 어떻게 처리하나요?

비관적 잠금 기반으로 재고 확인과 예약을 같은 트랜잭션에서 처리한다면, 재고 행의 잠금을 획득한 요청이 수량을 다시 확인하고 먼저 예약합니다. 그 요청이 커밋한 뒤 다음 요청은 남은 판매 가능 수량이 0임을 확인해 재고 부족으로 종료해야 합니다. 잠금을 얻기 전에 읽은 값을 그대로 사용하면 안전하지 않습니다.

동일 주문의 중복 요청은 예약을 추가로 만들지 않도록 고유 제약이나 멱등 처리가 필요합니다. 또 100개 요청 중 잠금 타임아웃으로 끝나는 요청도 있을 수 있어, 모두 즉시 재고 부족으로 응답한다고 단정하지 않겠습니다. 예약 합계가 재고를 넘지 않는지를 동시성 테스트로 검증하겠습니다.

> 확인 메모: 이력서의 잠금 기반 구현에 대한 기대 동작입니다. 재고 1개·요청 100개 조건의 실제 테스트 결과와 타임아웃 정책은 확인이 필요합니다.

### 25. 여러 상품이 포함된 주문에서 일부 상품의 재고만 부족하면 트랜잭션과 예약 상태를 어떻게 처리하나요?

주문 전체를 한 번에 성립시키는 정책이라면, 주문 항목의 재고 확인과 예약을 하나의 로컬 트랜잭션으로 묶겠습니다. 어떤 상품이라도 부족하면 예외를 발생시켜 앞서 만든 예약과 주문 변경을 함께 롤백하고, 어떤 항목이 부족한지 사용자에게 안내하겠습니다. 외부 PG 호출은 이 잠금 구간에서 수행하지 않겠습니다.

일부 상품만 주문할 수 있는 정책이라면 기술적으로 일부만 커밋하기 전에 금액·쿠폰·배송비 재계산과 사용자 동의를 먼저 정의해야 합니다. 서로 다른 DB에 분산된 경우에는 단일 롤백이 되지 않으므로 예약 취소 같은 보상 절차가 별도로 필요합니다.

> 확인 메모: 옥화당이 전체 실패와 부분 주문 중 어떤 정책을 사용하는지는 실제 주문 코드와 정책 확인이 필요합니다. 이 답변은 전체 주문 원자성을 전제로 한 설계안입니다.

### 26. 여러 상품의 재고를 잠글 때 발생할 수 있는 데드락을 어떻게 예방하고 재시도하겠나요?

같은 상품들을 서로 다른 순서로 잠그면 순환 대기가 생길 수 있으므로 모든 코드 경로에서 상품 ID 같은 공통 기준으로 정렬한 뒤 잠그겠습니다. 필요한 행만 인덱스로 좁혀 조회하고 트랜잭션을 짧게 유지하며, 외부 API 호출은 잠금 구간 밖으로 빼겠습니다.

그래도 데드락은 발생할 수 있으므로 DB가 중단한 트랜잭션 전체를 새 트랜잭션에서 제한적으로 재시도하겠습니다. 재시도에는 짧은 지연과 무작위 차이를 두고, 주문·예약의 멱등성을 보장해야 합니다. 계속 실패하면 무한 반복하지 않고 오류를 반환하며 데드락 로그로 실제 잠금 순서와 인덱스를 점검하겠습니다.

### 27. 재고 예약이 만료되는 순간 결제 성공 통지가 도착하면 어떤 기준으로 주문 상태를 결정하겠나요?

예약 만료 처리와 결제 성공 처리가 같은 주문 상태를 동시에 바꾸지 않도록 잠금이나 조건부 상태 전이로 경쟁을 해결하겠습니다. 다만 우리 DB의 상태 변경과 외부 PG의 승인을 하나의 트랜잭션으로 묶을 수는 없으므로, DB에서 만료가 먼저 됐다는 이유만으로 실제 승인이 없었다고 판단해서는 안 됩니다.

승인이 늦게 확인되면 PG의 실제 거래와 승인 시각을 조회하고, 이미 예약이 해제됐는지와 재고를 다시 확보할 수 있는지 확인하겠습니다. 확보가 불가능하면 정책에 따라 승인 취소·환불하고, 그 처리도 멱등하게 수행하겠습니다. 미확정 건은 별도 상태와 재조정 작업으로 끝까지 추적하겠습니다.

### 28. 주문 처리에서 사용한 트랜잭션 격리 수준은 무엇이며, 그 수준에서 발생할 수 있는 이상 현상은 무엇인가요?

옥화당에서 사용한 격리 수준은 실제 데이터소스와 세션 설정을 확인해 답하겠습니다. MySQL을 사용했다는 사실만으로 기본값이 그대로 적용됐다고 단정하지 않겠습니다. 격리 수준과 재고 보호 방식도 구분해야 합니다. 일반 조회가 일관된 스냅샷을 읽는다고 해서 재고 검사와 변경의 경쟁까지 해결되는 것은 아닙니다.

예를 들어 READ COMMITTED에서는 반복 조회 결과가 달라질 수 있고, InnoDB의 REPEATABLE READ에서는 일반 스냅샷 조회와 잠금 조회의 읽기 의미가 다릅니다. 범위 잠금과 인덱스에 따라 잠금 범위도 달라질 수 있습니다. 재고의 핵심 불변 조건은 적절한 잠금이나 원자적 조건부 갱신으로 보장하고 실제 동시 실행으로 확인하겠습니다.

> 확인 메모: 당시 격리 수준과 세션 설정은 미확인입니다. 특정 격리 수준에서 발생한 장애 경험을 추가로 만들어 말하지 마세요.

### 29. Spring의 `@Transactional`이 기대대로 동작하지 않는 대표적인 상황을 본인의 코드 사례와 연결해 설명해 주세요.

Spring의 기본 프록시 방식에서는 같은 객체 안에서 메서드를 직접 호출하면 프록시를 거치지 않아 내부 메서드의 `@Transactional` 설정이 새로 적용되지 않을 수 있습니다. 외부 호출에서 이미 시작한 트랜잭션까지 없어지는 것은 아닙니다. 또한 기본적으로 RuntimeException과 Error는 롤백 대상이지만 체크 예외는 별도 설정이 필요하고, 예외를 잡아서 정상 반환하면 의도한 롤백이 일어나지 않을 수 있습니다.

주문 서비스를 예로 들면 예약 메서드를 별도 빈의 트랜잭션 경계로 두고, 재고 부족 예외가 경계 밖까지 전달되는지 확인하겠습니다. 비동기 스레드로 기존 트랜잭션이 자동 전달되지 않는 점도 확인해야 합니다. 옥화당은 NestJS·TypeORM 프로젝트이므로 이를 Spring에서 직접 겪은 사례라고 섞어 설명하지 않겠습니다.

> 확인 메모: 설명은 Spring 실무 지식과 가상 주문 예시입니다. 본인이 겪은 구체적인 프록시 우회·롤백 장애 사례는 제공된 자료에 없습니다.

### 30. 주문·결제·재고가 서로 다른 서비스와 데이터베이스로 분리된다면, 부분 실패를 어떻게 처리하겠나요?

서비스마다 DB가 분리되면 전체를 하나의 로컬 트랜잭션으로 되돌릴 수 없습니다. 주문 서비스가 진행 상태를 관리하면서 재고 예약, 결제, 주문 확정 단계를 수행하고, 실패 시 예약 해제나 결제 취소 같은 보상 작업을 실행하는 Saga 방식을 검토하겠습니다. 각 단계는 중복 실행돼도 같은 결과가 되도록 멱등해야 합니다.

DB 변경과 이벤트 발행 사이의 유실은 트랜잭셔널 아웃박스로 줄이고, 소비자는 이벤트 중복과 순서 역전에 대응해야 합니다. 타임아웃은 실패 확정이 아니라 결과 미확정일 수 있으므로 조회·재조정을 거치겠습니다. 보상까지 실패한 거래도 추적 가능한 상태로 남겨 자동 재시도와 운영자 복구가 가능하게 하겠습니다.

## 4. 결제·멱등성·취소·환불

### 31. 옥화당의 결제 준비 멱등 처리는 어떤 중복 요청을 막기 위한 것이며, 멱등 키는 어떻게 만들었나요?

개인 프로젝트 옥화당에서는 결제 준비 단계의 멱등 처리를 구현했습니다. 이 단계에서 막아야 하는 것은 사용자의 연속 클릭이나 통신 재시도로 같은 구매 의도에 대한 주문·결제 준비 데이터가 중복 생성되는 상황입니다. 키를 설계한다면 고객과 결제 준비 작업의 범위 안에서 하나의 구매 시도를 식별하도록 만들고, 재시도에는 같은 키를 사용하겠습니다. 주문 내용이 바뀌거나 사용자가 새 결제를 시작하면 새 시도로 구분하고, 키와 요청 내용의 해시·처리 상태·결과를 함께 저장하겠습니다.

> 확인 메모: 실제 옥화당의 멱등 키 생성 위치·구성·유효기간은 코드 확인이 필요합니다. 위 키 구조는 설계 답변입니다.

### 32. 같은 멱등 키로 결제 준비 요청이 동시에 도착해도 한 번만 처리되도록 어떻게 보장했나요?

동시 요청까지 막으려면 먼저 조회하고 없으면 저장하는 방식만으로는 부족합니다. 저는 멱등 키에 유일 제약을 걸고 최초 삽입에 성공한 요청만 처리 소유권을 갖도록 설계하겠습니다. 나머지 요청은 저장된 결과를 돌려주거나 처리 중임을 응답합니다. 외부 PG 호출에도 동일 작업의 멱등 키를 전달할 수 있는지 확인하고, 서버가 중간에 종료되면 PG 조회로 결과를 복구하겠습니다. DB 중복 방지와 외부 결제의 중복 방지는 각각 해결해야 하며, 단순한 메모리 락으로는 여러 서버의 요청을 제어할 수 없습니다.

> 확인 메모: 옥화당에서 실제 사용한 유일 제약·잠금·PG 멱등 지원 여부는 구현 기록과 대조해야 합니다.

### 33. 같은 멱등 키에 서로 다른 주문 금액이나 상품 정보가 들어오면 어떻게 응답해야 하나요?

동일 키에 다른 금액이나 상품 정보가 들어오면 기존 결제의 재시도로 취급하지 않고 충돌 오류를 반환하겠습니다. 멱등 키를 처음 저장할 때 주문 ID, 통화, 서버에서 확정한 금액처럼 결과에 영향을 주는 필드의 정규화된 요청 해시도 저장합니다. 재요청의 해시가 같아야 이전 결과를 재사용합니다. 다르면 예를 들어 HTTP 409와 안정적인 오류 코드를 반환하고, 새 구매 의도라면 새 키를 사용하도록 안내하겠습니다. 기존 요청 내용을 덮어쓰면 동일 키의 의미와 감사 이력이 바뀌므로 허용하지 않겠습니다.

### 34. PG에서는 결제가 승인됐지만 서버가 응답을 받기 전에 타임아웃이 발생하면 어떻게 복구하겠나요?

타임아웃은 결제 실패가 아니라 결과를 모르는 상태로 다루겠습니다. 결제 시도를 확인 대기 상태로 남기고, 이미 저장한 주문 식별자나 PG 거래 식별자로 승인 여부를 조회합니다. 같은 작업을 다시 호출해야 한다면 PG가 보장하는 멱등 규칙 안에서 재시도하며, 새 키로 다시 승인하지 않겠습니다. 조회·웹훅·대사 중 어느 경로에서 결과를 받아도 동일한 상태 전이 함수를 통해 한 번만 반영합니다. 장시간 미확정인 건은 별도 알림과 운영 확인 대상으로 남기고, 결제 확인 전 이용권을 확정 지급하지 않겠습니다.

### 35. 결제 성공 웹훅이 중복되거나 순서가 뒤바뀌어 도착하면 어떻게 처리하겠나요?

먼저 제공자가 지원하는 웹훅 서명 검증으로 발신자를 확인하고, 이벤트 ID에 유일 제약을 두어 중복 수신을 식별하겠습니다. 정상 이벤트를 내구성 있게 저장한 뒤 빠르게 응답하고 후속 처리는 재시도 가능한 작업으로 분리할 수 있습니다. 이벤트 도착 순서대로 상태를 덮어쓰지는 않겠습니다. 현재 상태에서 허용되는 전이인지 확인하고, 오래된 승인 이벤트가 환불 완료를 승인 상태로 되돌리지 못하게 합니다. 이벤트만으로 최신 상태를 판단하기 어려우면 PG 거래 조회를 거쳐 승인·취소 사실을 각각 기록하겠습니다.

### 36. 클라이언트가 전달한 결제 금액과 PG 승인 금액, 서버의 주문 금액은 어느 단계에서 어떻게 검증하나요?

클라이언트가 보낸 금액은 결제의 기준값으로 신뢰하지 않겠습니다. 주문 생성 시 서버가 상품 가격, 수량, 할인 자격을 검증해 통화와 최종 금액을 계산하고 주문에 고정합니다. 승인 요청 전에는 해당 주문의 소유자·결제 가능 상태·금액을 확인하고, 승인 응답이나 웹훅 처리 시 PG가 확인한 주문 식별자·통화·금액을 다시 대조합니다. 불일치하면 주문을 결제 완료로 만들지 않고 확인 대상으로 격리합니다. 실제 승인이 발생했다면 거래 조회 후 승인 취소 등 보상 절차까지 이어져야 합니다.

### 37. 외부 PG 호출을 데이터베이스 트랜잭션 안에 포함하면 어떤 문제가 생기며, 어떻게 경계를 나누겠나요?

PG 호출을 긴 DB 트랜잭션 안에서 수행하면 네트워크 지연 동안 커넥션과 락을 점유하고, DB를 롤백해도 이미 성공한 외부 승인은 되돌릴 수 없습니다. 저는 짧은 트랜잭션으로 결제 시도와 처리 상태를 먼저 저장하고 커밋한 뒤 PG를 호출하겠습니다. 결과는 별도의 짧은 트랜잭션에서 조건부 상태 변경과 함께 반영합니다. 두 단계 사이의 장애는 멱등 요청, 거래 조회, 재처리 작업으로 복구합니다. 외부 결과가 불명확한 상태를 모델에 남기는 것이 전체 과정을 하나의 트랜잭션처럼 취급하는 것보다 중요합니다.

### 38. 부분 취소가 여러 번 발생하는 주문에서 누적 환불액이 실제 결제액을 초과하지 않도록 어떻게 보장하겠나요?

환불 가능액을 계산할 때 완료된 환불뿐 아니라 진행 중인 환불 예약액도 차감하겠습니다. 환불 요청마다 고유 작업 ID를 만들고, 결제 행을 잠그거나 조건부 UPDATE를 사용해 잔여 가능액이 충분할 때만 환불 금액을 예약합니다. 그 트랜잭션을 끝낸 뒤 PG를 호출하고, 성공하면 예약액을 확정 환불액으로 전환합니다. 타임아웃이면 예약을 즉시 해제하지 않고 거래 조회로 결과를 확인합니다. 이렇게 해야 동시 부분 환불 두 건이 각각 같은 잔여액을 보고 승인 금액을 초과하는 문제를 막을 수 있습니다.

### 39. 쿠폰·프로모션·캐시·카드가 함께 사용된 주문의 일부 상품을 환불할 때, 환불 금액과 수단별 배분은 어떻게 설계하겠나요?

먼저 주문 시점에 상품별 정상가, 할인 배분액, 실제 결제액과 결제 수단별 부담액을 저장하겠습니다. 부분 환불은 현재 할인 정책이 아니라 당시 적용 정책과 저장된 배분을 기준으로 계산합니다. 주문 전체 쿠폰의 배분과 원 단위 잔액 처리 규칙을 정해 상품별 합계가 주문 총액과 일치하도록 하겠습니다. 쿠폰 복원 여부, 캐시의 유상·무상 구분, 카드와 캐시의 반환 순서는 기획·재무와 합의할 정책입니다. 반복 환불에서도 상품별·수단별 누적 반환액이 원래 부담액을 넘지 않는지 함께 검증하겠습니다.

### 40. 정기결제 갱신일에 중복 실행, 결제 실패, 재시도가 발생하더라도 이용권과 청구 상태가 일치하도록 어떻게 설계하겠나요?

구독 ID와 청구 대상 기간을 조합한 청구 단위에 유일 제약을 두고, 하나의 청구에 여러 결제 시도가 연결되도록 설계하겠습니다. 동일 승인 작업의 재시도와 새로운 결제 시도는 구분하되, 성공한 청구에 추가 승인이 생기지 않도록 상태를 확인합니다. 이용권은 확인된 결제 성공 이벤트를 멱등하게 소비해 해당 기간에 한 번만 부여합니다. 실패 시 재시도 일정·유예기간·서비스 제한은 별도 정책으로 관리하고, 확인 대기 결제는 무조건 실패로 처리하지 않습니다. 청구 성공인데 이용권이 없는 상태도 정기적으로 대사하겠습니다.

## 5. 정산·금액 계산·대사

### 41. 클래스101에서 결제 완료부터 크리에이터 정산과 출금까지의 흐름을 설계한다면 어떤 데이터와 상태가 필요할까요?

결제, 정산 계산, 출금은 각각 독립적인 상태와 이력을 갖도록 설계하겠습니다. 결제와 환불 사실에서 정산 대상 항목을 만들고, 크리에이터·계약 버전·기간·통화별로 수수료와 공제를 계산해 정산 명세를 생성합니다. 검증과 확정을 거친 금액만 출금 가능액에 반영하고, 출금 요청 시에는 중복 사용을 막도록 금액을 예약합니다. 외부 이체 결과는 요청 접수와 실제 완료를 구분해 추적하겠습니다. 모든 단계에 원거래 식별자를 연결해 결제 한 건이 어떤 명세와 출금에 포함됐는지 역추적할 수 있어야 합니다.

### 42. 결제 금액, 매출 금액, 정산 예정 금액, 출금 가능 금액을 왜 구분해야 하나요?

각 금액은 확정되는 시점과 의미가 다르기 때문입니다. 결제 금액은 고객에게 승인된 거래 금액이고, 매출 금액은 회사가 합의한 인식 기준에 따라 집계한 금액입니다. 정산 예정 금액에는 크리에이터 계약에 따른 배분과 수수료·환불·공제가 반영되며, 출금 가능 금액은 그중 지급 조건을 충족하고 보류나 기존 출금 예약을 제외한 금액입니다. 이를 한 필드로 합치면 결제는 됐지만 아직 지급할 수 없는 돈을 출금할 위험이 있습니다. 명칭뿐 아니라 산식·기준 시점·통화를 데이터와 화면에서 명확히 구분하겠습니다.

### 43. 금액 계산에 `double`을 사용하면 어떤 문제가 생기며, Java와 MySQL에서 각각 어떤 자료형을 선택하겠나요?

`double`은 이진 부동소수점이라 0.1 같은 십진 소수를 정확히 표현하지 못하고, 누적 계산이나 비교에서 예상치 못한 차이가 생길 수 있습니다. Java에서는 문자열이나 정확한 정수 값에서 생성한 `BigDecimal`로 계산하고, 나눗셈과 반올림 규칙을 명시하겠습니다. MySQL에는 필요한 범위를 검토한 `DECIMAL`을 사용하겠습니다. 통화의 최소 단위 정수로 관리하는 방법도 가능하지만, 환율·수수료의 중간 계산에는 더 높은 정밀도가 필요합니다. 금액에는 통화를 함께 저장하고 언어·DB·API 사이의 변환에서도 정밀도를 보존하겠습니다.

### 44. 수수료·세금·공제 계산에서 반올림 단위와 적용 순서를 어떻게 정하고 일관되게 유지하겠나요?

수수료를 항목별로 계산한 뒤 합산하는지, 합산 금액에 요율을 적용하는지에 따라 결과가 달라지므로 먼저 계약과 업무 정책을 산식으로 확정하겠습니다. 중간 계산에는 충분한 정밀도를 유지하고, 정해진 단계에서만 통화별 단위와 반올림 모드를 적용합니다. 세금과 공제의 적용 순서도 임의로 정하지 않고 재무 담당자와 사례별 기대값을 합의하겠습니다. 분배 후 발생하는 잔여 최소 단위는 결정적인 규칙으로 배분하고, 원금과 항목 합계가 일치하는지 테스트합니다. 산식과 반올림 정책의 버전도 함께 보관하겠습니다.

### 45. 다중화폐 거래에서 결제 통화와 정산 통화가 다르다면 환율과 환산 시점을 어떻게 기록하겠나요?

원 결제의 금액·통화와 환산된 정산 금액·통화를 각각 보관하고, 적용 환율·환율 출처·기준 시각·환산 정책 버전을 함께 기록하겠습니다. 승인일 환율인지 정산 확정일 환율인지, 환불 시 원래 환율을 적용할지는 계약과 업무 정책으로 먼저 정해야 합니다. 환율이 바뀌었다는 이유로 확정된 과거 명세를 다시 계산해 덮어쓰지는 않겠습니다. 통화가 다른 금액을 그대로 합산하지 않고 통화별로 대사하며, 환차이와 반올림 차이는 별도 조정 항목으로 설명할 수 있게 설계하겠습니다.

### 46. 수수료율이나 정산 계약이 변경되어도 과거 정산 결과를 재현하려면 어떤 정보를 보관해야 하나요?

변경 가능한 현재 계약만 참조하면 과거 정산을 재현할 수 없으므로, 거래에 적용된 계약 버전과 실제 계산 입력을 보관하겠습니다. 수수료율, 세금·공제 기준, 적용 기간, 환율, 반올림 방식, 계산 로직 버전과 원거래 금액이 필요합니다. 확정 명세에는 계산 결과와 근거를 함께 저장하고, 과거 정책 데이터는 불변으로 관리하겠습니다. 재계산이 필요하면 기존 명세를 덮어쓰지 않고 새 실행과 차이 내역을 남깁니다. 동일 입력과 동일 버전에서 동일 결과가 나오는지 회귀 테스트로 확인하겠습니다.

### 47. 정산이 확정되거나 이미 출금된 거래에 환불이 발생하면 어떻게 반영하겠나요?

확정되거나 지급된 정산 내역을 과거로 돌아가 수정하기보다, 원거래와 연결된 환불·정산 조정 항목을 추가하겠습니다. 출금 전이라면 아직 지급 가능한 금액에서 반영할 수 있지만, 이미 지급했다면 향후 정산에서 차감하거나 별도 회수할지 계약과 운영 정책에 따라 결정해야 합니다. 잔액이 음수가 될 때의 출금 제한과 예외 승인도 정의하겠습니다. 고객 환불과 크리에이터 회수는 별도 처리 상태로 관리해 한쪽 실패가 숨겨지지 않게 하고, 각 조정의 사유·승인자·근거를 명세에서 확인할 수 있게 하겠습니다.

### 48. 금융 거래 기록을 수정 가능한 잔액 필드만으로 관리하는 방식과, 변경 이력을 누적하는 원장 방식은 어떤 차이가 있나요?

잔액만 갱신하면 현재 금액은 빠르게 알 수 있지만, 어떤 거래 때문에 그 값이 됐는지 설명하거나 오류를 재구성하기 어렵습니다. 원장은 입금·환불·수수료·출금 같은 변동을 누적해 과거 시점의 잔액과 변경 근거를 재현할 수 있게 합니다. 저는 원장을 기준으로 두고 조회용 잔액은 같은 트랜잭션에서 갱신하거나 검증 가능한 집계로 관리하겠습니다. 복식 구조를 쓴다면 통화별 차변·대변 합계가 일치하도록 제한합니다. 원장도 중복 기입 방지와 동시성 제어가 있어야 하며, 정정은 삭제보다 연결된 반대 분개나 조정 기록으로 남기겠습니다.

### 49. PG 거래 내역과 내부 결제·정산 데이터가 일치하는지 확인하는 대사 작업을 어떻게 설계하겠나요?

먼저 대사 기간·시간대·통화·마감 기준을 맞추고, PG 거래 ID를 기준으로 승인·부분 취소·전체 취소를 각각 비교하겠습니다. 건수와 총액을 비교한 뒤 거래별로 내려가 내부 누락, PG 누락, 금액 차이, 상태 차이로 분류합니다. 늦게 들어오는 데이터는 확인 대기 구간을 두고 재대사하며, 차이가 있다고 원본을 바로 덮어쓰지는 않겠습니다. 대사 실행 ID와 양쪽 입력 자료를 보관하고, 확실한 누락만 멱등하게 복구합니다. 미해결 건은 담당자·사유·해결 이력이 있는 예외 목록으로 관리하겠습니다.

### 50. 크리에이터가 “입금액이 예상보다 적다”고 문의하면 어떤 데이터와 계산 이력을 따라가며 원인을 설명하겠나요?

우선 크리에이터가 비교한 예상 금액의 기간과 통화, 기준이 결제 총액인지 정산액인지 확인하겠습니다. 해당 출금 건에서 정산 명세와 원거래로 거슬러 올라가 대상 매출, 계약상 배분, 환불, 수수료, 세금·공제, 보류액, 이전 조정액을 확인합니다. 환율과 반올림 차이도 계산 당시의 근거로 설명하겠습니다. 결과는 항목별 금액과 합계가 맞는 표로 제공하고, 오류가 확인되면 정정 명세와 지급 계획을 안내합니다. 재계산 결과만 보여주는 대신 당시 적용한 정책과 변경 이력까지 추적하는 것이 핵심입니다.

## 6. 데이터 모델링·API·도메인 이관

### 51. 주문, 결제 시도, 승인, 취소, 환불을 하나의 테이블로 관리하는 방식과 분리하는 방식의 장단점은 무엇인가요?

초기에는 한 테이블이 조회와 구현에 단순하지만, 한 주문에 결제 시도와 부분 환불이 여러 번 생기면 반복 컬럼과 상태 조합이 복잡해집니다. 저는 주문은 구매 내용과 계약 상태를, 결제 시도는 요청과 결과를, 승인·환불은 실제 금전 변동을 표현하도록 분리하겠습니다. 주문과 결제는 일대다 관계로 두고 PG 거래 ID와 작업 ID에 적절한 유일 제약을 적용합니다. 다만 무조건 서비스까지 분리하지는 않겠습니다. 같은 DB 안에서 명확한 모델과 트랜잭션 경계를 먼저 잡고, 조회에는 필요한 조인과 읽기 모델을 사용하겠습니다.

### 52. 상품명·가격·할인 정책이 변경돼도 과거 주문을 정확히 조회하려면 주문 데이터에 무엇을 저장해야 하나요?

과거 주문은 현재 상품 테이블만 참조해서 표현하면 안 된다고 생각합니다. 주문 항목에 구매 당시 상품명·옵션·단가·수량·통화와 할인 배분액, 최종 부담액을 스냅샷으로 저장하겠습니다. 상품 ID는 추적을 위해 남기되 당시 거래 조건은 스냅샷으로 재현합니다. 적용한 쿠폰·프로모션 정책 버전과 계산 근거도 남겨야 부분 환불과 문의 대응이 가능합니다. 주문 확정 후 가격을 직접 수정하지 않고 취소·정정 흐름으로 변경 이력을 남기며, 배송 정보처럼 개인정보가 포함된 스냅샷은 보관 목적과 기간을 별도로 관리하겠습니다.

### 53. 결제 상태와 주문 상태를 분리해야 하는 이유는 무엇이며, 허용되지 않는 상태 조합은 어떻게 막겠나요?

주문은 구매와 이행의 생애주기이고, 결제는 금전 거래의 생애주기라 서로 일대일로 움직이지 않습니다. 결제는 성공했지만 배송 전 취소 중일 수 있고, 한 주문에 여러 실패 시도와 부분 환불이 있을 수도 있습니다. 저는 각각 상태 전이표를 정의하고, 이용권 지급에는 확인된 결제 성공이 필요하다는 식의 교차 조건을 명시하겠습니다. 상태 변경은 기대한 이전 상태를 조건으로 수행해 경쟁 요청을 막습니다. 외부 결제 결과가 늦는 중간 상태는 허용하되, 허용 시간을 넘기면 복구 작업과 알림으로 관리하겠습니다.

### 54. 재시도 가능한 결제·환불 API의 요청 형식, 응답 코드, 오류 정보를 어떻게 설계하겠나요?

작업 식별자와 멱등 키, 대상 주문 또는 결제 ID, 환불 금액·통화를 명시하고 요청 내용의 일관성을 검증하겠습니다. 응답에는 작업 ID와 현재 상태, 재조회할 주소를 포함해 연결이 끊겨도 결과를 확인할 수 있게 합니다. 처리 완료면 기존 결과를 재사용하고, 비동기 접수라면 202처럼 완료와 구분되는 응답을 사용하겠습니다. 오류는 잘못된 입력, 상태 충돌, 일시적 실패, 결과 미확정으로 나눕니다. 클라이언트에는 안정적인 오류 코드와 재시도 가능 여부를 제공하고, 내부 PG 오류나 비밀값은 그대로 노출하지 않겠습니다.

### 55. 거래 내역이 지속적으로 추가되는 상황에서 중복이나 누락을 줄이는 페이지네이션을 어떻게 구현하겠나요?

지속적으로 추가되는 거래 내역은 OFFSET보다 커서 기반 페이지네이션을 우선 검토하겠습니다. 변경되지 않는 생성 시각과 고유 ID를 복합 정렬 키로 사용하고, 다음 페이지에서는 마지막 키보다 뒤의 행만 조회합니다. 시작할 때 상한 키를 고정하면 이후 추가된 거래 때문에 페이지가 밀리는 문제를 줄일 수 있습니다. 필터와 정렬에 맞는 복합 인덱스도 확인하겠습니다. 다만 처리 상태가 도중에 바뀌는 필터에서는 커서만으로 완전한 스냅샷을 보장하지 못하므로, 정확한 전체 추출은 기준 시점 스냅샷이나 별도 내보내기 작업으로 처리하겠습니다.

### 56. 결제·정산 데이터에 MySQL과 MongoDB 중 무엇을 선택하겠으며, 판단 기준은 무엇인가요?

결제·정산의 기준 데이터라면 저는 우선 MySQL을 선택하겠습니다. 주문·결제·환불·정산 사이의 관계가 명확하고, 유일 제약과 트랜잭션, 정확한 십진 금액 타입을 이용해 불변 조건을 표현하기 좋기 때문입니다. MongoDB도 트랜잭션을 지원하지만, 지원 여부만으로 판단하지 않고 실제 접근 패턴과 스키마 변화, 운영 경험을 함께 보겠습니다. 문서 형태의 외부 응답이나 유연한 조회 모델에는 별도 선택지가 될 수 있습니다. 저장소를 추가하면 대사와 복구 부담도 늘어나므로 하나의 DB로 요구를 충족하는지 먼저 검토하겠습니다.

### 57. 정산 명세 조회에 GraphQL을 도입한다면 어떤 이점과 위험을 검토하겠나요?

크리에이터 화면과 운영 화면이 서로 다른 정산 상세 항목을 요구한다면 GraphQL은 필요한 필드와 관계를 한 번에 조회하는 데 도움이 될 수 있습니다. 반면 중첩 조회로 N+1과 고비용 쿼리가 발생할 수 있고, 정산 데이터의 접근 권한도 필드와 객체 수준에서 검증해야 합니다. 도입한다면 페이지 크기·깊이·복잡도 제한과 배치 로딩을 적용하고, 리졸버별 지연과 DB 호출을 관측하겠습니다. 화면 요구가 단순하면 REST로도 충분하므로, GraphQL 자체보다 조회 유연성의 이득이 운영 복잡성을 상쇄하는지 먼저 확인하겠습니다.

### 58. B마트 전시 API 92개를 이관할 때 대상 목록, 호출 의존성, 이관 순서를 어떻게 관리했나요?

우아한형제들 재직 중 신규 가게홈 서버를 구축하면서 전시 API 92개를 이관했습니다. 관련 모듈과 테이블의 의존관계를 정리하고, Spring 다중 데이터소스 구성과 DB·Redis 이관, 단계별 배포 전 검증을 수행한 경험입니다. 이관에서 중요한 것은 API 개수만 세는 것이 아니라 호출 주체와 공통 의존성, 읽기·쓰기 경로를 함께 보는 것이라고 생각합니다. 같은 작업을 계획한다면 API별 담당자·변경점·검증 결과를 목록으로 관리하고, 공통 기반을 먼저 준비한 뒤 영향과 복구 가능성을 기준으로 전환 순서를 정하겠습니다.

> 확인 메모: 당시 사용한 목록 관리 도구, 실제 이관 순서와 담당 범위는 프로젝트 기록으로 확인해야 합니다.

### 59. API 이관 전후의 동작 호환성과 데이터 일치를 어떻게 검증했고, 트래픽 전환과 롤백은 어떻게 준비했나요?

가게홈 이관에서는 단계별 배포 전 검증을 거쳐 상품·기획전 기능을 운영 중단 없이 전환한 경험이 있습니다. 호환성 검증을 설계한다면 응답 스키마뿐 아니라 정렬·기본값·오류 응답·권한·캐시 동작까지 이전 구현과 비교하겠습니다. 데이터는 건수·누락·핵심 필드와 업무 시나리오를 함께 확인합니다. 트래픽 전환은 오류율과 지연, 업무 지표를 보며 범위를 늘리고, 중단 기준을 사전에 정하겠습니다. 롤백도 라우팅만 되돌리면 끝나는 것이 아니라 새 서버가 기록한 데이터를 이전 서버가 읽고 처리할 수 있는지까지 준비해야 합니다.

> 확인 메모: 실제 응답 비교 방식, 트래픽 분할 비율과 롤백 실행 여부는 확인되지 않아 설계 관점으로 작성했습니다.

### 60. 대량의 결제 데이터가 있는 테이블의 스키마를 변경해야 한다면 서비스 중단 없이 어떤 순서로 진행하겠나요?

기존 코드와 새 코드가 함께 동작하도록 확장·이행·정리 순서로 진행하겠습니다. 먼저 호환되는 컬럼이나 테이블을 추가하고, 변경을 추적할 수 있는 방식으로 새 쓰기 경로를 준비합니다. 과거 데이터는 작은 묶음으로 보충하면서 락 대기·복제 지연·오류를 관측하고, 신규 쓰기와 경합해 최신 값을 덮어쓰지 않도록 조건을 둡니다. 양쪽 결과를 비교한 뒤 읽기를 전환하고 충분한 관찰 기간 후 이전 구조를 제거하겠습니다. 온라인 DDL도 버전과 작업 종류에 따라 잠금이 발생하므로 실제 테이블 규모에 가까운 환경에서 검증하겠습니다.

## 7. 대용량 배치·비동기 처리·자동화

### 61. 100만 건 대상 할인 알림 배치의 전체 처리 구조와 본인이 맡은 부분을 설명해 주세요.

우아한형제들에서 100만 건을 대상으로 하는 할인 알림 배치를 구현했습니다. 대용량 배치에서 중요하게 보는 부분은 대상 선정, 제한된 크기의 조회·가공, 발송 결과 기록을 분리해 실패 위치를 식별하는 것입니다. 같은 규모를 다시 설계한다면 실행 기준 시각과 대상 조건을 먼저 고정하고, 작은 단위로 처리하면서 성공·실패·재시도 상태를 남기겠습니다. 외부 알림 전송은 DB 커밋과 함께 원자적으로 성공하지 않으므로, 재시작 위치뿐 아니라 발송 중복을 막는 식별자도 함께 설계하겠습니다.

> 확인 메모: 100만 건의 기준이 상품·사용자·발송 건수 중 무엇인지와 당시 Reader·Writer, 알림센터 연계 방식, 직접 담당한 범위를 확인해야 합니다. 뒤의 구조 설명은 설계 제안입니다.

### 62. 해당 배치의 입력 데이터를 읽을 때 어떤 조회 방식을 사용했으며, 메모리 사용량과 데이터 누락을 어떻게 관리했나요?

100만 건 전체를 한 번에 메모리에 올리는 방식은 피하겠습니다. 대상 식별자와 처리에 필요한 컬럼만 읽고, 정렬이 안정적인 키를 기준으로 일정량씩 조회하겠습니다. 처리 중 데이터가 추가·변경될 수 있다면 시작 시점의 상한 ID나 대상 목록을 고정해 조회 범위를 명확히 하겠습니다. 메모리는 조회 크기뿐 아니라 JPA 영속성 컨텍스트에 누적되는 객체도 확인하고, 청크 처리 후 참조가 해제되는지 보겠습니다. 마지막에는 예상 대상 수와 처리 결과를 대조해 누락을 검증하겠습니다.

> 확인 메모: 당시 사용한 커서·페이징 방식과 정렬 키, 메모리 측정치는 자료에 없어 단정하지 않았습니다.

### 63. Spring Batch의 청크 크기와 트랜잭션 범위를 어떤 기준으로 정했나요?

청크 크기는 처리량을 높이면서도 메모리, 잠금 유지 시간, 실패 시 재처리 비용이 감당 가능한 수준으로 정하겠습니다. 작은 크기부터 같은 데이터로 측정하고, 커밋 비용 감소보다 긴 트랜잭션과 메모리 증가의 손해가 커지는 지점을 보겠습니다. DB 쓰기와 체크포인트가 같은 트랜잭션 자원에 묶이는지도 확인하겠습니다. 외부 알림 호출은 롤백되지 않기 때문에 청크 트랜잭션만으로 중복 발송을 막을 수 없으며, 별도 발송 상태와 멱등 처리가 필요합니다.

> 확인 메모: 당시 실제 청크 크기, 트랜잭션 매니저, 부하 측정 결과는 코드와 실행 기록으로 보완해야 합니다.

### 64. 배치가 70만 건 처리 후 중단되면, 이미 처리한 대상에게 중복 알림을 보내지 않고 어떻게 재시작하나요?

같은 실행 대상과 식별 파라미터를 유지한 채 마지막으로 커밋된 체크포인트부터 재시작하겠습니다. 다만 체크포인트 이전에 외부 발송이 성공하고 결과 저장만 실패할 수 있어, 체크포인트만 믿지는 않겠습니다. 캠페인과 수신 대상 조합에 고유한 발송 키를 두고, 외부 제공자가 멱등 키나 결과 조회를 지원하면 이를 활용하겠습니다. 지원하지 않으면 결과가 불명확한 발송을 별도 상태로 남겨 확인해야 합니다. 이런 조건에서 중복이 절대 없다고 약속하기보다 보장 범위와 복구 절차를 명확히 하겠습니다.

### 65. 배치 작업 두 개가 동일 대상을 동시에 처리하지 않도록 어떤 장치를 두었나요?

실행 단위 중복과 개별 항목 중복을 따로 막겠습니다. Spring Batch 메타데이터를 공유해 동일 JobInstance의 중복 실행을 제어하고, 업무 테이블에도 처리 대상과 실행 기준을 묶는 고유 제약을 두겠습니다. 서로 다른 실행이 같은 대상을 포함할 수 있으므로 작업 시작 시 조건부 UPDATE로 처리권을 획득하는 방식도 검토하겠습니다. 임대 방식의 잠금을 사용한다면 만료된 이전 작업자가 계속 쓰지 못하도록 버전 검증까지 필요합니다. 스케줄러 중복 방지만으로 업무 중복 처리가 해결되지는 않습니다.

> 확인 메모: 당시 실제 적용한 중복 실행 방지 장치는 확인되지 않았으므로 위 내용은 설계 답변입니다.

### 66. 알림 전송 API에 요청 제한이 있거나 일시적인 오류가 발생하면 재시도 간격과 최대 횟수를 어떻게 정하나요?

오류를 일시 장애와 영구 오류로 먼저 나누겠습니다. 요청 제한이나 일시적인 서버 오류는 제공자의 재시도 지침을 따르고, `Retry-After`가 있으면 존중하겠습니다. 그 외에는 지수 백오프에 지터를 더해 재시도가 동시에 몰리지 않게 하겠습니다. 재시도 횟수뿐 아니라 총 대기 시간과 알림의 유효 기간도 제한하고, 잘못된 수신 정보처럼 반복해도 해결되지 않는 오류는 격리하겠습니다. 전송 결과가 불명확할 때는 같은 식별자로 조회하거나 재시도해 중복 발송 위험을 줄이겠습니다.

### 67. 반드시 처리해야 할 정산 항목 하나가 계속 실패한다면, 전체 배치를 중단할지 해당 항목을 격리할지 어떻게 판단하겠나요?

실패 원인과 해당 항목이 전체 합계에 미치는 영향을 먼저 보겠습니다. 특정 항목의 잘못된 입력이라면 그 항목을 보류하고 원인과 금액을 기록하되, 의존관계가 없는 정상 항목은 처리할 수 있습니다. 반면 계산 규칙이나 환율 데이터가 잘못됐다면 전체 결과에 영향을 줄 수 있으므로 중단하겠습니다. 격리한 항목을 성공으로 세지는 않으며, 미처리 금액이 남은 정산은 부분 완료로 표시하겠습니다. 재무 담당자와 합의한 출금 승인 기준을 통과한 범위만 지급하겠습니다.

### 68. 데이터베이스 반영은 성공했지만 후속 이벤트 발행이 실패하는 문제를 어떻게 해결하겠나요?

업무 데이터와 발행할 이벤트를 같은 DB 트랜잭션에 저장하는 트랜잭셔널 아웃박스 방식을 검토하겠습니다. 별도 전달기가 미발행 이벤트를 읽어 전송하고 성공 상태를 갱신하면, DB 반영 후 이벤트가 사라지는 공백을 줄일 수 있습니다. 전송 성공 직후 전달기가 죽으면 같은 이벤트가 다시 발행될 수 있으므로 소비자는 이벤트 ID를 기록해 중복 효과를 막아야 합니다. 주문별 순서가 중요하면 주문 ID와 버전도 함께 전달하고, 전달 지연·재시도·실패 격리 상태를 모니터링하겠습니다.

### 69. 20여 개 팀·100여 개 워크플로우를 위한 Slack 통합 솔루션에서 공통화한 부분과 팀별로 남겨둔 부분은 무엇인가요?

사내 Slack 통합 솔루션에서는 팀마다 달랐던 지원 요청을 공통 절차와 팀별 예외로 나누었습니다. JIRA 티켓 생성, 요청 정보 전달, 스프레드시트 연동, 릴리스 백포팅처럼 반복되는 작업을 연결해 요청자가 여러 도구를 오가며 정보를 다시 입력하는 부담을 줄였습니다. 반면 팀마다 다른 승인 담당자와 요청 조건까지 하나로 강제하는 것은 피해야 한다고 생각합니다. 공통화의 기준은 화면이 같은지가 아니라 요청 접수부터 처리 결과 확인까지 반복되는 업무 흐름이 같은지입니다.

> 확인 메모: 공통 기능과 팀별 설정의 실제 구분, 자동화·승인 경계를 당시 설계 자료로 확인해야 합니다. 20여 개 팀·100여 개 워크플로우는 최신 이력서 기준입니다.

### 70. 할인 알림 배치의 경험을 일별 정산 배치에 적용한다면 정확성 검증과 완료 판정 기준을 어떻게 강화하겠나요?

알림 배치에서 다룬 대량 처리 경험은 활용하되, 정산에서는 건수뿐 아니라 금액의 일치까지 완료 조건으로 삼겠습니다. 정산 대상 기간과 기준 시각, 계약·수수료 정책 버전을 고정하고 같은 입력으로 같은 결과가 나오는지 확인하겠습니다. 원천 거래와 정산 항목을 식별자로 연결해 누락·중복을 찾고, 통화별 합계와 보류·실패 금액을 대조하겠습니다. 배치 프로세스가 정상 종료됐다는 이유만으로 완료 처리하지 않고, 대사와 승인까지 통과해야 지급 가능한 상태로 전환하겠습니다.

## 8. 실시간 시스템·분산 처리·장애 복구

### 71. 고산운에서 방별 작업 직렬화가 필요했던 구체적인 경쟁 상태와 해결 방법을 설명해 주세요.

개인 프로젝트 고산운에서 방별 작업 직렬화를 구현했습니다. 협동 시뮬레이션에서는 같은 방의 상태를 여러 요청이 읽은 뒤 각각 갱신하면, 앞선 변경이 덮이거나 이미 소모된 자원을 다시 사용하는 문제가 생길 수 있습니다. 방 단위로 상태 변경 순서를 정하면 한 작업의 결과를 다음 작업이 기준으로 삼을 수 있습니다. 설계상으로는 검증부터 변경까지 직렬화 경계 안에 두고, 저장·타이머처럼 다른 진입점도 같은 경계를 따르는지 확인해야 합니다.

> 확인 메모: 실제 재현했던 경쟁 상태와 코드 경계는 저장소 확인이 필요합니다. 자원 중복 사용은 가능한 문제의 예시이며 실제 발생한 장애로 단정하지 않습니다.

### 72. 방별 작업 직렬화는 단일 프로세스 안에서만 유효한가요? 서버가 여러 대가 되면 어떻게 보장하겠나요?

프로세스 내부 큐나 뮤텍스만 사용했다면 다른 서버의 작업까지 막지는 못합니다. 여러 서버로 확장한다면 한 방을 담당하는 쓰기 주체를 하나로 정하고 요청을 그 주체로 전달하겠습니다. 소유권 이전과 장애 복구 때는 이전 서버가 다시 쓰지 못하도록 세대 번호나 fencing token을 저장 시 검증해야 합니다. 또 클라이언트 재시도는 단일 소유자에게도 중복 도착할 수 있으므로 요청 ID로 처리 결과를 구분하겠습니다. 서버 수를 늘리는 것과 방 하나의 처리량을 늘리는 것은 별도의 문제입니다.

### 73. 스냅샷 캐시와 실제 진행 상태가 어긋나지 않도록 어떤 기준으로 스냅샷을 생성하고 갱신했나요?

고산운에서는 스냅샷 캐싱과 저장·복원을 구현했습니다. 설계 원칙은 특정 버전의 상태로 만든 스냅샷이 중간 변경과 섞이지 않게 하는 것입니다. 이를 강화한다면 상태 변경 버전을 증가시키고, 직렬화된 처리 구간에서 일관된 복사본을 만든 뒤 그 버전을 캐시 키나 메타데이터에 기록하겠습니다. 스냅샷 생성 중 상태가 바뀌어도 이전 버전의 결과가 최신 캐시를 덮지 않도록 검사하겠습니다. 클라이언트에도 버전을 전달하면 오래된 스냅샷의 역전 적용을 막을 수 있습니다.

> 확인 메모: 실제 갱신 주기·무효화 조건·버전 필드의 적용 여부는 자료에 없어, 구현한 기능과 개선 설계를 구분했습니다.

### 74. 상태 저장 중 프로세스가 종료되면, 복원 후 중복 실행이나 데이터 손실을 어떻게 처리하나요?

저장 중 종료를 대비하려면 먼저 어디까지를 영속적으로 완료했다고 응답할지 정해야 합니다. 파일이라면 임시 파일에 완전히 기록한 뒤 교체하고, DB라면 트랜잭션으로 상태와 처리 식별자를 함께 저장하겠습니다. 마지막 스냅샷 이후 작업까지 복구해야 한다면 작업 로그나 이벤트를 내구성 있게 남기고, 복원 시 이미 반영된 요청은 건너뛰겠습니다. 메모리에서만 성공한 작업은 프로세스 종료로 잃을 수 있으므로, 저장 주기와 허용 가능한 손실 범위를 명시하고 실제 강제 종료 테스트로 검증하겠습니다.

> 확인 메모: 고산운의 실제 저장 매체·원자적 교체 방식·복구 보장 범위는 별도 확인이 필요합니다.

### 75. 선립:티버스에서 WebSocket 재연결 후 클라이언트가 놓친 상태를 어떻게 복구했나요?

선립:티버스에서는 WebSocket 연결 복원과 방별 상태 관리를 구현했습니다. 재연결 시에는 끊기기 전 클라이언트 상태를 그대로 신뢰하지 않고 현재 서버 상태와 다시 맞추는 것이 핵심입니다. 설계한다면 참가자의 세션을 재검증하고 서버 스냅샷과 버전을 내려주겠습니다. 마지막 수신 버전 이후의 변경을 보관하고 있다면 증분 복구도 가능하지만, 이력이 없거나 간격이 크면 전체 상태를 다시 받겠습니다. 좌석 같은 공유 자원은 재접속했다고 자동 소유권을 인정하지 않고 서버의 현재 점유 상태를 기준으로 판단하겠습니다.

> 확인 메모: 실제 복원이 전체 스냅샷인지 증분 메시지인지, 참가자 식별 방식은 구현 확인이 필요합니다.

### 76. 여러 사용자가 같은 좌석을 동시에 선택하는 문제와, 같은 재고를 동시에 구매하는 문제는 무엇이 같고 다른가요?

둘 다 같은 자원을 여러 요청이 동시에 점유하려는 문제라서, 조회 후 따로 갱신하면 경쟁 상태가 생깁니다. 한 처리 경계에서 점유 가능 여부를 확인하고 소유권을 바꾸거나, 조건부 갱신·고유 제약으로 한 요청만 성공하게 해야 합니다. 차이는 실패의 비용과 복구 기준입니다. 좌석은 연결 종료나 임대 만료로 해제할 수 있지만, 재고는 결제 결과가 불명확하면 즉시 풀어서는 안 됩니다. 재고 예약은 주문·결제 상태와 연결하고, 늦게 도착한 승인이나 환불까지 고려해 보상 절차를 설계해야 합니다.

### 77. Cloudflare Durable Objects를 선택한 이유는 무엇이며, 방별 상태 관리에서 얻는 이점과 제약은 무엇인가요?

선립:티버스는 방별로 사용자가 상호작용하는 서비스라, 방 ID를 기준으로 상태와 요청 처리를 모을 수 있는 Durable Objects와 잘 맞습니다. 이런 구조는 좌석과 진행 상태의 권위 있는 처리 지점을 만드는 데 도움이 됩니다. 다만 단일 스레드여도 외부 fetch를 기다리는 동안 다른 요청이 실행될 수 있어, 핸들러 전체가 자동 직렬화된다고 보지는 않겠습니다. 저장소의 입력 게이트가 보호하는 범위와 별도 동기화가 필요한 범위를 구분해야 합니다. 객체별 부하, 재시작 시 상태 복구, 비용과 플랫폼 의존성도 함께 평가하겠습니다.

> 확인 메모: 위 내용은 현재 서비스 구조에 대한 기술적 적합성 설명입니다. 당시 비교 후보와 실제 선택 이유는 본인의 의사결정 기록으로 확인해야 합니다.

### 78. 메시지 빈도와 좌표 검증은 서버의 어느 단계에서 수행했으며, 정상 사용자의 요청을 잘못 차단하지 않도록 어떻게 조정했나요?

선립:티버스에서 메시지 빈도와 좌표 검증을 구현했습니다. 원칙적으로 서버가 상태를 바꾸기 전에 메시지 형식, 인증된 참가자, 방 소속, 허용 범위를 검사해야 합니다. 이를 설계한다면 좌표의 숫자 여부와 유한성, 공간 경계, 시간 대비 이동량을 확인하고, 빈도 제한은 짧은 순간의 정상적인 몰림을 허용하되 지속적인 과부하는 차단하겠습니다. 모든 검증 실패를 같은 기준으로 처리하지 않고 관측 지표를 보면서 지연·재연결로 생긴 정상 요청과 악의적 요청을 구분하겠습니다.

> 확인 메모: 실제 제한 값, 검증 순서, 조정 이력은 확인되지 않았습니다. 속도 검증 등은 제안하는 추가 설계입니다.

### 79. 웹과 API를 동일 릴리스로 배포해도 이전 웹 클라이언트가 남을 수 있는데, 버전 호환성은 어떻게 처리하겠나요?

웹과 API의 릴리스를 맞추는 것만으로 오래 열린 브라우저나 캐시된 파일까지 교체되지는 않습니다. 우선 필드 추가처럼 이전 클라이언트가 허용할 수 있는 변경을 적용하고, 필드 삭제나 의미 변경은 호환 기간을 두겠습니다. 요청이나 연결 과정에서 클라이언트 버전을 확인해 지원 범위를 벗어나면 명확한 갱신 안내를 제공하겠습니다. 데이터 구조를 바꿀 때는 구버전과 신버전이 함께 동작하는 단계가 필요하며, 배포 직후의 이전 클라이언트 요청과 롤백도 테스트하겠습니다.

### 80. 이러한 실시간 시스템 경험을 결제·정산에 적용할 때, 재사용할 수 있는 원칙과 더 엄격하게 바꿔야 할 원칙은 무엇인가요?

공유 상태의 변경 순서를 정하고, 서버를 기준으로 검증하며, 재연결 후 상태를 복구하는 원칙은 결제·정산에도 적용할 수 있습니다. 다만 금액을 다루면 메모리의 일관성만으로는 부족합니다. DB의 원자성, 요청 멱등성, 변경 이력, 외부 거래와의 대사가 함께 필요합니다. 게임의 일시적인 화면 차이는 다음 스냅샷으로 맞출 수 있어도 중복 청구는 그렇게 해결되지 않습니다. 완료 응답 전에 무엇을 영속화해야 하는지, 장애 후 어떤 근거로 복구하는지를 더 엄격하게 정의하겠습니다.

## 9. 테스트·모니터링·보안·운영

### 81. MDC 기반 SQL 진입점 로깅은 어떤 정보를 남기며, 기존 SQL 로그만으로는 찾기 어려웠던 문제를 어떻게 해결했나요?

우아한형제들에서 MDC 기반 SQL 진입점 로깅을 구현해 장애 원인 파악 시간을 25분에서 9분으로 줄였습니다. SQL 자체만 보면 어떤 업무 흐름에서 실행됐는지 바로 연결하기 어려운데, 진입점 정보를 함께 남기면 느린 쿼리를 요청이나 배치 흐름으로 거슬러 올라갈 수 있습니다. 설계 관점에서는 추적 ID, 진입한 업무 이름, 실행 시간을 연결하되 SQL 파라미터의 민감정보는 제외하겠습니다. 중요한 것은 로그의 양을 늘리는 것이 아니라 원인을 좁히는 데 필요한 연결 정보를 제공하는 것입니다.

> 확인 메모: 당시 실제 MDC 키와 SQL 진입점 수집 방식은 코드 또는 발표 자료로 확인해야 합니다.

### 82. 비동기 작업이나 스레드 풀을 사용할 때 MDC 정보가 유실되거나 다른 요청에 섞이지 않도록 어떻게 처리하나요?

MDC는 일반적으로 스레드에 묶여 있으므로 작업을 다른 스레드에 넘길 때 필요한 값을 복사해야 합니다. Spring의 TaskDecorator 같은 경계에서 제출 시점의 컨텍스트를 캡처하고 실행 스레드에 설정한 뒤, 작업이 끝나면 finally에서 이전 값을 복원하거나 제거하겠습니다. 스레드 풀은 스레드를 재사용하므로 정리하지 않으면 다음 요청의 로그에 이전 정보가 섞일 수 있습니다. 큐나 네트워크를 넘는 경우에는 추적 ID를 메시지 메타데이터로 전달하고 소비 지점에서 다시 컨텍스트를 구성하겠습니다.

> 확인 메모: 사내 TaskExecutor 통합 경험은 소재은행에 있지만, TaskDecorator를 실제 사용했는지는 확인되지 않았습니다.

### 83. 장애 원인 파악 시간이 25분에서 9분으로 줄었다는 결과는 어떤 사례와 측정 기준으로 확인했나요?

기록된 성과는 SQL 진입점 로깅 개선으로 평균 원인 파악 시간이 25분에서 9분으로 줄었다는 것입니다. 이를 설명할 때 장애가 완전히 복구되는 시간과 원인을 식별하는 시간을 구분하겠습니다. 측정의 신뢰성을 확인하려면 시작·종료 시점의 정의, 비교한 사례 수, 장애 난이도와 담당자 차이를 함께 봐야 합니다. 같은 기준의 로그나 대응 기록을 제시하는 것이 가장 좋고, 일부 사례의 관측치라면 모든 장애에서 동일한 효과가 있었다고 확대해서 말하지 않겠습니다.

> 확인 메모: 표본 수, 관측 기간, 시작·종료 기준은 현재 자료에 없으므로 면접 전 근거 확인이 필요합니다.

### 84. 속닥속닥의 테스트 425개 실행 시간을 3분에서 45초로 줄인 원인은 무엇이며, 테스트 격리는 어떻게 유지했나요?

우아한테크코스 팀 프로젝트 속닥속닥에서 테스트 격리와 실행 시간 개선을 수행했고, 425개 테스트 실행 시간이 3분에서 45초로 줄었습니다. 이런 개선은 반복되는 초기화 비용과 테스트 간 공유 상태를 나누어 보는 것이 중요합니다. 같은 문제를 점검한다면 Spring 컨텍스트 재생성, DB 초기화, 외부 I/O에 걸리는 시간을 먼저 측정하겠습니다. 컨텍스트를 재사용해도 데이터와 정적 상태는 테스트마다 초기화하고, 단독 실행·전체 실행·순서 변경에서 결과가 같은지 확인해 속도 때문에 격리를 희생하지 않겠습니다.

> 확인 메모: 실제 단축 원인이 컨텍스트 재사용인지 DB 정리 방식인지 등은 자료에 없습니다. 개선 성과와 일반적인 진단 방법을 구분했습니다.

### 85. 결제 멱등성과 재고 동시성 테스트를 작성한다면 어떤 경쟁 상황과 불변 조건을 검증하겠나요?

같은 멱등 키로 동시에 결제 요청을 보내고, 응답을 받기 전 재시도하거나 같은 키에 다른 금액을 넣는 경우를 검증하겠습니다. 기대 조건은 승인 효과와 결제 레코드가 중복되지 않고, 다른 요청 내용이 같은 결과로 잘못 처리되지 않는 것입니다. 재고는 1개에 다수 요청을 동시에 시작해 예약 합계가 재고를 넘지 않는지 확인하겠습니다. 마지막으로 예약 만료와 결제 성공이 경쟁하는 경우도 테스트하겠습니다. 실제 DB의 잠금과 고유 제약을 검증해야 하므로 모킹한 단위 테스트만으로 끝내지 않겠습니다.

### 86. PG 타임아웃, 중복 웹훅, 데이터베이스 장애를 테스트 환경에서 어떻게 재현하겠나요?

제어 가능한 PG 대역을 만들어 승인 직후 응답만 지연시키는 경우와 승인 자체가 실패하는 경우를 구분하겠습니다. 동일 웹훅을 반복하거나 역순으로 보내고, 처리 중 프로세스를 종료한 뒤 재시작해도 상태가 올바르게 복구되는지 확인하겠습니다. DB 장애는 커밋 전 실패와 커밋 결과를 알 수 없는 연결 끊김을 나눠 재현하겠습니다. 테스트의 핵심은 오류 응답을 받는지가 아니라 중복 청구, 초과 환불, 누락이 없고 불명확한 거래가 조회·대사로 해소되는지입니다.

### 87. 결제·정산 시스템의 운영 대시보드에 어떤 기술 지표와 비즈니스 지표를 표시하겠나요?

기술 지표로는 응답 지연의 p95·p99, 오류율, 타임아웃, DB 잠금 대기, 큐 적체와 외부 PG 지연을 보겠습니다. 비즈니스 지표는 결제 시도 대비 승인율, 오래 머무는 처리 중 거래, 환불 지연, 정산 대상 대비 완료·보류 금액, 대사 불일치 건수입니다. 승인율은 카드 거절과 시스템 오류를 나누어야 불필요한 경보를 줄일 수 있습니다. 전체 평균만 보지 않고 결제 수단·통화·처리 단계별로 나누며, 금액과 건수는 민감정보 없이 집계하겠습니다.

### 88. API 오류율은 정상이지만 일부 정산이 누락되는 장애를 어떻게 탐지하겠나요?

요청이 성공했다는 지표와 업무가 완결됐다는 지표를 분리하겠습니다. 일정 시점에 정산 대상이 되어야 하는 원천 거래 목록을 독립적으로 산출하고, 실제 정산 항목과 식별자 단위로 대조하겠습니다. 건수와 금액 합계가 같아도 서로 다른 누락·중복이 상쇄될 수 있으므로 합계 비교만으로 끝내지 않겠습니다. 마감 시각을 넘긴 미처리 항목과 데이터 유입 중단도 감시하고, 발견된 누락은 원인을 남긴 뒤 멱등한 재처리 경로로 복구하겠습니다.

### 89. 결제·정산 로그에서 민감정보 노출을 막으면서도 추적 가능성을 확보하려면 무엇을 기록하고 무엇을 가려야 하나요?

추적에 필요한 요청 ID, 내부 거래 ID, 상태 전이, 처리 시각, 실행 주체와 결과 코드를 중심으로 기록하겠습니다. 카드번호, 인증 토큰, 비밀 키, 전체 계좌정보나 원문 요청·응답은 기본적으로 남기지 않겠습니다. 조사에 필요한 개인정보가 있다면 마스킹·접근 통제·보존 기간을 함께 정하고, 로그 조회 자체도 감사 대상에 포함하겠습니다. 일반 진단 로그와 금전 변경 감사 기록은 목적이 다르므로, 후자는 변경 전후 값과 사유를 변조하기 어려운 방식으로 보관하겠습니다.

### 90. 운영자가 환불하거나 정산 금액을 조정하는 관리 기능에 어떤 권한 통제와 감사 기록을 적용하겠나요?

환불 조회, 환불 실행, 정산 조정을 별도 권한으로 나누고 서버에서 거래 단위 접근 권한을 검사하겠습니다. 정산 조정처럼 영향이 큰 작업은 요청자와 승인자를 분리하고, 금액 한도나 추가 인증을 정책에 맞게 적용하겠습니다. 변경 전후 금액, 대상 거래, 사유, 실행자·승인자, 시각을 기록하며 기존 원장을 덮기보다 조정 이력을 추가하겠습니다. 중복 클릭과 재전송도 멱등하게 처리하고, 운영자가 DB를 직접 수정하지 않고 검증된 관리 기능으로 복구할 수 있게 하겠습니다.

## 10. 기술 선택·협업·주도성·비즈니스 판단

### 91. Java·Spring 실무 경험이 있는데도 개인 프로젝트에서 NestJS·Next.js를 선택한 이유는 무엇인가요?

옥화당에서는 NestJS로 주문·결제 API를, Next.js로 고객 화면과 운영자 화면을 개발했습니다. 이 선택을 설명하는 기준은 개인 프로젝트에서 화면부터 서버까지 변경을 연결하기 쉬운지입니다. TypeScript를 함께 사용하면 언어 전환 부담이 줄고 NestJS의 모듈·DI 구조는 Spring 경험을 활용하기에도 좋습니다. 다만 타입을 공유해도 외부 입력이 검증되는 것은 아니므로 서버의 런타임 검증은 별도로 필요합니다. 조직에서는 개인의 익숙함보다 기존 운영 역량과 유지보수 비용을 우선하겠습니다.

> 확인 메모: 기술 선택의 실제 계기와 비교 후보는 사용자 확인이 필요한 답변 초안입니다.

### 92. Java·Spring과 TypeScript·NestJS를 모두 사용한 경험을 바탕으로, 금액과 거래 상태를 다루는 서비스에서 각각 주의할 점을 설명해 주세요.

두 환경 모두 금액 표현과 상태 전이 규칙을 명시적으로 다뤄야 합니다. Java에서는 BigDecimal을 문자열 등 정확한 입력으로 만들고 스케일·반올림 정책을 정하겠습니다. TypeScript의 number는 정수 안전 범위와 소수 오차를 고려해야 하므로 최소 통화 단위 정수 또는 검증된 십진수 표현을 선택하고 DB·JSON 변환도 확인하겠습니다. Spring의 프록시 기반 트랜잭션 경계와 NestJS·TypeORM의 트랜잭션 매니저 전달 방식은 다르지만, 결제·재고 갱신이 같은 트랜잭션에 참여하는지 검증해야 한다는 원칙은 같습니다.

### 93. “취소한 주문의 쿠폰을 복원해 달라”는 요구를 받으면 구현 전에 어떤 정책과 예외 상황을 확인하겠나요?

전체 취소와 부분 취소를 먼저 구분하고, 쿠폰 유효기간이 지났거나 이미 다른 주문에 사용된 경우의 정책을 확인하겠습니다. 발급 수량 제한, 1인당 사용 횟수, 최소 주문금액, 다른 할인과의 중복 조건도 복원 후 유지할지 합의해야 합니다. 처리 시점은 취소 요청 접수가 아니라 실제 취소 확정과 연결하고, 같은 취소 이벤트를 여러 번 받아도 쿠폰은 한 번만 복원되게 하겠습니다. 환불 금액 계산과 쿠폰 권리 복원을 구분해, 고객에게 각각의 처리 상태를 안내하겠습니다.

### 94. 출시 일정이 촉박한 결제 기능에서 반드시 지켜야 할 조건과 나중으로 미룰 수 있는 범위는 어떻게 구분하나요?

금액 검증, 중복 청구 방지, 권한 검증, 거래 추적, 실패 복구는 일정 때문에 생략할 수 없는 조건으로 보겠습니다. 대신 처음 지원할 결제 수단이나 프로모션 조합, 운영 화면의 편의 기능은 범위를 줄일 수 있습니다. 자동화가 늦어지는 업무는 검증·승인·기록을 갖춘 수동 절차로 한시적으로 처리할 수 있지만, 원장을 직접 고치는 식의 우회는 피하겠습니다. 출시 전 핵심 장애 시나리오와 롤백 조건을 합의하고 작은 범위부터 적용해 실제 거래 결과를 확인하겠습니다.

### 95. 문제의 특성을 고려해 익숙한 기술이나 복잡한 구조를 일부러 선택하지 않은 경험이 있나요?

고산운은 JavaScript·Canvas·Node.js로, 영상 제작 도구는 Python·FFmpeg로 구현했습니다. 같은 언어로 통일하기보다 브라우저 렌더링과 실시간 상호작용에는 웹 기술을, 영상 합성과 인코딩에는 해당 도구 생태계를 활용하는 방식입니다. 설계를 설명할 때도 우선 현재 규모에서 한 프로세스와 명확한 처리 경계로 해결할 수 있는지 보겠습니다. 분산 시스템이 필요한 근거가 없다면 운영 지점을 늘리는 구조를 서둘러 도입하지 않고, 실제 병목과 장애 요구가 드러날 때 확장하겠습니다.

> 확인 메모: 실제로 검토 후 제외한 기술이나 아키텍처는 기록에 없습니다. 마지막 부분은 기술 선택 원칙이며 특정 도입을 거절한 과거 사례가 아닙니다.

### 96. 코드 리뷰에서 동료와 트랜잭션 범위나 데이터 모델에 대한 의견이 갈렸을 때 어떻게 합의하겠나요?

먼저 서로 지키려는 조건을 문장으로 맞추겠습니다. 예를 들어 주문과 재고가 항상 함께 바뀌어야 하는지, 외부 결제 실패를 어느 상태로 남길지부터 합의해야 트랜잭션 범위를 논의할 수 있습니다. 이후 각 안을 같은 동시성·실패 시나리오에 대입하고, 필요하면 작은 재현 테스트로 잠금 시간이나 복구 가능성을 비교하겠습니다. 취향보다 정확성, 운영 복잡도, 변경 비용을 기준으로 결정하고, 선택 이유와 나중에 재검토할 조건을 기록하겠습니다.

### 97. 사내 기술 블로그와 서버개발그룹 밋업에서 공유한 내용은 무엇이며, 받은 피드백이 실제 코드나 운영 방식에 영향을 주었나요?

사내에서는 SQL 진입점 로깅처럼 실제 운영 문제를 개선한 과정을 기술 블로그와 서버개발그룹에서 공유했습니다. 저는 결과 수치만 전달하기보다 어떤 정보가 부족해 원인 파악이 어려웠고, 변경 후 어떤 경로로 문제를 추적할 수 있게 됐는지 설명하는 것이 중요하다고 생각합니다. 피드백을 코드에 반영할 때는 적용 범위나 예외 상황을 구체화해 재현 가능한 개선 항목으로 바꾸겠습니다. 공유의 가치는 발표 자체보다 동료가 같은 문제를 더 빨리 해결하도록 만드는 데 있습니다.

> 확인 메모: 실제 받은 피드백과 그로 인해 변경된 코드·운영 사례는 자료에 없어 만들지 않았습니다. 발표 자료에서 한 사례를 확인하면 답변을 더 구체화할 수 있습니다.

### 98. 요청받은 기능 구현을 넘어 스스로 문제를 발견하고 끝까지 해결한 경험을 설명해 주세요.

우아한형제들에서 장애 원인 파악에 시간이 오래 걸리는 문제를 개선한 경험이 있습니다. SQL만으로는 업무 진입점과 실행 흐름을 연결하기 어려웠기 때문에 MDC 기반 SQL 진입점 로깅을 구현했고, 평균 원인 파악 시간을 25분에서 9분으로 줄였습니다. 기능이 동작하는지에 그치지 않고 운영자가 문제를 찾는 과정까지 개선한 사례입니다. 이후 해결 과정을 사내에 공유해 개인의 문제 해결 경험이 다른 개발자의 진단에도 쓰일 수 있도록 했습니다.

> 확인 메모: 개선 과제를 처음 제안한 주체와 본인이 맡은 범위는 면접 전 확인해야 합니다. 성과의 측정 기준도 83번 확인 메모와 같습니다.

### 99. 본인의 설계나 판단이 잘못됐던 경험은 무엇이며, 이를 어떻게 알아차리고 수정했나요?

정확히 설명하려면 세부사항을 충분히 확인한 뒤 공유해야 한다고 생각해 초기 공유가 늦어지는 경향이 있었습니다. 하지만 분석이 완성될 때까지 기다리면 동료가 위험을 늦게 알거나 의사결정을 미룰 수 있다는 점을 인식했습니다. 그래서 현재는 확인된 사실, 아직 가설인 부분, 당장 필요한 판단을 먼저 나누고 상세 분석을 단계적으로 보완하는 방향으로 바꾸고 있습니다. 정확성과 빠른 공유는 반대되는 가치가 아니라, 불확실성을 명시하면 함께 지킬 수 있다고 배웠습니다.

> 확인 메모: 기존 지원서에 기록된 공유 방식의 개선 경험을 사용했습니다. 특정 장애·일정 지연 사건이나 정량 효과는 자료에 없어 추가하지 않았습니다.

### 100. 크리에이터의 빠른 정산 요구와 재무 담당자의 정확성·검증 요구가 충돌한다면, 어떤 근거와 절차로 해결책을 제안하겠나요?

먼저 빠른 정산이 필요한 이유와 검증에 시간이 걸리는 지점을 각각 확인하겠습니다. 실제 대기 시간이 데이터 수집, 대사, 승인 중 어디에서 생기는지 측정하면 정확성을 낮추지 않고 줄일 수 있는 시간이 보입니다. 정상 거래는 자동 검증으로 빠르게 확정하고, 불일치가 있는 거래만 보류하는 방식을 제안하겠습니다. 정산 예정 금액과 출금 가능 금액을 분리해 예상 일정과 보류 사유도 안내하겠습니다. 지급을 앞당기는 정책이 필요하다면 환불 위험과 회수 조건을 재무·사업 담당자와 합의한 뒤 제한된 범위에서 검증하겠습니다.
