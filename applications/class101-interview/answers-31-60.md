### 31

옥화당에서는 연속 클릭과 통신 재시도로 결제 준비가 중복되는 문제를 막는 멱등 처리를 구현했습니다. 키는 구매 시도별 UUID와 고객·작업 범위로 구분하고, 같은 시도의 재요청에는 동일한 키를 사용하겠습니다. 요청 해시와 처리 결과를 함께 저장해 내용이 같은 요청만 기존 결과를 재사용하게 하겠습니다.

동시 요청은 DB 유일 제약으로 처리 주체를 하나로 제한하겠습니다. 최초 삽입에 성공한 요청만 실행하고, 나머지는 완료 결과나 처리 중 상태를 돌려줍니다. PG가 멱등 요청을 지원하면 같은 작업 키를 전달하고, 서버가 중단되거나 타임아웃이 발생하면 거래 조회로 결과를 복구해 외부 중복 결제도 막겠습니다.

**핵심 키워드:** 요청 해시 · 충돌 응답 · 동일 의미 · 변경 금지

같은 멱등 키에 다른 금액이나 상품이 들어오면 충돌 오류를 반환하겠습니다. 최초 요청의 주문 ID·통화·확정 금액을 정규화해 해시로 저장하고 재요청과 비교합니다. 해시가 다르면 409와 명확한 오류 코드를 반환하고 새 구매 시도에는 새 키를 사용하게 해, 기존 요청과 결과가 덮어써지지 않도록 하겠습니다.

**핵심 키워드:** 결과 미확정 · 거래 조회 · 동일 키 · 상태 전이

타임아웃은 결제 실패가 아니라 결과 미확정으로 처리하겠습니다. 주문이나 PG 거래 식별자로 승인 여부를 조회하고, 재호출이 필요하면 PG의 멱등 보장 범위 안에서 같은 키를 사용합니다. 조회·웹훅·대사로 받은 결과는 동일한 상태 전이 로직에서 한 번만 반영하고, 장기 미확정 건은 운영 알림으로 관리하겠습니다.

**핵심 키워드:** 서명 검증 · 중복 제거 · 상태 전이 · 순서 역전

웹훅은 서명 검증 후 이벤트 ID의 유일 제약으로 중복을 걸러내겠습니다. 이벤트를 안전하게 저장한 뒤 응답하고, 후속 처리는 재시도 가능하게 분리합니다. 도착 순서대로 상태를 덮어쓰지 않고 허용된 전이만 반영해 오래된 승인 이벤트가 환불 완료를 되돌리지 못하게 하며, 불명확한 경우 PG 거래를 조회하겠습니다.

### 36

**핵심 키워드:** 서버 금액 · 주문 스냅샷 · 승인 대조 · 보상 처리

### 37

**핵심 키워드:** 짧은 트랜잭션 · 외부 호출 분리 · 조건부 갱신 · 재처리

PG 호출은 DB 트랜잭션 밖으로 분리하겠습니다. 네트워크 지연 동안 락과 커넥션을 점유하고, DB 롤백으로 외부 승인을 취소할 수도 없기 때문입니다. 결제 시도를 먼저 저장·커밋한 뒤 PG를 호출하고, 결과는 별도 트랜잭션에서 조건부로 반영하겠습니다. 단계 사이의 장애는 멱등 요청과 거래 조회로 복구합니다.

### 38

환불 가능액에서는 완료된 환불뿐 아니라 진행 중인 예약액도 빼겠습니다. 결제 행 잠금이나 조건부 UPDATE로 금액을 먼저 예약한 뒤 PG를 호출하고, 성공하면 확정 환불액으로 전환합니다. 타임아웃 때는 예약을 바로 풀지 않고 결과를 조회해, 동시 부분 환불이 같은 잔여액을 중복 사용하지 못하게 하겠습니다.

### 39

부분 환불은 주문 당시의 상품별 할인 배분과 결제 수단별 부담액을 기준으로 계산하겠습니다. 쿠폰 복원, 유상·무상 캐시 구분, 반환 순서는 기획·재무와 정책으로 확정합니다. 최소 단위 잔액도 일관된 규칙으로 배분하고, 상품별 합계와 수단별 누적 환불액을 검증해 원래 결제액을 초과하지 않게 하겠습니다.

### 40

**핵심 키워드:** 청구 기간 · 유일 제약 · 멱등 지급 · 대사

구독 ID와 청구 기간에 유일 제약을 두고, 하나의 청구에 여러 결제 시도를 연결하겠습니다. 성공한 청구의 추가 승인을 막고, 이용권은 확인된 성공 이벤트를 멱등하게 처리해 한 번만 지급합니다. 실패 재시도와 유예기간을 정책으로 관리하되 미확정 결제를 실패로 단정하지 않고, 결제 성공과 이용권 지급의 불일치도 대사하겠습니다.

### 41

**핵심 키워드:** 단계별 상태 · 정산 명세 · 출금 예약 · 원거래 추적

결제·정산·출금은 각각 상태와 이력을 분리하겠습니다. 결제와 환불을 바탕으로 계약·기간·통화별 명세를 계산하고, 검증·확정된 금액만 출금 가능액에 반영합니다. 출금 시 금액을 예약해 중복 사용을 막고, 이체 접수와 실제 완료도 구분하겠습니다. 모든 단계에 원거래 ID를 연결해 자금 흐름을 역추적하겠습니다.

네 금액은 의미와 확정 시점이 다르므로 분리해야 합니다. 결제액은 고객 승인 금액이고 매출액은 회사의 인식 기준을 적용한 금액이며, 정산 예정액에는 계약상 배분·수수료·환불이 반영됩니다. 출금 가능액은 지급 조건을 충족한 금액에서 보류·예약액을 제외한 값이므로, 이를 합치면 아직 지급하면 안 되는 돈이 출금될 수 있습니다.

`double`은 십진 소수를 정확히 표현하지 못해 금액 계산에서 오차가 누적될 수 있습니다. Java에서는 문자열이나 정수에서 만든 `BigDecimal`, MySQL에서는 범위에 맞는 `DECIMAL`을 사용하겠습니다. 금액에 통화를 함께 저장하고 중간 계산의 정밀도와 최종 반올림 규칙을 명시해, API와 DB 사이에서도 정밀도를 유지하겠습니다.

과거 정산을 재현하려면 당시 계약 버전과 계산 입력을 함께 보관해야 합니다. 요율·공제·환율·반올림 규칙·로직 버전을 확정 명세에 연결하고 과거 정책은 변경하지 않겠습니다. 재계산은 기존 명세를 덮어쓰지 않고 새 실행과 차이를 기록하며, 동일 입력과 버전에서 같은 결과가 나오는지 회귀 테스트로 검증하겠습니다.

확정된 정산을 수정하기보다 원거래에 연결된 환불·조정 항목을 추가하겠습니다. 출금 전에는 지급 가능액에 반영하고, 이미 지급했다면 계약에 따라 다음 정산에서 차감하거나 별도로 회수합니다. 고객 환불과 크리에이터 회수 상태를 분리해 한쪽 실패를 추적하고, 음수 잔액의 출금 제한과 조정 사유·승인 이력을 남기겠습니다.

기간·시간대·통화·마감 기준을 맞춘 뒤 PG 거래 ID로 승인과 취소를 비교하겠습니다. 건수와 총액에서 시작해 거래별 누락·금액 차이·상태 차이를 분류하고, 지연 데이터는 재대사합니다. 양쪽 입력과 실행 이력을 보관하며 확실한 누락만 멱등하게 복구하고, 나머지는 담당자와 해결 이력이 있는 예외 목록으로 관리하겠습니다.

한 테이블은 초기 구현이 단순하지만 여러 결제 시도와 부분 환불이 생기면 상태가 복잡해집니다. 주문은 구매 내용, 결제 시도는 요청과 결과, 승인·환불은 실제 금전 변동으로 분리하겠습니다. 주문과 결제를 일대다로 연결하고 거래 ID에 유일 제약을 두되, 서비스 분리보다 같은 DB 안에서 모델과 트랜잭션 경계를 먼저 명확히 하겠습니다.

### 52

### 55

**핵심 키워드:** 커서 조회 · 복합 정렬 키 · 상한 고정 · 스냅샷

추가되는 거래 내역에는 생성 시각과 고유 ID를 사용하는 커서 페이지네이션을 적용하겠습니다. 마지막 키 다음부터 조회하고 시작 시 상한을 고정해 새 거래 때문에 페이지가 밀리는 문제를 줄입니다. 다만 상태 필터가 도중에 바뀌면 커서만으로 일관성을 보장할 수 없으므로, 정확한 전체 추출은 기준 시점 스냅샷으로 처리하겠습니다.

### 56

**핵심 키워드:** 관계형 모델 · 트랜잭션 · 정확한 금액 · 운영 비용

결제·정산의 기준 데이터에는 MySQL을 우선 선택하겠습니다. 주문·결제·환불의 관계가 명확하고 유일 제약·트랜잭션·정확한 십진 타입으로 불변 조건을 표현하기 좋기 때문입니다. MongoDB도 트랜잭션을 지원하므로 지원 여부만으로 판단하지 않고, 접근 패턴과 스키마 유연성의 이득이 운영·대사 비용을 상쇄하는지 비교하겠습니다.

### 57

**핵심 키워드:** 조회 유연성 · N+1 · 접근 권한 · 복잡도 제한

GraphQL은 크리에이터와 운영 화면이 서로 다른 상세 항목을 요구할 때 필요한 필드를 유연하게 조회할 수 있습니다. 반면 중첩 조회의 N+1과 비용 증가, 객체·필드별 권한 누락을 관리해야 합니다. 배치 로딩과 페이지 크기·깊이·복잡도 제한을 적용하고, 조회 유연성의 이득이 운영 복잡성보다 클 때 도입하겠습니다.

### 58

**핵심 키워드:** API 92개 · 의존관계 · 공통 기반 · 단계별 전환

가게홈 서버 구축에서 전시 API 92개를 이관하며 모듈·테이블 의존관계 정리와 다중 데이터소스 구성, DB·Redis 이관을 수행했습니다. 이관 관리는 호출 주체·읽기와 쓰기 경로·캐시·검증 상태를 API별로 연결하는 것이 핵심입니다. 공통 기반부터 준비하고 영향과 복구 가능성에 따라 전환 순서를 정해 데이터 소유권과 호환성을 유지하겠습니다.

### 59

**핵심 키워드:** 호환성 비교 · 단계적 전환 · 쓰기 안전 · 롤백

가게홈 이관에서는 단계별 배포 전 검증을 거쳐 기능을 운영 중단 없이 전환했습니다. 호환성은 응답 스키마·정렬·오류·권한·캐시까지 비교하고, 쓰기 요청은 중복 재생하지 않겠습니다. 제한된 범위부터 오류율·지연·업무 지표를 보며 전환하고, 롤백은 라우팅뿐 아니라 신규 데이터의 구버전 호환성과 단일 쓰기 주체까지 보장하겠습니다.

### 60

**핵심 키워드:** 확장·이행·정리 · 점진 보충 · 호환성 · 잠금 관측

스키마는 확장·이행·정리 순서로 변경하겠습니다. 호환 컬럼과 새 쓰기 경로를 먼저 준비하고, 과거 데이터는 작은 묶음으로 보충하되 최신 값을 덮어쓰지 않도록 조건을 둡니다. 양쪽 결과 검증 후 읽기를 전환하고 관찰 기간을 거쳐 이전 구조를 제거하겠습니다. 온라인 DDL도 작업별 잠금과 복제 지연을 실제 규모에 가까운 환경에서 검증합니다.
