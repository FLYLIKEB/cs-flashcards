01. Next.js · React

화면이 어떻게 만들어지고 사용자와 반응하는지부터 잡아요.

React · 컴포넌트화면을 작은 조각으로 나누어 만드는 도구예요.

버튼, 강의 카드, 결제 폼을 각각 컴포넌트로 만들어요. props는 부모가 전달하는 정보, state는 컴포넌트가 기억하는 현재 상태예요.

쉽게 떠올리면
강의 카드에 제목을 props로 전달하고, 신청 버튼을 눌렀는지는 state로 표현할 수 있어요.

이렇게 말해보세요

/courses는 강의 목록, /courses/123은 강의 상세예요. 공통 상단 메뉴는 layout에 둘 수 있어요.

이렇게 말해보세요

Server · Client Component서버에서 할 일과 브라우저에서 할 일을 나누는 기준이에요.

Server Component는 서버 쪽에서 데이터를 읽고 화면을 구성하는 데 쓰여요. Client Component는 클릭·입력·state·브라우저 API 같은 상호작용에 필요해요. use client는 그 경계를 선언해요.

쉽게 떠올리면
강의 소개를 읽어 오는 부분과, 클릭할 때 열리는 신청창을 나누는 식이에요. Client Component도 첫 화면에서는 서버가 만든 HTML을 활용할 수 있어요.

이렇게 말해보세요
“데이터 조회와 비밀값은 서버 쪽에 두고, 상호작용이 필요한 범위에 클라이언트 컴포넌트를 쓰겠습니다.”

SSR · SSG · ISR화면을 언제 만들어서 보여 줄지에 관한 용어예요.

SSR은 요청 시점에 서버가 화면을 만들고, SSG는 미리 만들어 둬요. ISR은 만들어 둔 정적 결과를 갱신하는 방식이에요. 실제 사용 방식은 Next.js 버전과 라우터·캐시 설정을 함께 봐야 해요.

쉽게 떠올리면
거의 안 바뀌는 강의 소개는 미리 준비할 수 있지만, 개인별 결제 상태는 최신성·권한이 중요해요.

이렇게 말해보세요
“페이지마다 얼마나 최신이어야 하는지와 개인별 정보인지부터 구분하겠습니다.”

Loading · Error · 사용자 피드백기다리는 중인지, 실패했는지를 화면에 알려 주는 장치예요.

로딩 상태는 작업 중임을 보여 주고, 오류 상태는 다시 시도할 방법을 알려 줘요. Next.js에는 경로의 로딩과 오류 화면을 구성하는 규칙이 있어요.

이렇게 말해보세요
“정상 화면뿐 아니라 대기·실패·재시도 화면까지 한 흐름으로 보겠습니다.”

Server Action · Route Handler서버에서 데이터를 바꾸거나 HTTP 요청을 처리하는 진입점이에요.

Server Action은 폼 제출 등 서버의 데이터 변경 작업에 연결할 수 있어요. Route Handler는 GET·POST 같은 HTTP 요청을 처리해요. 어느 쪽이든 서버에서 입력·인증·권한을 검사해야 해요.

이렇게 말해보세요

이렇게 말해보세요

이렇게 말해보세요
“요청 처리와 업무 규칙을 구분해 변경·테스트하기 쉽게 만들겠습니다.”

03. API · 인증 · 결제

신청과 결제가 안전하게 한 번 처리되는 흐름을 떠올려요.

HTTP · API · 상태 코드프로그램끼리 요청과 응답을 주고받는 약속이에요.

API는 기능을 사용하는 접점이고, HTTP는 웹에서 요청을 전달하는 방법이에요. 메서드·상태 코드·응답 내용을 함께 봐야 성공과 실패를 이해할 수 있어요.

쉽게 떠올리면
강의 조회와 신청 저장은 목적이 달라요. 실패했을 때도 권한 부족인지, 입력 문제인지, 서버 문제인지 알려 줘야 해요.

이렇게 말해보세요
“요청 목적과 실패 이유가 드러나는 응답을 설계하겠습니다.”

인증 · 인가누구인지 확인하는 것과 해도 되는지 확인하는 것은 달라요.

인증은 사용자의 신원을 확인하고, 인가는 그 사용자가 특정 데이터나 기능에 접근할 권한이 있는지 확인해요. 화면에서 버튼을 숨겨도 서버 권한 검사는 필요해요.

쉽게 떠올리면
로그인했더라도 다른 사람의 주문을 취소할 수는 없어야 해요.

이렇게 말해보세요
“로그인 여부와 해당 주문의 소유권을 서버에서 각각 확인하겠습니다.”

쿠키 · 세션 · JWT로그인 상태를 다음 요청에서도 알아보게 하는 재료들이에요.

쿠키는 브라우저가 서버로 보내는 저장 수단, 세션은 요청 사이의 상태를 관리하는 방식이에요. JWT는 정보를 담는 토큰 형식이에요. 서명만 된 JWT는 내용을 암호화하지 않으므로 비밀값을 넣지 않아요.

쉽게 떠올리면
입장 팔찌를 보여 주는 것과 비슷해요. 팔찌를 어디에 보관하고, 누가 발급했고, 언제 무효로 할지도 정해야 해요.

이렇게 말해보세요
“토큰 형식만 고르기보다 저장·만료·폐기·권한 확인을 함께 설계하겠습니다.”

CORS · 출처다른 출처의 응답을 브라우저 코드가 읽어도 되는지 정하는 규칙이에요.

출처는 스킴·호스트·포트의 조합이에요. CORS는 브라우저의 교차 출처 접근 정책이며, 로그인 검사나 서버의 접근권한 검사를 대신하지 않아요.

쉽게 떠올리면
프론트와 API 주소가 다르면 CORS 설정이 필요할 수 있어요. 허용 출처를 넓혔다고 API가 안전해지는 것은 아니에요.

이렇게 말해보세요
“CORS와 인증·인가를 서로 다른 책임으로 구분하겠습니다.”

Webhook · 서명 검증외부 서비스가 일이 생겼다고 우리 서버에 알려 주는 요청이에요.

결제사는 승인·취소 같은 이벤트를 웹훅으로 알려 줄 수 있어요. 서명을 검증하고 중복·지연·순서 변경에 대응해야 해요. 화면의 성공 메시지만으로 결제를 확정하면 안 돼요.

쉽게 떠올리면

이렇게 말해보세요
“검증된 결제 이벤트를 기준으로 상태를 반영하고 중복 전달에도 안전하게 처리하겠습니다.”

쉽게 떠올리면

이렇게 말해보세요
“재시도는 허용하면서 중복 결제 같은 부작용은 막겠습니다.”

04. DB · 정합성 · 캐시

빠르게 보여 주면서도 주문과 결제 기록이 맞아야 해요.

관계형 DB · 기본키 · 외래키데이터를 표로 나누고 관계와 규칙을 정하는 저장 방식이에요.

기본키는 한 행을 식별하고, 외래키는 다른 표의 행과 연결해요. 제약조건은 저장하면 안 되는 데이터를 DB에서도 막아 줘요.

“클릭 수와 실제 결제 성공을 구분하고, 취소·환불 반영까지 살피겠습니다.”
